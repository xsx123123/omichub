# Web 容量优化与多进程实测

> 类型：2026-10-27 第二轮运行快照；中间件改动已在工作区，**未发布到现有 Web**。
> 前置基线：[首轮 Web / Celery 容量报告](CygnusX_web_capacity_assessment.md)。
> 状态：固定 500 RPS 短时验收通过；1000 / 2000 RPS 未通过；10000+ RPS 尚未达成。

## 1. 改动与约束

`AuditMiddleware` 对非写操作直接传递 ASGI 调用，避免原来不执行审计却仍建立
BaseHTTPMiddleware task group / 响应体转发的开销。POST/PUT/PATCH/DELETE 保留原 dispatch
与落库路径。`CookieRequiredMiddleware` 对非消费路径、关闭计费功能或非 HTTP 的调用
直接传递；真实消费请求仍走原来的冻结/停用账户守卫。两个 dispatch 补齐了端点类型注解。
没有引入跨请求权限缓存、响应缓存、认证豁免或关闭限流，也没有修改业务响应。

新增 `scripts/web_capacity_server.py` 只供隔离容量验证：使用真实应用、路由、中间件和
数据库，仅替换启动/关闭生命周期，不运行迁移、种子同步、沙箱预热或 Provider 探测。
它不是生产入口。端口限定在 18000..18999，支持有界运行、cProfile、配置清单输出。
`--legacy-wrappers` 仅在该独立进程内恢复这两个类原先继承的 `BaseHTTPMiddleware.__call__`，
用于同配置对照；不修改现有 Web 的进程内对象。

## 2. 性能剖析与单进程对照

剖析基于真实五接口混合请求，发现 FastAPI 路由匹配、OTel 路由识别及多层 HTTP
中间件调度都有明显 CPU 成本。cProfile 会显著放大开销，其 91 RPS 不能作为容量结论；
原始 `.pstats` 与按内部耗时排序的输出保留在运行证据中。

对照均关闭 APP_DEBUG，保留遥测与完整鉴权，数据库 pool=4 / overflow=0；
每次 20 个独立测试用户、无操作间隔、3 秒预热、30 秒测量，交替运行两轮。
实例清单确认旧模式调用 `BaseHTTPMiddleware.__call__`，新模式调用各自的 fast path。

| 轮次 | 旧包装成功 RPS | 新路径成功 RPS | 旧 P95 ms | 新 P95 ms | 错误率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 213.38 | 235.20 | 186.89 | 148.31 | 均 0% |
| 2 | 210.88 | 231.27 | 188.06 | 149.91 | 均 0% |

本次平均成功吞吐提升约 9.9%，P95 降低约 20.5%；这是短时对照，不是统计置信区间
或大数据量用户的保证。后续不能通过跳过安全检查来追求万级数字。

## 3. 一个入口连接多个 Web 进程

四个独立 Python / Uvicorn 进程在同一宿主机、同一现有容器内的独立端口运行，
每进程 pool=4 / overflow=0。临时 Nginx 以非 root 的 nginx 用户运行在未映射到宿主
公网端口的 18180，使用 least_conn 与 upstream keepalive；通过私有网络访问。
没有修改原 Nginx 的 8888 入口、限流规则、Compose 或生产进程。
这验证的是**同机独立 Web 进程扩展**，不等于跨机器/多 Pod 的可用性验收。

每档 100 个独立测试用户持续请求，预热 3 秒，测量 30 秒：

| Web 进程数 | 成功 RPS | 成功 P95 ms | 错误率 | 1 秒 P95 基线门槛 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 208.59 | 1005.92 | 0% | 未通过 |
| 2 | 350.65 | 644.86 | 0% | 通过 |
| 4 | 626.49 | 352.78 | 0% | 通过 |

四进程约为单进程的 3.00 倍，并非理想的 4 倍。Nginx 独立访问日志确认所有目标
进程都处理了请求，四进程阶段累计分配约 17.5k–18.1k 个请求/进程，包括预热和随后
的固定到达率测试。数据库最多额外使用 16 个连接，而不是套用默认每进程 30 个连接。

## 4. 固定到达率验收

对同一个四进程入口运行 k6，100 个测试身份轮换，5 个真实只读业务 API 等权混合。
每档 30 秒、预分配 200 VU、最多 300 VU。目标门槛：错误率 <1%、有效业务响应 >99%、
P95 <300ms、P99 <1s、`dropped_iterations == 0`。

| 目标 RPS | 完成请求数 | 实际 HTTP RPS | P95 ms | HTTP 错误率 | 丢弃到达 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 500 | 15001 | 499.93 | 15.29 | 0% | 0 | 通过 |
| 1000 | 17416 | 576.96 | 1047.53 | 0% | 12585 | 未通过 |
| 2000 | 17903 | 591.10 | 1019.48 | 0% | 42098 | 未通过 |

1000 / 2000 是配置的目标到达率，不能把它们标为实际处理能力。服务变慢后到达
负载需要更多在途 VU，达到 300 VU 上限后产生丢弃；即使完成请求都返回 200，
也没有兑现目标速率。未来验收既要有足够的压测端容量，也要满足服务器延迟门槛。

## 5. 适用范围与后续工作

测试仍使用空项目/任务/会话的普通账号，未覆盖密码登录、SSE/上传、LLM 生成或计算任务。
所有进程与压测机在同一台 16 核宿主机上；结果不是生产长时稳定性或跨主机容量承诺。
临时 Web / Nginx 已退出，100 个本轮测试账号与 JWT 已撤销并清理，原服务仍健康。

当前固定 500 RPS 是新的已验收短时基线，10000+ RPS 仍需真实规模数据、更多 CPU /
主机、路由开销剖析、请求内重复查询优化、明确的连接池预算，以及完整的共享状态验证。
不能直接按四进程成绩线性推算几十个实例。部署多副本前仍须完成首轮报告列出的
独立迁移步骤、单实例 Beat、启动副作用治理、共享文件存储、取消/重连和摘流契约。

## 6. 验证与证据

`evidence/web-capacity-optimization/` 保存本轮运行产物，不入提交：

- `profile.pstats` / `profile-top.txt`：真实请求 CPU 剖析。
- `legacy{1,2}.json` / `fast{1,2}.json` 与实例 manifests：交替对照。
- `scale-{1,2,4}.json`、`scale-run.json`、`gateway-distribution.json`：多进程实际吞吐与分流。
- `k6-{500,1000,2000}-summary.json` 与 logs：固定到达率成功及失败证据。
- `scale_probe.py` / `nginx-{1,2,4}.conf`：本次隔离实验的完整复跑逻辑与入口配置。
- `cleanup.json`：临时进程/账号/令牌撤销与原服务健康验证。
- `middleware-tests.txt` / `focused-{ruff,mypy}.txt`：定向验证。
- `full-ruff.txt` / `full-mypy.txt` / `unit-e2e.txt`：全仓检查原始结果。
- `baseline-failed-tests.txt` / `baseline-mypy.txt` / `mypy-comparison.json`：恢复旧包装后的失败复现与类型错误对照。

中间件定向回归 31 项通过，包括所有写方法的审计、冻结账户拦截、非消费路径、
WebSocket 原样透传、流式首块及时送达。新改动涉及的文件 Ruff 与 strict mypy 定向校验通过。
全量 unit/e2e 结果为 4191 通过、16 失败、22 跳过、63 隔离排除；恢复两个类的旧包装后，
这 16 项仍全部失败（服务 mock、配置契约、Redis/审批链路等），不是本次 fast path 引入。
全仓 Ruff 有 265 项错误；strict mypy 当前 992 项，原中间件基线为 1001 项，归一化对照
没有新增错误，9 项减少来自 dispatch 类型补齐。全仓检查仍不绿，不能宣称全量门禁通过。
没有提交、发布或修改用户的其他脏文件。
