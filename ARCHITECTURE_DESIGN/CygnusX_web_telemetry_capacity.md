# Web 静态路由监控标签容量快照

> 实测日期：2026-10-27。第四轮隔离实验，候选代码未重启生产服务发布。
> 前序：[原始容量](CygnusX_web_capacity_assessment.md)、
> [中间件与多进程](CygnusX_web_capacity_optimization.md)、
> [请求内身份复用](CygnusX_web_request_identity_capacity.md)。
> 固定 1250 RPS 仅短时通过，1500/2000 RPS 未通过，10000+ RPS 未验收。

## 1. 范围与运行条件

仍为 Ryzen 7 8845HS（8 物理核、16 线程）同机测试，复用现有 Web 容器的依赖、
真实中间件、JWT、权限和 PostgreSQL。临时实例使用未发布的私网端口，入口为独立
Nginx master，未修改生产 Nginx 限流或重启已有服务。

100 个本轮专属普通账号轮询五种 GET：个人信息、项目列表、最近任务、会话列表、
模块注册表。账号业务数据为空，未测试上传、SSE、密码登录、写事务或大数据列表。
未运行 LLM、生信任务或沙箱；本轮未重复测 Celery，队列结论见前序报告。
`scripts/web_capacity_server.py` 仅跳过启动迁移/种子同步/Provider 探测/沙箱预热，
保留请求执行与监控，不能用作生产启动入口。

运行依赖为 FastAPI 0.141.1、Starlette 1.4.1，本轮未修改依赖锁。
单进程对照 pool=4、overflow=0；扩展测试每进程 pool=3、overflow=0。
16 个进程的临时池上限合计 48，不能按生产默认池参数直接复制成 16 个 Web。

## 2. 改动与可回退边界

剖析发现 OTel 的默认 span 标签解析每次遍历路由，重复解析固定接口有 CPU 开销。
`core/telemetry_routes.py` 复用标准静态路由的 span 名称和 `http.route` 属性，
保留官方 instrumentation 构建的完整中间件栈。

缓存按应用隔离，键区分 method/path/root_path/Host/scheme/server，默认最多
1024 条，键长上限默认 2048。返回属性复制；动态路径、未知 URL、非标准属性和
自定义匹配器不缓存。路由版本变化清空；版本能力不可用/读取失败走原解析器。
框架兼容性通过特性探测处理，不支持时跳过安装。

`TELEMETRY_ROUTE_CACHE_SIZE=0` 可关闭该功能。认证、权限、路由选择、业务处理、
span 和指标仍逐请求执行。没有引入用户/响应跨请求缓存，前轮身份复用仍限于单请求。

## 3. 同配置交替对照

每次 20 用户、无思考时间、3 秒预热、30 秒测量，先后交替运行两次。
两组都启用 telemetry，差异仅为标签缓存容量 0 / 1024。

| 组别 | 第一次成功 RPS | 第二次成功 RPS | 第一次 P95 ms | 第二次 P95 ms |
| --- | ---: | ---: | ---: | ---: |
| 原解析器 | 221.94 | 230.14 | 148.51 | 142.04 |
| 标签缓存 | 244.06 | 243.33 | 131.79 | 132.32 |

四次均零错误。两次均值的吞吐约提高 7.8%，P95 约降低 9.1%，仅说明本机该负载下
有改善，不代表所有接口或部署环境同幅度提升。
优化进程累计 16147 次请求，标签命中 16141 次、未命中 6 次，保存 6 条。
每请求 SELECT 仍约 2 次，两组相当，未通过跳过数据库读取获得吞吐。

## 4. 同机扩展与固定到达率

100 用户闭环、3 秒预热、30 秒测量：

| 临时进程数 | 成功 RPS | P95 ms | P99 ms | 错误率 |
| --- | ---: | ---: | ---: | ---: |
| 8 | 1124.67 | 133.42 | 452.21 | 0 |
| 16 | 1405.31 | 116.43 | 163.94 | 0 |

随后对 16 进程用 k6 固定到达率，各 30 秒，预分配 200 VU、最多 500。
通过要求业务成功率 >99%、HTTP 错误率 <1%、P95 <300ms、P99 <1s、丢弃到达数为 0。

| 目标 RPS | 完成请求 | 全程实际 RPS¹ | P95 ms | 丢弃到达 | 结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1250 | 37501 | 1241.12 | 58.34 | 0 | 短时通过 |
| 1500 | 36728 | 1212.35 | 885.58 | 8273 | 未通过 |
| 2000 | 34699 | 1147.14 | 929.17 | 25301 | 未通过 |

¹ k6 汇总包含停止与收尾时间。三档已发出的请求均业务成功；1500/2000 的丢弃与
延迟已经违反门槛，不能以 HTTP 零错误称为容量通过。1250 的退出码为 0，另外两档
均为阈值失败退出码 99。

前轮固定 1000 RPS 通过，本轮短时验证提高到 1250，但跨轮结果受同机负载影响，
不能把全部差异归因于本次标签缓存。严格因果对照见上一节的单进程交替实验。

## 5. 验证、证据与清理

专项单测覆盖有界 LRU、属性隔离、超长/动态/未知路径回退、Host/method/root 区分、
版本异常、嵌套路由更新与同长度路由替换失效，以及每次请求认证、独立 span 和
HTTP duration 直方图计数。专项类型与 Ruff 检查通过。

完整 unit/e2e：4213 通过、16 失败、22 跳过、63 隔离排除，失败集合与前轮完全相同。
全库 Ruff 仍为 265 项；包含旧 `telemetry.py` 导入顺序问题的文件级检查不全绿。
全库 mypy 为 988 项，较前轮增加的两项位于本轮未修改的 ReportCopilot 调用点；
本轮改动文件没有新增类型错误。迁移链静态检查通过。以上不构成全仓门禁通过，
这些候选变更尚未发布。

原始记录位于 `evidence/web-capacity-route-telemetry/`（运行证据，不入提交）：
`baseline*.json` / `optimized*.json`、`*-stats.json`、`scale-{8,16}.json`、
`scale-manifest-*.json`、`scale-sql-*.json`、`k6-*-summary.json`、`scale-run.json`。
完整回归与基线差异见该目录 `validation-comparison.json`。

临时 Web 和独立网关均已停止；100 个专属账号已删除，原 JWT 返回 401，宿主和
容器的 JWT 文件已删除，Nginx 仅剩原 master，Web/Worker/DB/Redis 健康。
机器检查见 `cleanup.json`。

## 6. 万级目标的下一步边界

多 Web 能分担请求，本机 8→16 进程仍有收益，但进程翻倍的收益已明显小于翻倍。
本实验不足以给出万级所需服务器数量；不能将 1405 RPS 线性外推为集群承诺。
应在独立预发布多机环境放置 Web、压测机与共享数据库/Redis，明确入口限流、
总连接预算和真实用户数据量，逐档运行 2000/5000/10000/12000 RPS。
万级验收至少持续 30 分钟，并同时观察 DB、队列积压、资源和故障恢复。
现有 k6 脚本可复用；云资源采购、生产扩容与发布尚未执行。
