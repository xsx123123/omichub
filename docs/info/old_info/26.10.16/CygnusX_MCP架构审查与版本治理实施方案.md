# CygnusX MCP 架构审查与版本治理实施方案

日期：2026-10-16  
版本：评审稿 v1.0  
用途：架构评审、仓库调查、分阶段实施和部署验收。

## 1. 结论与证据边界

CygnusX 已具备合理的 MCP 分层：注册与发现、上下文装配、传输适配、统一业务服务、沙箱、审计及 Builder 生命周期管理。§11 的“固定动词 + 动态 Flow 目录”正确识别了工具膨胀的根因。当前首要工作是完成暴露面收敛、统一执行权限、补齐真实链路验收，并将已有版本快照提升为完整的发布与回退体系。

本报告依据上传的 `CygnusX_mcp_architecture.md`，未核验实际仓库、数据库、容器和测试报告。所有“文档记载已实现”均不等于本次完成运行验证。本文新增的数据模型、状态机、预算和接口属于建议方案，不代表已有实现。

证据优先级：

1. 运行证据须注明部署版本、配置、环境和执行时间。
2. 代码与测试须注明提交和覆盖范围。
3. 文档中 §11 是 Flow 固定化的权威描述；§5 是较早 Builder as-built 记录。
4. §1–§3、§6–§10 是历史快照，不可直接视作当前系统。
5. 本次未提供的实施手册及 `mcp-server/ARCHITECTURE.md` 只能作为待查线索。

## 4. 三套暴露口径与目标模块边界

### 4.1 三套入口

| 入口 | 原有风险 | 目标 |
|---|---|---|
| Chat 每 Flow 自动工具 | 工具数随 Flow 增长 | 停止注册，保留编译器输出 describe 契约 |
| RNA/ATAC 四件套 | 双端平行维护 schema | 迁入统一服务，特殊规则保留为插件 |
| 外部通用提交 | 工具数固定但原校验浅 | 统一 prepare、确认和 submit |

统一服务不仅要复用提交函数，还要共享默认值、规范化参数、错误码、门控、权限和确认语义。协议适配层不得再实现另一份业务规则。

### 4.2 建议职责

| 模块 | 负责 | 不应承担 |
|---|---|---|
| Flow 契约与编译器 | 参数类型、默认值、约束、执行映射 | 为每个 Flow 注册工具 |
| AnalysisFlowToolService | discover/describe/prepare/submit 业务编排 | 绑定某个 MCP 传输 |
| 校验插件 | 可复用领域检查 | 增加 MCP 工具或暗中提交任务 |
| Chat/外部适配层 | 参数转换、协议响应 | 复制校验、确认或授权 |
| 上下文装配器 | 去重、选择、预算、能力裁剪 | 替代执行时权限检查 |
| Builder | 生成候选实现、验证、记录证据 | 自动扩大生产工具集合 |
| 发布管理 | 不可变版本、审批、激活、回退 | 直接修改历史快照 |

旧客户端兼容调用与默认发现应解耦。若框架不支持隐藏工具，采用独立兼容入口，并设置到期策略；不能将仍列在 tools/list 的 stub 计为工具数量已收敛。

## 5. Tool Pack、Capability 与防膨胀

Tool Pack 用于组织工具集合；Capability 表达可执行能力及约束；MCP Server 表达协议、部署和隔离边界；Flow 是目录数据。四者不可混为“一个业务能力就新建一个 Server/工具”。

有效暴露集合建议为：请求集合 ∩ Agent允许集合 ∩ 用户权限 ∩ 环境可用集合。调用阶段重新检查授权，防止猜工具名或绕过目录调用。

| 增长来源 | 约束 |
|---|---|
| Flow 数 | 固定工具不变；不在 schema 枚举全部 flow_id |
| 参数契约 | describe 按需读取，不塞全量 oneOf |
| 目录 | 筛选、分页、稳定游标；默认20条、最多50条为建议初值 |
| 实验能力 | 显式选择与预算，不默认挂载全部实验工具 |
| 结果 | llm_payload 独立限额，完整结果走 artifact 或分页 |
| 对话历史 | 契约按版本复用，避免每轮重复注入全目录 |
| 运行资源 | Server、进程、并发、版本存储、生成成本独立配额 |

“list 输出不随 Flow 数膨胀”只有在分页约束下才成立。固定工具数也不意味着平台总工具数恒定；任务、文件、下载及检索能力应有独立总预算。

## 6. Builder 与实验池审查

### 6.1 已有基础

§5 记载已有 mcp_builds、mcp_versions、mcp_reviews、预留 mcp_visibility，以及实验 TTL、审核、版本快照、转正和 rollback API。实验池自动进入 Chat 发现仍被列为后续项，不应假设已经启用。

### 6.2 必须补查的断点

- 注册早于测试审核：注册记录不等于获得执行权限；检查 invoke 是否按状态拒绝未发布构建。
- UDS 绕过 MCPClient：可以不复用不适用的 URL/命令校验，但必须有等价的鉴权、限流、超时、审计和输出控制。
- AST 不替代输出注入防护；合法代码仍可能返回不可信远程内容。
- PyPI 域名白名单不等于禁止运行时安装；需核验执行策略和依赖固定。
- 配额检查必须抗并发，不能先 count 再无保护插入。
- 版本历史、代码快照、回滚接口必须检查资源归属，不能仅检查已登录。

### 6.3 生命周期目标

到期立即拒绝新调用，异步清理仅负责资源回收。运行中任务采用明确的有限宽限或取消政策。清理定位到具体 Server 子进程，避免误杀同一 Studio 容器的其他工作。

§5.8 的“禁用后随空闲回收”与 §10 的“到期自动注销并销毁容器”并不完全一致，应统一为可测语义。容器共享时不应机械执行整容器销毁。

## 7. MCP 版本管理：核心设计

### 7.1 先定义版本对象

| 对象 | 含义 | 建议标识 |
|---|---|---|
| 实现版本 | 代码、模板或构建产物变化 | 不可变 version_id、artifact_digest |
| 契约版本 | 工具名、输入输出 schema、错误语义和行为变化 | contract_version、contract_digest |
| 运行环境版本 | 镜像、依赖、Python/SDK等 | 镜像 digest、lockfile digest |
| Flow 契约版本 | Flow 参数、校验与执行定义 | flow_contract_digest |
| 部署版本 | 某环境当前激活哪个发布物 | deployment_id、generation |

SemVer 是面向人的兼容性声明，不是完整性校验或排序真相。代码、契约和环境应以不可变 ID/digest 精确定位。版本升级不得增加带版本后缀的新工具名；工具身份保持稳定，版本由目录和部署记录承载。

### 7.2 三类 MCP 的回退边界

| 类型 | 可控内容 | 回退方式 |
|---|---|---|
| Builder 实验 MCP | 代码、工具快照、沙箱环境 | 重建目标版本并切换部署引用 |
| 平台内置 Preset | 与应用代码共同发布 | 使用平台镜像/应用发布回退，不只改 DB tools 快照 |
| 外部第三方 MCP | 本地配置与已发现契约 | 可固定可控镜像或端点；远程供应商代码不可控时只能检测漂移、停用或恢复旧配置 |

不能对不可控远端承诺“完整代码回退”。数据库 tools 快照回退也不代表真实执行代码已回退。

### 7.3 推荐版本包内容

每个版本至少保存：源构建ID、代码或制品引用及摘要、规范化工具契约摘要、依赖锁定、运行环境摘要、变更说明、兼容性判定、测试证据、创建者、时间、审批记录、前驱版本。秘密只保存 secret_ref，不把凭证写进代码、快照或日志。

契约摘要使用稳定规范化算法，并记录算法版本。纳入输入输出约束、默认值、影响语义的插件版本和行为声明；排除时间戳等非语义字段。插件实现变化不能仅靠 YAML 版本不变而漏检。

### 7.4 状态与晋级

建议版本状态：draft → validated → approved → released；失败进入 rejected，退役进入 deprecated/revoked。部署状态另设 preparing → ready → active → draining → stopped/failed。

版本发布与生产激活分离：released 表示可部署，不代表已在生产执行；回退不会删除新版本或改写历史状态。

版本生成、审批、激活和回退由服务端状态机强制执行，Prompt 中的流程说明不能替代门禁。

### 7.5 兼容性判定

| 变化 | 默认处理 |
|---|---|
| 新增必填参数、删参数、收窄约束 | 破坏性变化，主版本升级并人工复核 |
| 删除/重命名工具、改变副作用或身份语义 | 破坏性变化 |
| 新增可选参数 | 候选兼容变化，检查默认行为与实际客户端 |
| 输出字段删除/类型变化 | 按消费者契约判定，通常破坏性 |
| 仅修实现错误 | 候选补丁版本，仍需行为回归 |
| 文本描述变化 | 检查模型行为影响，不能仅因 schema 相同认定零风险 |

自动比较只给出建议，不把 SemVer 推导当作安全证明。契约完全一致也不代表业务行为等价。

## 8. 发布、回退与故障恢复

### 8.1 发布流程

1. 生成不可变版本，校验摘要与依赖。
2. 在受控环境执行握手、tools/list、契约校验和代表性业务用例。
3. 审批绑定精确 version_id/digest；审批后内容不可变。
4. 启动候选部署并健康检查，失败不修改 active 引用。
5. 使用数据库事务及 generation 比较交换激活引用，防止并发发布覆盖。
6. 广播失效事件，刷新跨进程发现缓存；事件丢失时通过 generation 校验补偿。
7. 保留旧部署有限时间供回退和排空，按版本记录指标与审计。

### 8.2 回退流程

回退是一次指向历史已验证版本的新部署操作，而非把 current_version 字符串改回去。

1. 检查操作者、资源归属、目标制品完整性、目标是否被撤销。
2. 检查旧版本与当前数据结构、权限策略、秘密引用及外部依赖是否兼容。
3. 展示当前/目标版本、契约差异、运行中调用数量和预期影响。
4. 使用现有审批机制绑定目标版本和预期 generation；必要时执行候选验证。
5. 原子切换 active 引用；新调用绑定新激活的目标版本。
6. 旧调用按原版本完成或按明确政策取消，不能中途混用实现。
7. 记录原因、actor、前后版本、证据和结果；验证失败保持原 active。

### 8.3 回退限制

- 代码回退不撤销已提交任务、外部 API 写入、文件删除或数据库变更；补偿须另设业务流程。
- 数据库结构采用兼容演进；破坏性迁移不能依赖普通版本回退恢复。
- 有状态工具需声明状态格式和迁移策略；无兼容证明则阻止自动回退。
- 已确认但未提交的 Flow 请求如契约或执行绑定变化，默认要求重新 prepare；即使回到旧契约，也不能复活已过期或已消费凭证。
- 被撤销的漏洞版本默认禁止回退，例外需明确受控审批。
- 旧版本清理不得删除仍被 active、运行中调用或保留策略引用的制品。

### 8.4 并发与缓存

同一 Server/环境的发布和回退使用 generation 乐观锁；冲突返回明确错误，要求重新读取。每次调用绑定 version_id、contract_digest 和 deployment_generation，整个调用不变。发现结果携带版本指纹；旧客户端发生不兼容时返回可识别的契约变更错误并要求重新发现，不静默使用过期 schema。

## 9. 数据模型与接口建议

优先扩展已有 mcp_versions，不创建第二套平行版本库。实际字段名须经仓库调查确认。

| 实体 | 建议补充 |
|---|---|
| mcp_versions | immutable ID、artifact/contract/runtime digest、manifest、状态、测试与审批引用、兼容性摘要 |
| mcp_deployments（建议新增） | server、environment、version、generation、状态、健康结果、created_by |
| mcp_servers | active deployment引用；保留 current_version 仅作兼容显示，避免双真相 |
| 发布/回退操作记录 | operation_id、idempotency_key、expected_generation、前后版本、原因、actor、结果 |
| 调用审计 | server/version/deployment、身份、操作、耗时、结果摘要；敏感参数脱敏 |

建议复用并扩展现有 versions/rollback 路由，新增版本详情、差异比较、验证、激活及操作状态查询。写接口接受精确目标ID、expected_generation、幂等键及原因；权限由服务端决定。异步操作返回 operation_id，不能在后台未完成时报告成功。

## 10. 分阶段实施与优先级

| 优先级 | 工作 | 放行条件 |
|---|---|---|
| P0 | 核查阶段3真实暴露、双端校验与确认闭环 | 真实链路及故障用例通过后再切换 |
| P0 | 实验池调用时权限、审核、TTL | 越权、过期、未批准调用均失败 |
| P0 | 核查现有 rollback 是否真正恢复执行制品 | 不允许仅修改快照或版本标签 |
| P1 | 不可变版本包、依赖复现、兼容差异 | 目标版本可重建且契约一致 |
| P1 | deployment/generation与原子激活 | 并发发布/回退无覆盖；失败保持原版本 |
| P1 | 上下文预算、分页、结果边界 | 扩容不会线性增加固定schema |
| P1 | 运行中调用排空、缓存失效与恢复 | 不混版本，无孤儿进程 |
| P2 | 版本管理页面、成本与效果观测 | 可查看差异、证据、操作进度和审计 |
| P2 | 保留清理、撤销、灾备演练 | 可恢复、可审计，制品引用完整 |

建议顺序：只读调查 → 修复执行权限和固定化 → 建立不可变版本 → 实现部署切换与回退 → 测试环境演练 → 用户验收 → 生产灰度。不得让版本治理重构阻塞已必要的权限修复。

## 11. 验收矩阵

下列数字为建议初始门槛，可按实例容量调整；调整应留记录。

| 项目 | 验收标准 | 证据 |
|---|---|---|
| Flow 扩容 | 2/20/100 Flow 下固定工具名和schema不变 | 实际模型请求和外部 tools/list 快照 |
| 旧工具下线 | 默认发现无 per-flow 与四件套；兼容入口可独立验证 | 双端配置、发现与旧客户端测试 |
| 校验对等 | 6类非法输入覆盖新旧路径及Chat/外部，全部拒绝 | 用例和规范化错误结果 |
| 确认并发 | 20并发同凭证最多创建1任务；重试返回已知任务或明确待对账 | 数据库、队列与确认记录 |
| 故障恢复 | Redis失效、提交后记录失败、SUBMITTING悬挂均有可识别状态 | 故障注入报告 |
| 契约漂移 | 未升YAML版本但修改参数/插件，旧确认仍被拒绝 | 哈希前后与错误码 |
| 权限 | 跨用户 invoke/test/renew/delete/versions/rollback 无成功越权 | 身份矩阵 |
| TTL | 到期立即拒绝新调用；建议5分钟内清理对应空闲子进程 | 时序与进程记录 |
| 版本完整性 | 篡改制品或摘要不匹配不能部署 | 负例报告 |
| 版本复现 | 同manifest重建得到同契约及约定业务结果 | 构建记录、依赖和镜像摘要 |
| 发布并发 | 旧generation操作失败，不覆盖新激活结果 | 并发操作记录 |
| 回退失败 | 目标启动/健康检查失败，active不变 | 指针与运行证据 |
| 回退成功 | 新调用执行目标版本；进行中调用保持原绑定 | 每调用version_id |
| 缓存一致 | 多进程最终看到相同generation，超时进入明确降级/拒绝 | 多进程测试 |
| 输出预算 | 普通llm_payload建议≤8KiB，超限有引用且不失去错误信息 | 响应快照 |
| 副作用边界 | 回退不重复提交、不伪称撤销历史写入 | 业务审计 |

跨Redis/数据库/队列的 exactly-once 未被文档保证，验收不得通过正常路径幂等测试将其升级为全局承诺。

## 12. 管理界面建议
