# CygnusX AI 记忆系统优化实施方案

Oct 20, 2026 · @jian zhang

## 目标、范围与成功标准

本方案分 5 个阶段推进：先在真实环境拿到证据，再修复串项目、遗忘不彻底、检索降级等设计缺陷，最后补齐运维能力并收敛历史包袱，使记忆系统达到可灰度上线的状态。工期为估算值（开发与预发布约 7 周，生产灰度与收敛再约 7 周，合计约 14 周），待阶段 0 的基线数据出来后修订。

**要达成的三个结果**

1. **可证明**：真实 PostgreSQL/pgvector 迁移与回退演练、Worker/Beat/Provider 联调通过；25 案例具备修前基线与修后对比。
2. **不串味、可遗忘**：切换项目不再带出旧焦点；用户归档一条事实后，能知道派生内容（块、摘要）里是否仍有残留，并能清理。
3. **可运维**：关键失败有告警，周度整理可按次回滚，回执类数据表有界增长。

**不在本方案范围内**

- 程序性记忆 / 知识卡片引擎与模型权重层面的“学习”。
- 将 blocks/facts、legacy、Studio 文件三种载体合并为一套。
- Studio 文件记忆的跨会话共享。
- 删除 `mem0_memories` 表与 `MEM0_*` 配置段（须独立导出与人工决策，仅标注废弃）。

**成功标准**（阈值为建议值，阶段 0 基线出来后修订）

| 维度 | 通过标准 | 证据来源 |
| --- | --- | --- |
| 迁移 | 生产快照副本上 upgrade / downgrade 全部成功，行数对账无非预期差异 | 演练报告与对账 SQL 输出 |
| 记忆质量 | 25 案例修后总体不低于修前基线，且“串项目”“复活已遗忘内容”类致命失败为 0 | 验收协议评分表 |
| 隔离 | 跨项目焦点泄露的自动化测试 0 例失败 | CI 测试结果 |
| 稳定性 | settle 失败率、embedding 降级率有告警阈值并在灰度期内未触发 P1 告警 | 监控面板 |
| 可回滚 | 整理回滚演练后，块内容与回滚前快照逐字一致 | 回滚演练记录 |

## 实施原则与总体路线

总体顺序是“证据 → 缺陷修复 → 运维补强 → 灰度 → 收敛”，其中观测告警与整理回滚必须赶在灰度之前完成。开发可以并行，但任何数据迁移在通过真实库演练之前不得合并进发布分支。

**五条实施原则**

1. **默认关闭不变**：`memory_v2_enabled` 保持默认 false；每项新能力使用独立开关，灰度时逐项打开，出问题可单项关闭。
2. **迁移只增不删**：新增 Alembic 迁移仅加列、加表、加索引；降级遇到会丢正文或血缘的数据时拒绝执行，沿用现有纪律。
3. **模型不直接写库**：新增的任何写入路径（含遗忘清理、整理回滚）都走应用服务，保留身份、分区、版本与事务检查。
4. **一项改动 = 测试 + 指标 + 回退开关**：缺任一项不合并。
5. **结论用证据说话**：排序参数、阈值只在有基线数据后调整，不凭感觉改。

**阶段间的硬依赖**

| 前置项 | 阻塞的后续项 | 原因 |
| --- | --- | --- |
| P0 真实库迁移演练通过 | P1 新增迁移的合并、全部灰度 | 新迁移叠加在未验证的迁移链上，风险不可控 |
| P0 25 案例修前基线 | P2 排序/检索改动的效果结论 | 无基线无法证明变好 |
| P0 Worker/Beat/Provider 联调 | 全部灰度 | 锁、预算并发、1024 维校验此前只在 SQLite 或 mock 下验证 |
| P3 观测告警与整理回滚 | 灰度开启（含周度整理） | 灰度期不能盲飞，整理出错须可撤销 |

## 阶段 0：证据基线（约 2 周）

阶段 0 的唯一目的是把“代码已实现”推进到“真实环境已验证”，并留下后续所有优化的对照基线。三条工作流可并行，全部通过才算过门禁。

### 0-A 真实 PostgreSQL 迁移与回退演练

1. **准备环境**：搭建与生产同大版本、已装 pgvector 的 PostgreSQL，导入生产快照。快照含个人记忆，须按记忆数据权限保护，必要时先脱敏。
2. **记录迁移前对账基线**：对 `agent_memories`、`memory_blocks`、`memory_facts` 按 status、scope、agent\_id 是否为空分组计数，并记录共享块数量。
3. **逐节点 upgrade**：按 `m5n6o7p8q9r0` → `n6o7p8q9r0s1` → `memory_project01` → `memory_episode01` → `memory_rank01` → `memory_partition01` → `memory_consolidate01` 顺序执行（中间可能夹有其他领域 revision，以 Alembic 实际拓扑为准）。每个节点后跑对账 SQL，记录耗时与锁等待，重点看 HNSW 索引创建和大表回填。
4. **重点核对 `memory_partition01`**：原 active 个人事实行未丢失；已有 inactive 共享目标未被复活；错分区项目事实被归档而非删除；块血缘（`superseded_by`）链完整，共享块版本高于全部来源版本；已有非空共享块内容未被覆盖。
5. **重点核对 `memory_project01`**：统计因无法确认来源项目而被归档的旧项目/摘要事实数量，人工抽检一批（建议 20 条）确认归档合理。
6. **回退演练**：逐节点 downgrade，确认含长正文、块血缘、整理审计的降级被明确拒绝且数据未损坏；再演练“从快照恢复”这条最终回退路径并记录耗时。
7. **幂等验证**：在迁移后的库上小批量运行 `migrate_legacy_memories` 与 `backfill_embeddings`，重复执行结果不变。

产出：演练报告（对账表、各节点耗时、问题清单）与书面回退步骤。门禁：全部节点 upgrade 成功，对账无非预期差异，回退流程演练成功。

### 0-B 25 案例修前基线

1. 对当前代码打 tag 作为“修前”版本，部署到隔离环境，开启 v2，配置真实的 1024 维 embedding 模型与抽取模型。
2. 按验收协议（docs/info/26.10.20/CygnusX记忆质量验收集-2026-10-20.md）逐案例执行，记录输入、实际注入的 `<user_memory>` 全文、模型回复、评分与失败类型。
3. 失败类型建议按后续阶段的修复对象归类：串项目/旧焦点污染、遗忘后仍被提及、检索漏召回、摘要不接续、误写长期记忆。这样修后可以逐类对比。
4. 评分口径固定，建议至少两人独立评分并抽查一致性。

产出：基线评分表与失败类型分布。门禁：25 案例全部实测完成，运行记录可复现。

### 0-C Worker / Beat / Provider 联调

| 检查项 | 做法 | 通过标准 |
| --- | --- | --- |
| 任务路由 | 手动触发 settle、`record_recall_batch`、`consolidate_memory` | 均进入 analysis 队列并被消费 |
| Beat 调度 | 测试环境临时调整触发时间验证一次 | 按北京时间触发，投递到正确队列 |
| advisory lock | 同时启动两个整理任务；强杀持锁 worker | 一个执行一个跳过；连接断开后锁释放 |
| 周预算并发 | 多 worker 同时整理 | 调用总数不超过 `memory_consolidation_max_calls`，失败也计入额度 |
| 1024 维校验 | 用真实 Provider 生成向量 | 维度、非有限数、空返回均正确降级，`memory.embedding_outcomes` 分布可见 |
| 向量回填 | 对一批 active 无向量事实执行 `backfill_embeddings` | 每批不超过 500，失败不标完成，可重复执行 |
| 开关复查 | 整理中途关闭站点开关 | 行为与架构文档所述一致（模型调用后复查） |
| 检索性能 | 对 `memory_facts` 向量查询做 EXPLAIN | 走 HNSW 索引，记录 P95 延迟 |

产出：联调记录与延迟/成本数据。门禁：以上全部通过。

## 阶段 1：体验与隐私缺陷（约 2–3 周）

本阶段修两个用户最容易感知的问题：切换项目仍看到旧焦点，以及归档一条事实后，它在摘要和画像里的复述仍然存在。两项互相独立，可由两人并行。

### 1-A current\_focus 按项目分块

**方案选择**

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A | `memory_blocks` 新增可空 `project_id` 列，调整唯一约束 | 约束由数据库保证，查询语义清晰，与 `memory_facts` 一致 | 需要一次迁移，改动面含 ORM、服务、API | **推荐** |
| B | 把项目编码进 `block_name`（如 `current_focus:<项目ID>`） | 无需改表 | 约束松散，字符串拼接易出错，管理面难以按项目过滤 | 不推荐 |

**迁移（新 revision，命名建议 `memory_focus_project01`）**

1. 新增 `project_id` 列，可空，类型与 `memory_facts.project_id` 保持一致。
2. 删除旧唯一约束 `(user_id, agent_id, block_name)`，改建两个部分唯一索引：`project_id IS NULL` 时按 `(user_id, agent_id, block_name)` 唯一；`project_id IS NOT NULL` 时按 `(user_id, agent_id, block_name, project_id)` 唯一。使用部分索引是为了不依赖 PostgreSQL 15 的 `NULLS NOT DISTINCT`。
3. 存量 `current_focus` 行保持 `project_id = NULL`，语义变为“无项目 / 通用焦点”，**不**凭猜测回填项目。
4. downgrade：存在 `project_id` 非空的块时拒绝降级，不丢内容。

**读写路径**

- **读**：请求带项目时，只读该项目的焦点块，**不回退**到通用焦点（回退正是串味来源）；请求无项目时读 `project_id = NULL` 的焦点块。共享的 profile / preferences 块不受影响。
- **写**：settle 刷新焦点时按会话所属项目写入对应块；会话无项目则写通用块。`cygnusx_update_memory_block` 的项目从受控会话派生，不接受模型传入。
- **懒创建**：项目焦点块在首次写入时创建，`ensure_memory_blocks()` 不为每个项目预建空块。
- 版本 CAS、凭据检查、2000 字符上限、归档血缘全部沿用现有块生命周期。
- **注入**：块标题增加项目标识，便于排查。

**接口与前端**

- `memory-overview` 返回块的 `project_id`；`PATCH /users/me/memory-blocks/{block_name}` 增加可选项目参数。
- `MemoryManagementPanel` 将焦点块按项目分组展示；管理员视图保持只读。

**测试**

- 项目 A 的焦点不会出现在项目 B 的注入里；无项目请求不会读到任何项目焦点。
- 存量 `NULL` 焦点行在无项目请求下行为不变。
- PostgreSQL 上并发创建同一项目焦点只成功一条；CAS 冲突返回业务错误。
- 迁移 upgrade / downgrade（含拒绝降级分支）纳入阶段 0 建立的真实库演练流程。

**开关与回退**：新增 `memory_focus_per_project_enabled`，默认 false。关闭时读写都回到通用焦点块，行为与现状一致；已创建的项目焦点块保留不删。

### 1-B 遗忘残留提示与清理

现状是归档一条事实不会传播到块、摘要和其他事实。完整的语义级遗忘成本很高，本阶段分步做，先让用户**知道**，再让用户**能清**。

**步骤 1：残留扫描与提示**

1. 遗忘/删除成功后，服务层用被归档事实的正文与关键词，在同一用户可见范围内做词面扫描：共享 profile / preferences 块、当前 Agent 的焦点块、其他 active 事实、active episode。
2. 返回 `residual_hints`（命中类型、对象 ID、不超过 60 字符的上下文摘录）。摘录只回给该用户本人，日志中不记录正文。
3. `cygnusx_forget_memory` 将提示一并返回给 Agent，Chat 纪律要求向用户如实说明“已归档该条，但摘要/画像中可能仍有相关表述”；管理面板在删除结果中展示同样的提示。
4. 提示文案使用“可能”：词面匹配找不到语义复述，不能承诺“已全部清除”。

**步骤 2：用户确认后的清理入口**

- 命中块：直接跳转到块编辑（已有 CAS 编辑能力）。
- 命中 episode / 其他事实：提供“一并归档”按钮，复用现有归档接口。
- 不由程序或模型自动改写块内容，避免误伤人工策展内容。

**步骤 3（可选，视步骤 1–2 的使用反馈再定）：防止同义重写**

settle 只能拦住“同文复活”，用户遗忘的事实被换种说法后仍可能被重新抽取。可新增 `archived_reason`（用户遗忘 / 被替代 / 冷归档 / 迁移归档），并在 settle 抽取输入中附带近期“用户遗忘”事实作为排除项。这一步需要新增列与迁移，范围较大，所以放在可选。

**测试与指标**

- 单测：词面扫描只在当前 user 范围内进行；日志与异常不含正文；归档后再次扫描不重复命中已归档行。
- 指标：`memory.forget_residual_hits`（带命中类型）、残留提示后的清理点击率。

**开关**：新增 `memory_forget_residual_scan_enabled`，灰度前默认 false。

## 阶段 2：检索质量（约 2 周）

本阶段先修正确性（向量只在同一模型内比较），再提升召回（向量与关键词合并重排）。顺序不能反：混合检索会放大“新旧向量混排”的影响。

### 2-A embedding 模型版本过滤与回填

现状是 `embedding_model` 已记录，但向量查询不按它过滤。即使新旧模型维度相同，语义空间也未必兼容，混排会无声地降低召回质量。

1. **查询过滤**：向量检索增加条件 `embedding IS NOT NULL AND embedding_model = <当前配置模型>`。不匹配的行不参与向量召回，但仍可被关键词召回，因此换模型不会让事实“消失”。
2. **写入保持成对**：向量与 `embedding_model` 必须同时写入或同时为 NULL，补一条单测固化该约束。
3. **回填任务扩展**：`backfill_embeddings` 目前只处理“active 且无向量”的条目。新增模式，处理“模型标识与当前配置不一致”的条目并重新生成向量；每批不超过 500，幂等，失败不标完成。先提供 dry-run，只报告待回填数量，再按预算分批执行。
4. **换模型操作手册**：先配置新模型并启动回填，回填期间旧向量因过滤不参与向量召回，由关键词补位；覆盖率达到预设阈值（建议 95%，可调整）后再认为切换完成。
5. **索引风险**：带过滤条件的 HNSW 查询可能返回条数少于 LIMIT。阶段 0 的 EXPLAIN 与延迟测试要覆盖该场景；缓解办法是放大候选数后再过滤，或使用 pgvector 的迭代扫描能力（需按生产版本确认是否可用）。
6. **观测**：新增 `memory.embedding_model_mismatch_rows`，统计 active 行中与当前模型不一致的数量。

**测试**：混合模型数据下向量召回只返回当前模型的行；旧模型行仍可被关键词命中；回填后覆盖率上升且重复执行结果不变。

**开关**：`memory_embedding_model_filter_enabled`，灰度期默认 false，验证通过后改为 true。

### 2-B 向量 + 关键词混合检索

现状是某分区没有向量结果才降级到关键词。当向量有结果但漏掉含关键实体（项目代号、编号、专有名词）的事实时，关键词没有机会补位。

1. **同时取两路候选**：每个分区（共享、当前 Agent）并行取向量 top Kv 与关键词 top Kk（建议各 20，可调）。关键词沿用现有的转义匹配与最多 8 个词项。
2. **RRF 合并**：按排名而非分数合并，避免两路分值不可比。

```latex
\mathrm{RRF}(d)=\sum_{i\in\{\mathrm{vec},\,\mathrm{kw}\}}\frac{1}{k+\mathrm{rank}_i(d)},\qquad k=60
```

3. **保留相似度下限**：RRF 只看排名，会让低相似度的向量命中也得分。向量侧设相似度下限，低于下限不进入候选；阈值依据阶段 0 基线数据确定，不预先拍定。
4. **与现有复合打分衔接**：将 RRF 分归一化到 \[0,1\] 后作为 `relevance`，其余因子（时间衰减、importance、recall）公式不变。同分仍保持共享优先。
5. **有界性不变**：工具搜索返回上限 10（默认 5），提示词最多选 5 条普通事实；每分区候选上限为 Kv + Kk。
6. **降级**：未配置 embedding 模型时只走关键词，行为与现状一致。
7. **参数调整纪律**：时间衰减 lambda 与各权重在混合检索稳定之后再做小范围对比，不与本项同批改动，否则无法归因。

**测试**：向量命中但漏关键实体时关键词补位；两路命中同一 ID 只出现一次；空向量与单路为空的边界；分区同分共享优先。

**评测**：在 25 案例之外补充 5–10 个“关键实体召回”专项案例（建议），修前修后分别运行并记录漏召回数。

**开关**：`memory_hybrid_retrieval_enabled`，默认 false；灰度期对同一批案例做修前修后对比。

## 阶段 3：可运维性（约 2–3 周，可与阶段 1、2 并行）

本阶段让系统在灰度时“看得见、撤得回、不无限增长”。其中 3-B 整理回滚与 3-D 观测告警是灰度的硬前置，其余可顺延。

### 3-A settle 游标 SQL 化与尾批强制结算

现状有两个问题：任务把整个会话加载进内存再定位游标，长会话成为热点；游标后不足 4 条的尾批永远不结算，会话结束时最后一段进展可能丢失。

1. **游标 SQL 化**：先单独查游标消息（保留 `cursor_missing` 判定），再用 `(created_at, id)` 的复合条件查询游标之后的消息，按同一顺序排序，`LIMIT` 取 `memory_settle_max_messages + 1` 条以判断是否还有后续。消息表上需有 `(session_id, created_at, id)` 的覆盖索引，没有则通过迁移补上（表名与现有索引以代码为准）。
2. **预算裁剪保持不变**：取回后仍按完整消息裁剪到 8000 字符。首条消息本身超预算（`input_budget`）仍然卡住游标，本方案不做消息分片，只保证它进入告警（见 3-D）。
3. **尾批强制结算**：新增 Beat 任务 `settle_idle_sessions`，定期扫描“空闲超过 T（建议 30 分钟，可配置）且游标后有未结算消息”的会话，投递带 `force_tail` 标记的 settle。尾批最小消息数放宽为可配置项（建议默认 2）。
4. **扫描有界**：每次扫描最多投递固定数量的会话（建议 200），排除 AgentTeams 合成会话，任务内再次检查运行开关；重复扫描依靠 `range_key` 唯一性保持幂等。
5. **成本观测**：新增 `memory.settle_tail_enqueued`，并在灰度期单独统计尾批带来的模型调用量。

**测试**：游标后读取只含新消息且 `created_at` 相同按 id 稳定排序；`cursor_missing` 保留；尾批结算推进游标；同一空闲会话重复扫描不重复结算；AgentTeams 会话被排除。

**开关**：`memory_settle_tail_enabled`，默认 false。

### 3-B 周度整理按 run 回滚（灰度前必须完成）

整理审计已保存计划、块更新前快照与来源 ID，缺的是“把它用起来”的回滚入口。

1. **入口**：应用服务方法 `rollback_consolidation_run(run_key, actor)`，提供管理员 API 与运维 CLI 两种调用方式，仅管理员可用，记录操作者。
2. **以 run 为单位、全有或全无**：事务内对每一项做条件更新，任一项冲突则整次回滚中止并返回冲突清单。先提供 dry-run，列出将恢复的项与已冲突的项，由管理员决定是否人工处理。
3. **事实替代的恢复**：仅当旧事实当前仍处于“被本次 run 替代”的状态时才恢复为 active 并清除指向；之后被用户改动过的不动。
4. **块内容的恢复**：仅当块当前版本等于本次整理写入后的版本（即之后无人改动）时，才把快照内容写回，**写成新版本（version + 1）**，版本号保持单调；块已被改动则不覆盖，列入冲突清单。
5. **冷归档的恢复**：需要区分“冷归档”与“用户后来手动归档”。这依赖 1-B 步骤 3 的 `archived_reason`；若该步骤未实施，本期回滚只覆盖整理（事实替代与块），不覆盖冷归档，冷归档保留正文，可人工恢复。
6. **防重复与审计**：`memory_consolidation_runs` 新增可空 `rolled_back_at`，并写一条回滚审计记录关联原 `run_key`；已回滚的 run 拒绝再次回滚。需要一个新迁移（建议命名 `memory_consolidate_rollback01`），降级时若存在回滚记录则拒绝。
7. **安全**：审计与快照含个人内容，权限与记忆数据一致，日志不记录正文。

**测试**：回滚后事实状态与块内容和快照逐字一致；块被后续修改时中止；重复回滚被拒；非管理员被拒；dry-run 无副作用。该回滚流程纳入阶段 0 的演练范围。

### 3-C 回执与审计表的增长治理

| 表 | 增长方式 | 策略 |
| --- | --- | --- |
| `memory_recall_batches` | 每次召回批次一行，仅用于幂等 | 新增每日清理任务，按 TTL（建议 14 天）分批删除，每批约 5000 行；TTL 必须明显大于任务重试与重投窗口，上线前核对 |
| `memory_settlements` | 每个成功区间一行，承担区间幂等 | 暂不清理，纳入表大小观测 |
| `memory_consolidation_runs` | 每次整理一行，含块快照，回滚依赖它 | 保留；超过回滚窗口后是否把快照置空只留元数据，列入待决策 |
| `memory_consolidation_budgets` | 每周一行 | 无需处理 |

清理任务同样受运行开关约束，并输出 `memory.recall_batches_purged`。清理依赖时间列上的索引，没有则随迁移补上。

### 3-D 观测与告警（灰度前必须完成）

现状只有埋点，没有面板与告警。先建一个记忆看板，再配下列告警。数值均为建议初值，灰度前两周按真实数据校准。

| --- | --- | --- | --- |

## 阶段 4：收敛（灰度稳定后，约 1–2 周）

本阶段清理历史包袱，降低认知与运维成本。所有项都不应在灰度稳定之前开始，避免在不稳定基础上同时动旧路径。

### 4-A legacy 分支退役

现状是 `agent_memories` 与服务层 legacy 读写分支仍保留，v2 不向旧表双写。退役分四步：

1. **盘点调用方**：列出仍走 legacy 分支的入口，包括使用旧 3200 字节逻辑的直接上下文调用、`GET /users/me/memories`、`GET /admin/users/{user_id}/memories`。
2. **打点**：新增 `memory.legacy_path_used`（带入口标签），灰度期观察实际调用量。
3. **标注废弃**：前端与管理员视图全部切到 `memory-overview` 投影后，旧列表接口保留一个发布周期并标注废弃。
4. **移除分支**：旧接口调用量降为 0 且旧数据迁移对账完成后，移除服务层 legacy 读写分支。`agent_memories` 表本身**保留只读**，与 `mem0_memories` 一样，删除须独立导出与人工决策。

前置条件：灰度稳定运行（建议至少 4 周）、`migrate_legacy_memories` 对账通过。具体日期见待决策事项。

### 4-B 统一 v2 关闭的语义

现状：`memory_v2_enabled=false` 时，Chat 与 Agent 的自动记忆链路关闭，但管理与服务层却切换到 legacy 投影。运维看到的数据和用户实际被注入的数据不是同一份，容易误判。

1. **拆清两个概念**：`memory_v2_enabled` 只表示“记忆自动化是否运行”（Chat、L4、工具、settle、整理）；管理面的数据投影固定为 v2，并以只读方式合并展示 legacy 数据，不再随开关切换。
2. **文案**：管理页在开关关闭时提示“记忆自动化已关闭，数据保留”。
3. **回退语义不变**：v2 新增内容仍不双写回旧表，关闭 v2 不是无损数据回退。该点在架构文档 §9.3 保持并写得更醒目。
4. **影响面**：管理 API 的 DTO 与 `MemoryManagementPanel`、`AdminMemoryView`。

**测试**：v2=false 时 overview 仍返回 v2 数据；同时 Chat、工具、settle、整理仍被运行闸门挡住。

### 4-C 冷归档的误归档防护

冷归档条件是 `recall_count=0`、`last_recalled_at` 为空、`importance≤3` 且超过 90 天。风险在于召回计数是异步的：召回批次尚未落库时，归档任务看不到它。

需要说明一点：`memory_recall_batches` 只存 batch\_id、用户和时间，不含事实 ID，因此**不能**用它逐条确认某个事实最近是否被召回。可行的防护是下面两项。

1. **队列积压保护（建议先做）**：冷归档开始前检查 analysis 队列，若召回批次任务有积压（最老任务等待超过阈值，建议 10 分钟），跳过本周冷归档，下周再执行，并记录 `memory.cold_archive_skipped_backlog`。
2. **两阶段归档（可选）**：新增可空 `cold_candidate_at`，首次命中只标记，间隔至少 7 天后仍满足条件才归档。优点是给异步统计留足缓冲，缺点是要加列与迁移、归档周期变长。是否实施，视灰度期观察到的“归档后又被用户恢复或再次提及”的次数决定。

### 4-D 文档与运行手册

1. 同步更新架构文档的 §1、§5、§6、§9、§11 与存储 ADR（docs/adr/0001-memory-storage.md），把本方案落地后的行为写成 as-built。
2. 新增三份运行手册：迁移与回退演练、整理回滚、更换 embedding 模型。
3. 在架构文档 §1 增加“内容该放哪个载体”的选择表（个人块 / 项目事实 / 情节 / Agent 焦点 / Studio 文件），降低三种载体并存的认知成本。

## 灰度发布与回退方案

灰度的原则是一次只打开一项能力，每一步都有观察期、进入下一步的条件和明确的回退动作。一个现实约束要先说清：当前运行闸门是**站点级**（`memory_v2_enabled` + 站点管理开关），没有按用户灰度的机制。因此生产首次开启会影响全站，是否增加用户级白名单见待决策事项。

**开关清单**

| 开关 | 状态 | 控制范围 | 默认 |
| --- | --- | --- | --- |
| `memory_v2_enabled` + 站点管理开关 | 已有 | Chat、L4、工具、settle、召回统计 | false |
| `memory_consolidation_enabled` | 已有 | 周度整理与冷归档 | true（但受 v2 闸门约束） |
| `memory_focus_per_project_enabled` | 本方案新增 | 焦点块按项目读写 | false |
| `memory_forget_residual_scan_enabled` | 本方案新增 | 遗忘后的残留扫描与提示 | false |
| `memory_embedding_model_filter_enabled` | 本方案新增 | 向量召回按模型过滤 | false |
| `memory_hybrid_retrieval_enabled` | 本方案新增 | 向量 + 关键词混合检索 | false |
| `memory_settle_tail_enabled` | 本方案新增 | 空闲会话尾批结算 | false |

**灰度步骤**（观察期为建议值；整理相关步骤须覆盖至少一次周日运行）

| 步骤 | 环境 | 打开的内容 | 进入下一步的条件 | 回退动作 |
| --- | --- | --- | --- | --- |
| G1 | 预发布（生产快照副本） | 全部迁移 + v2 开启，整理与新开关均关闭 | 阶段 0 全部通过；25 案例修后评分不低于基线 | 重建环境，无生产影响 |
| G2 | 预发布 | 逐项打开新开关，最后打开整理并演练回滚 | 每项观察 3–7 天无 P1/P2 告警；回滚演练成功 | 关闭对应开关 |
| G3 | 生产，低峰期，有值班 | v2 开启（含注入、工具、settle、召回统计），整理与新开关仍关闭 | 观察 7 天；settle 失败率、embedding 降级率在阈值内 | 关闭站点开关，数据保留 |
| G4 | 生产 | 依次打开 embedding 过滤 → 混合检索 → 焦点分项目 → 遗忘残留扫描 → 尾批结算 | 每项观察至少 3 天；案例抽测不低于基线 | 关闭对应单项开关 |
| G5 | 生产 | 打开整理；首周将 `memory_consolidation_max_calls` 调低（建议 5） | 首次周日运行后核对整理审计，抽查块与事实变化，无异常再恢复默认预算 | 关闭整理开关，并对异常 run 执行回滚 |

**回退触发条件**

| 触发条件 | 动作 | 说明 |
| --- | --- | --- |
| 出现跨用户记忆泄露的迹象 | 立即关闭站点开关，按安全事件处理 | 最高优先级，先止血再分析 |
| settle 失败率或 embedding 降级率持续超阈值 | 先排查；无法在约定时间内恢复则关闭站点开关 | 关闭只停止自动化，不删除数据 |
| 整理产出异常（块被改坏、事实被误替代） | 关闭整理开关，对相关 run 执行回滚 | 依赖 3-B |
| 检索质量下降（案例评分下降、漏召回增多） | 关闭混合检索或模型过滤开关 | 回到旧检索路径 |
| 用户反馈串项目 | 核对是否启用了焦点分项目；关闭 `memory_focus_per_project_enabled` 回到通用焦点 | 已创建的项目焦点块保留 |
| 迁移后发现数据问题 | 关闭站点开关；不直接执行 schema downgrade | 以演练过的方案处理，最终手段是从快照恢复 |

**回退的边界**（沿用架构文档的结论）：关闭开关只停止新的自动化，不撤销已经在途的写入，也不会把 v2 新增内容写回旧表。所以回退流程是“先关开关保住数据，再评估恢复”，不能把 schema downgrade 当作一键撤销。

**待决策事项**

1. **生产是否增加用户级灰度白名单？** 当前只有站点级闸门。建议增加，否则 G3 就是全站开启。
2. **项目被删除或归档时，对应的项目焦点块怎么处理？** 建议随项目归档（保留正文，状态置为 archived）。
3. **请求带项目但该项目没有焦点时，是否回退到通用焦点？** 本方案按“不回退”设计（见 1-A），因为回退正是串味来源；如要改，需同时说明可接受的串味风险。
4. **是否实施 1-B 步骤 3 的 `archived_reason`？** 它决定冷归档能否被回滚、能否防止同义重写。若要让 3-B 覆盖冷归档，需要提前到阶段 1 做。
5. **`memory_consolidation_runs` 中块快照的保留期？** 建议值 90 天，之后快照置空、只留元数据；需要与合规要求对齐。
6. **legacy 分支的退役日期？** 方案给出的是条件（灰度稳定至少 4 周加一个发布周期的废弃期），具体日期需要产品与发布节奏确认。
7. **空闲阈值 30 分钟与尾批最小消息数 2 是否接受？** 阈值越低，进展越完整，但模型调用成本越高。
8. **告警接收渠道与值班安排？** 3-D 的 P1/P2 告警需要明确的接收人和响应时限。
