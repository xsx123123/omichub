## 0. 一页结论

1. **你的审计文档质量是高的，结论我全部采信**，没有推翻项。它把「为什么现在没有记忆感」的运行层根因找全了：召回恒空（embedding 未配置且静默失败）、`memory_blocks=0`（无创建路径）、settle 近一个月零产出、`forget` 工具在 v2 必败。这四个不修，谈任何高级设计都是空中楼阁。
2. **但审计覆盖的是「正确性与运维」维度，没有覆盖你的真实目标维度**。你要的是「学习与知识积累的稳健记忆机」——这在主流设计里对应**情节记忆（episodic）、反思巩固（reflection/consolidation）、程序性记忆（procedural）**三块能力，而当前架构只有「语义事实（semantic facts）」一层，且检索打分只有 `similarity × 时间衰减` 一个信号。**即使把审计的 P0 全部修完，你得到的也只是一个「能记住事实的系统」，而不是「有学习感的记忆机」。**
3. 「没有记忆的感觉」是三层原因叠加：运行层（注入恒空，占主因）→ 设计层（只有事实、没有情节与巩固，记忆会堆积不会生长）→ 体验层（记忆不可见、Agent 不主动引用、写入无确认回路）。三层各给了药方，见 §3 与 §5。
4. 2026 年主流设计有六条可迁移原则（§2.4），其中两条直接印证你审计里的判断：**混合检索兜底**（Zep 向量+BM25+图遍历三路，你是纯向量单路，挂了就是零）和**写入路径质量控制优先于存储结构**（这是今年研究界的共识焦点，你的 settle 失败静默吞错正是反例）。
5. 优化路线建议在审计 Phase 0–4 的基础上插入两个新阶段：**Phase 2.5 情节记忆与 current_focus 激活**（「记忆感」性价比最高的一击）和 **Phase 5 巩固作业与强化学习式检索**（让记忆会生长）。另附一个 20~30 题的个人记忆评测集方案（§6.3）——2026 年的教训是厂商基准数字互相打架、不可尽信，自己的平台自己测。

**审计未覆盖的三个盲区（设计/产品维度，本文 §3、§5 展开）：**

1. **没有情节记忆层**：settle 只抽「持久事实」，不产出「这次会话做了什么、结论是什么、遗留什么」的会话摘要。而「记忆感」的主要来源恰恰是情节——「你上次做到哪了」。
2. **记忆不生长**：没有反思/巩固机制，事实只会堆积，不会被合成成更高层的认识（Generative Agents 的 reflection、A-MEM 的记忆演化、ReasoningBank 的策略蒸馏都是解决这个）。
3. **记忆不可见**：前端面板恒空、Agent 回复里从不主动引用记忆、用户说「记住这个」后没有任何确认回路。主观「记忆感」= 客观召回质量 × 可见性，后者当前为零。

## 2. 2026 年主流 Agent 记忆设计调研

### 2.1 分类法：四种内容类型 + 一种组织方式

2026 年业界基本收敛到 LangMem 提出、mem0 等行业报告沿用的分类：

| 类型 | 存什么 | 例子 | 成熟度 |
|---|---|---|---|
| **语义记忆 Semantic** | 事实、偏好、实体属性 | 「用户常用 GRCh38」「输出要 Markdown」 | 最成熟，所有系统都有 |
| **情节记忆 Episodic** | 过去交互的事件与经过 | 「上周三会话排查了批次效应，结论是换 ComBat」 | 中等，多数系统只有雏形 |
| **程序性记忆 Procedural** | 怎么做事：工作流、工具使用习惯、从成败里蒸馏的策略 | 「这个平台跑质控先看 fastqc 再看比对率」 | **最不成熟**，2026 年最前沿方向 |
| **工作记忆 Working** | 当前会话上下文 | 当前对话窗口 | 成熟 |
| **分层组织 Hierarchical** | 不是第五种内容，而是组织上面四种的方式：核心层常驻上下文、召回层可搜索、归档层冷存 | MemGPT 的 core/recall/archival 三级 | 主流组织方式 |

CygnusX 现状对位：工作记忆 ✅（会话上下文）；语义记忆 ⚠️（有架子但部署半失效）；核心层 ⚠️（blocks 表存在但恒为 0）；情节记忆 ❌；程序性记忆 ❌；巩固机制 ❌。

| 系统 | 记忆抽象 | 谁来管记忆 | 时间语义 | 存储 | 对 CygnusX 的启示 |
|---|---|---|---|---|---|

### 2.3 2026 年两个新动向与一个警示

**新动向：**

- **模型厂商把记忆做成一等公民**：Anthropic 2026 年 2 月预览、6 月正式发布 Memory Tool（`/memories` 文件目录交给 Client 管理，并支持从 ChatGPT/Gemini 导入）；OpenAI Responses API 则明确「不接管状态管理，长期记忆开发者自建」。含义：**记忆层责任在平台侧**，你做记忆系统这个决策本身是对的；同时「文件正统」回潮，你 Studio 的文件记忆路线不孤单。
- **写入路径质量控制成为研究焦点**：2026 年的评测综述明确指出，写入路径成本可占 agent 总执行时间的 80% 以上，但多数系统不披露。含义：你的「增量 settle + 幂等游标」方向是对的（控制写入成本），要修的是失败静默；不要盲目上「每轮都重写记忆」的重写入方案。

**警示——基准罗生门**：LoCoMo 基准正被多方质疑。Zep 发文称按正确实现重测，自家 75.14% 高于 mem0 最佳配置约 10%，而 mem0 论文只给 Zep 记 65.99%；更尴尬的是 **mem0 自己公布的结果里，full-context 基线（约 73%）打赢了自家最佳配置（约 68%）**——记忆层跑输了把全部对话直接塞进上下文。含义：①厂商基准数字不可尽信，任何「要不要引入 XX 记忆框架」的决策都不能只看排行榜；②你的平台应该建自己的小型评测集（§6.3），修前修后各跑一次，这是唯一可信的度量。

### 2.4 可迁移到 CygnusX 的六条设计原则

1. **机制跑通优先于存储高级**（Letta 文件方案教训）：先把现有 pgvector 薄层修到「写进、召回、可见」，再考虑图谱等高级结构。
2. **混合检索兜底**（Zep）：向量 + 关键词双路，任何单路失效都不至于归零。
3. **复合检索信号**（Generative Agents）：`相关性 × 新近度 × 重要性`，外加访问强化（被召回越多的记忆越不该被埋掉）。
4. **失效而非删除**（Zep）：矛盾与过时走 supersede/invalidated，保留审计链——你已符合，保持。
5. **写入路径质量控制优先**（2026 研究共识）：失败必须可见、可重试；抽取质量比抽取频率重要。
6. **记忆从堆积到生长靠巩固**（Generative Agents reflection / A-MEM 演化 / ReasoningBank 蒸馏）：定期的「整理作业」把情节蒸馏成画像、把重复模式蒸馏成策略——这是「学习与知识积累」的发动机。

## 3. 为什么「和 Agent 沟通没有记忆的感觉」——根因分层

| 层 | 根因 | 证据 | 权重 |
|---|---|---|---|
| **L0 运行层** | 记忆注入永远是空串：embedding 未配置且静默失败、blocks 恒为 0、settle 近一个月零产出 | 审计 §5 运行数据（10 条事实全无向量、2026-10 六次 settlement 零产出） | **主因**。模型手里根本没有记忆可用，自然表现得像没有记忆 |
| **L1 设计层** | 只有语义事实一层：没有情节记忆（上次做了什么）、`current_focus` 是死配置、检索只有相似度×时间衰减单信号、无反思巩固 | 架构文档 §4/§5；审计 §4.3 | 修完 L0 后立刻显现：系统能「想起事实」但不会「记得经历」，记忆感仍然单薄 |
| **L2 体验层** | 记忆不可见：前端面板恒空、文案与实现不符；Agent 回复从不主动引用记忆；用户说「记住 X」后无确认 | 审计 §3.5 | 主观感受的直接来源：即使 L0/L1 修好，不可见 = 不存在 |

**一句话：先修 L0 让记忆存在，再补 L1 让记忆完整，最后做 L2 让记忆被感知。** 三层都要做，但顺序不能乱。

## 4. 目标架构：面向学习与知识积累的稳健记忆机

### 4.1 分层模型（建议稿）

```text
│ L2 情节记忆（新增，scope=episode）                          │
│    每次 settle 额外产出一条会话级摘要：                       │
│    做了什么 / 关键结论 / 遗留问题                            │

│      （A-MEM-lite，先不做 LLM 自动重写链接）                 │

│    · settle（现有修复）：事实 + 情节摘要 + focus 刷新          │
│    · 巩固作业（新增，周期任务）：合并近似重复、冲突 supersede、 │
│      情节→画像蒸馏、冷热迁移（active→archived）              │
└─────────────────────────────────────────────────────────┘
```

设计取舍说明：

- **不上知识图谱**（Zep 式）：你的数据量级（当前 10 条事实，量级预期百到千）用不上图遍历，pgvector + 关键词双路足够；图谱是 Phase 6 以后的选项，且到那时 Graphiti 这类开源引擎可以直接接。先跑通机制。
- **情节记忆落在现有 facts 表**（`scope=episode` + 更长 `content` 上限），不新建表——少一次迁移，检索复用；只有确认体量/查询模式不合适时再拆表。
- **重要性打分复用 settle 的 LLM 调用**：抽取事实时顺手输出 importance（1-10），边际成本约等于零，避免 Generative Agents 式每条记忆单独调一次模型的开销。

### 4.2 写入管线（三条，各自独立可回滚）

1. **即时显式写入**（现有工具链修复）：用户说「记住 X」→ 工具写入 → **必须返回确认文本让模型复述**（「已记住：……」），闭环 L2 体验层。
2. **settle 增量沉淀**（修复 + 扩展）：现有「抽事实」之外，加两个产出物：会话情节摘要（写 L2）、current_focus 刷新（写 L1）。失败处理按审计 P0-4：失败不推进游标、可重放。
3. **周期巩固作业**（新增）：每周一次，做四件事——合并近似重复事实、LLM 仲裁冲突 supersede、把近期情节蒸馏进 profile/preferences、按访问频次做冷热迁移。这是「记忆会生长」的发动机，也是长期保持记忆库健康的清道夫。

### 4.3 检索与注入（建议打分公式）

```
score = relevance × recency × (1 + α·importance) × (1 + β·recall_boost)

relevance    = 向量余弦相似度（向量缺失时回退关键词匹配得分）
recency      = exp(-λ × age_days)，λ 维持 0.02
importance   = importance/10 归一（新字段，默认 0.5）
recall_boost = log(1 + recall_count) 归一，recall_count 由 touch_recalled 接线后累计
```

- `touch_recalled` 接线（审计 P2-3）不只是观测需要——**被反复召回的记忆衰减更慢**，这是间隔重复式的强化，恰好契合你「学习与知识积累」的场景：常用的知识越用越牢，不常用的自然沉底。
- 注入预算：当前 3200 字节对「blocks + top-5 事实」够用；加了情节层后建议提到 4–6 KB 并做分项配额（blocks 全量 > 最近 1 条情节 > top-N 事实），超预算时按优先级砍，不是简单截断。

### 4.4 体验层（L2）三件事

1. **开场连续性**：新会话首轮自动注入 `current_focus` + 最近一条情节摘要，并在提示词纪律里要求模型「若存在上次进展，自然地接续一句」（不是背课文，一句即可）。
2. **引用可见**：提示词纪律加一条「使用了记忆内容时，用『根据你之前……』这类措辞显式归因」。记忆被说出来，用户才感知到记忆存在。
3. **写入确认**：`save_memory` 返回结构化确认，模型必须复述一遍记了什么；前端记忆面板修好后（审计 Phase 3），用户可随时翻看和纠正——看见 + 可纠正 = 信任。

## 7. 风险与提醒

1. **不要在 Phase 0 之前加任何新功能**：当前部署是「半失效」状态，在失效链路上叠加情节记忆只会多一个失效点。
2. **警惕写入成本膨胀**：2026 年的数据是写入路径可占 agent 执行时间 80%+。settle 加情节摘要和 focus 刷新后，单次 settle 的 LLM 调用从 1 次变 1 次（合并提示词）或 2 次——必须合并成一次调用内多产出，不要拆成串行多调用。
3. **记忆越多，召回越挑**：评测协议研究表明，无关会话累积到一定规模，召回可靠性会先垮掉，远在撞到存储容量上限之前。所以巩固作业（去重、归档、冷热迁移）不是可选项，是长期可靠性的前提。
4. **不要引入现成框架替换自研层**（mem0 等）：①你已经从 mem0 迁出来过一次，残留还没清完；②你的分区语义（共享/Agent/项目三维）比现成框架的两维模型更贴合你的产品；③基准罗生门说明换框架换不来确定收益。把主流设计当「设计素材库」抄机制，不当「依赖」装。

## Part 9（2026-10-21 第九轮）：SiliconFlow Embedding 接入实施报告核对结论

> 核对对象：《CygnusX-SiliconFlow-Embedding接入实施报告》（2026-10-21，Codex 施工）。

4. **启用说明完整**：三行 .env + 密钥注入 + UUID 获取路径 + 「先探测、再隔离验证、后回填」的克制顺序。并修正了我的表述：Provider 密钥实际会被仓库层**加密存 DB**，不能宣称「密钥不落库」——接受该修正。
