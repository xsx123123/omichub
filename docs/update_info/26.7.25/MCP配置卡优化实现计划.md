# MCP 配置卡内容补全 · 详细实现计划

> 适用对象：编码 Agent（kimi code / Claude Code / CODEX 等）
> 项目：OmicHub 平台前端 ·「AI 资源中心 → MCP 服务」模块
> 任务性质：**在现有页面基础上修复数据回填与字段缺失问题**，不是重新设计，禁止推倒重写。

---

## 一、背景与目标

### 1.1 现状

「AI 资源中心 → MCP 服务」列表页工作正常：

| 服务 | 传输 | 状态 | 工具数 | 预设 |
|---|---|---|---|---|
| omichub-pipelines | builtin | Online | 10 | 是 |
| omichub-platform | builtin | Online | 5 | 是 |
| omichub-tools | builtin | Online | 8 | 是 |

但点开任一服务的配置详情卡（四个 Tab：通用 / 工具 / 提示 / 资源），内容大面积缺失，详情卡与列表页数据严重不一致。

### 1.2 目标

让配置详情卡**完整、真实地反映 MCP 服务的运行配置与能力清单**：

1. 「通用」Tab 按传输类型展示完整配置项（builtin 展示 command / args / env 等）；
2. 「工具」Tab 回填已发现的工具列表，与列表页工具数一致；
3. 「提示」「资源」Tab 接入 prompts/list、resources/list，或统一占位样式；
4. 空态文案与实际按钮一致，消灭"文案引用了不存在的按钮"这类问题。

### 1.3 约束

- 不改路由、不改列表页现有逻辑与展示；
- 弹窗风格、表单控件样式与平台其他弹窗保持一致；
- 先读现有代码（MCP 服务管理相关组件、接口层、后端配置 schema）再动手；
- 每个阶段独立可验收，改完一个阶段验证一个阶段。

## 二、问题清单（截图实测）

### P1「通用」Tab：builtin 类型关键配置字段整体缺失

- **现状**：传输方式为 `builtin`，但表单只有：服务名称（灰色，疑似不可编辑）、传输方式、SSE 端点 URL（空 placeholder `https://your-mcp-server.com/sse`）、服务描述、工作目录（空 placeholder）、超时（30 秒）。**没有启动命令（command）、启动参数（args）、环境变量（env）**——builtin 本地进程类型最核心的三个字段。
- **问题本质**：字段未按传输方式做显隐联动。builtin 不该出现 SSE 端点 URL；SSE 类型才需要它。
- **预期**：
  - `builtin` / `stdio` 类型展示：启动命令、启动参数、环境变量（键值对列表，可增删）、工作目录、超时；
  - `sse` / `streamable-http` 类型展示：端点 URL、请求头 / 鉴权字段（如后端支持）、超时；
  - 服务名称若是主键不可编辑，使用 `disabled` 样式并加 tooltip 说明，不要用疑似 placeholder 的浅灰样式。

### P2「工具」Tab：已发现工具未回填

- **现状**：列表页显示 omichub-pipelines 有 **10 个工具**，详情卡「工具」Tab 却是空态：「暂无工具，点击"测试"可重新发现。」
- **伴生问题**：空态文案提到的「测试」按钮在弹窗中**不存在**（底部只有「取消 / 保存」）。
- **问题本质（疑似）**：工具发现（tools/list）的结果只存在列表接口或内存缓存中，未持久化到服务配置，详情接口不返回 tools 数据；或详情弹窗漏渲染。
- **预期**：
  - 工具列表回填：工具名 + 描述（可有参数 schema 折叠展开），数量与列表页一致；
  - 提供「重新发现」按钮，实际调用 tools/list 刷新；
  - 若按钮本期不做，则修正空态文案，不得引用不存在的按钮。

### P3「提示」Tab：未实现

- **现状**：仅有占位文案「提示词资源将在后续版本支持。」
- **预期**：服务端若已支持 prompts/list 则接入展示（提示词名 + 描述 + 参数说明）；若本期不实现，占位文案保留但样式与「资源」Tab 统一。

### P4「资源」Tab：疑似同样未实现

- **现状**：截图未覆盖，需自查。大概率与「提示」Tab 相同。
- **预期**：同 P3 策略，接入 resources/list 或统一占位样式。

### P5 数据一致性：详情卡与列表页数据源割裂

- **现状**：列表页有工具数（10/5/8），详情卡无工具数据——两个视图的数据显然不是同一份。
- **预期**：明确数据流——详情接口返回完整服务配置（含 tools/prompts/resources 或至少 tools），或详情弹窗打开时并行调用能力发现接口；并在文档中说明数据流向，防止后续再割裂。

## 三、根因排查链路（先定位，再动手）

按以下顺序逐层验证，每层确认排除后再进入下一层：

1. **接口层**：打开详情弹窗时调用了哪个接口？在 Network 面板对比列表接口与详情接口的返回 JSON，确认详情接口是否包含 `tools` 数组、`command` / `args` / `env` 字段。
2. **后端 schema 层**：若接口未返回——检查 MCP 服务的配置 schema 定义，builtin 类型是否缺少 command/args/env 的字段描述；tools/list 的发现结果是否只存内存/缓存而未持久化到服务配置记录。
3. **前端渲染层**：若接口已返回——检查详情弹窗组件的字段映射与渲染逻辑，是否漏渲染或字段名对不上。
4. **文案与交互层**：「工具」Tab 空态文案引用的「测试」按钮——是按钮没实现，还是文案写错了？二选一修正。

## 四、分阶段实现

### 阶段 1：详情数据打通（P5 → P2）

**目标**：详情弹窗能拿到完整服务数据，「工具」Tab 回填工具列表。

- 后端：详情接口返回完整服务配置，包含已发现的 tools（名称、描述、inputSchema）；如工具发现结果未持久化，补充持久化逻辑或在详情接口内实时调用 tools/list。
- 前端：「工具」Tab 渲染工具列表（名称 + 描述，参数 schema 可折叠）；数量与列表页一致。
- 同步修正空态文案：要么补「重新发现」按钮（推荐，工作量小、价值高），要么改文案。

**验收**：打开 omichub-pipelines 详情卡 →「工具」Tab 列出 10 个工具，与列表页工具数一致；omichub-platform 5 个、omichub-tools 8 个同样一致。

### 阶段 2：「通用」Tab 按传输类型联动（P1）

**目标**：表单字段随传输方式动态显隐，builtin 展示完整启动配置。

- 后端：配置 schema 补齐 builtin 类型的 command / args / env 字段描述（若缺）。
- 前端：
  - `builtin` / `stdio`：显示启动命令、启动参数、环境变量（键值对编辑器）、工作目录、超时；
  - `sse` / `streamable-http`：显示端点 URL、请求头/鉴权、超时；
  - 切换传输方式时字段联动显隐，避免无效字段误导；
  - 服务名称若为不可编辑主键：改 `disabled` 样式 + tooltip「服务名称创建后不可修改」。

**验收**：三个 builtin 服务的详情卡均能看到完整启动配置；切到 SSE 类型时字段正确切换；空 placeholder 不再出现在不适用字段上。

### 阶段 3：「提示」「资源」Tab 接入或统一占位（P3、P4）

**目标**：两个 Tab 状态明确、样式统一。

- 自查服务端是否支持 prompts/list、resources/list：
  - 已支持 → 接入展示（名称 + 描述 + 参数/URI 说明）；
  - 未支持 → 保留占位文案，但两个 Tab 占位样式统一（图标 + 说明文字居中），与「工具」Tab 空态风格一致。

**验收**：四个 Tab 无"半成品"观感；未实现的 Tab 有明确的"后续版本支持"提示且样式统一。

### 阶段 4：一致性与回归检查

**目标**：整体收尾，防止顾此失彼。

- 弹窗控件样式与平台其他弹窗一致（输入框、开关、按钮）；
- 列表页「点击服务行可展开查看其内部工具列表」的展开区数据与详情卡「工具」Tab 同源；
- 保存逻辑回归：修改描述/超时后保存，列表页与详情卡同步刷新；
- 离线/异常态兜底：服务离线时详情卡各 Tab 的表现（工具列表置灰 or 显示最后一次发现结果 + 提示）。

**验收**：全链路走查通过，无样式打架、无数据不同步。
