# 用户模块权限管控功能 实现计划

> 适用对象：OmicHub 管理后台。本文档交付给编码 Agent（kimi code / Claude Code / CODEX 等）执行，
> 提示词块可直接整段复制粘贴。

## 背景与目标

管理员需要按用户控制其可使用的功能模块（典型场景：不想让某些用户使用 AI 助手 / AI 工作台）。
目标效果：管理员在「用户管理」中为每个用户勾选可用模块；未授权用户仍可打开页面，
但看到锁定提示（锁图标 + 占位页 + 首次弹窗），引导其联系管理员解锁；后端 API 层强制拦截，防止绕过。

## 方案评估结论（verdict）

方向成立，属于业界标准的 **per-user feature gating / entitlement** 模式：

- **前端控制展示、后端强制拦截**：前端按权限渲染锁定状态（UX 层），后端在每个 API 上校验授权（安全层），
  否则用户可通过 DevTools 直接调接口绕过。
- **未授权用统一占位组件而非冰冷 403**：通行做法是 NotAuthorized 占位页/组件，
  文案明确告知「无此模块权限，请联系管理员开通」。
- **管理员侧勾选矩阵配置**：典型 RBAC 管理面板即权限勾选网格，挂在用户管理的「更多」入口下。

相对用户原始设想（「打开页面就弹窗」）的三处微调：

1. **拦截交互分三层**：侧边栏锁图标（一眼可见未开通）→ 页面级占位页（常驻引导）→
   弹窗仅在每次会话首次进入时弹一次（避免每次误点都被打断）。
2. **后端同步校验**：AI 类及其他受管控模块的接口在服务端校验授权，前端只做展示层。
3. **防自锁**：管理员账号模块权限默认全开且接口层强制不可取消；
   「账号禁用」与「模块未授权」是两种独立状态，文案与逻辑分开。

## 需求清单

1. 模块授权数据模型：按用户存储被禁用模块列表（默认全开）。
2. 管理员配置入口：用户管理「更多 → 模块权限」，对话框勾选矩阵，AI 模块置顶标记。
3. 用户侧拦截：侧边栏锁图标 + 半透明；路由进入未授权模块显示占位页；
   每会话首次进入额外弹一次提示弹窗。
4. 后端强制校验：受管控模块 API 返回 403 + MODULE_LOCKED 错误码。
5. 边界与防自锁：管理员不可被取消权限；管理员专属模块（系统管理）不参与配置；
   账号禁用与模块未授权互不影响。

## 分阶段实现

### 阶段 1：数据模型与后端校验

- 用户表新增 `disabled_modules`（字符串数组，默认空数组 = 全部可用）。
- 模块注册表落在配置文件 `data/MODULE_LOCKED.yaml`，后端启动时加载并校验，
  经接口下发给前端；权限对话框、路由守卫、API 中间件全部从该注册表取模块清单。
- 用户信息接口下发 `disabled_modules`。
- 受管控模块 API 增加权限中间件：命中 `disabled_modules` 返回 HTTP 403 + `MODULE_LOCKED`，
  消息「该模块未开通，请联系管理员解锁」。
- 系统管理类模块仅管理员可用，不纳入配置；管理员权限接口层强制不可取消。
- 验收：直调被禁用户的 AI 接口返回 403 + MODULE_LOCKED。

### 阶段 2：管理员配置入口

- 用户管理表格「更多」下拉新增「模块权限」（管理员行禁用并提示原因）。
- 对话框勾选矩阵：每行一个模块，勾选 = 开通；AI 助手 / AI 工作台置顶并加「AI」标签。
- 底部显示「已开通 X / 共 Y 个模块」；保存更新后端并刷新列表；失败不关闭对话框并提示错误。
- 验收：勾选/取消保存后，用户侧 `disabled_modules` 同步变化。

### 阶段 3：用户侧拦截交互

- 侧边栏无权限模块显示锁图标，菜单项可点击，opacity 0.6。
- 路由守卫：进入未授权模块正常跳转，页面渲染统一 `NotAuthorized` 占位页
  （大锁图标 + 「该模块未开通」+ 联系管理员说明 + 「联系管理员」按钮）。
- 首次弹窗：每会话第一次进入未授权模块，在占位页上弹提示弹窗
  （「您暂无「{模块名}」模块的使用权限，请联系管理员解锁后使用。」+「我知道了」）；
  sessionStorage 记录已提示，会话内不重复弹。
- API 拦截：收到 `MODULE_LOCKED` 统一走占位页/弹窗逻辑，不按普通错误 toast。
- 权限变更用户侧下次刷新或重新拉取用户信息即生效，不要求实时推送。
- 验收：按总 checklist 逐项过。

### 阶段 4：边界与防自锁

- 账号「禁用」= 不可登录/使用全平台；「模块未授权」= 可登录、仅被管控模块锁定。
- 自检：管理员无法通过任何入口取消自己的模块权限；角色切换不丢权限数据。

## 〇、模块注册表配置文件（先做）

1. 新建 `data/MODULE_LOCKED.yaml` 作为全平台模块注册表（唯一数据源），
   初始内容包含当前所有侧边栏模块，schema 如下：

```yaml
# data/MODULE_LOCKED.yaml —— 平台模块注册表
# 新增模块时：在此文件追加一个条目即可，权限对话框 / 路由守卫 / API 中间件自动生效
modules:
  - key: ai-assistant          # 模块唯一标识，与前端菜单 key、路由一一对应
    name: AI 助手              # 权限对话框中的显示名
    route_prefix: /ai-assistant  # 前端路由前缀，路由守卫据此判断
    api_prefix: /api/ai          # 后端 API 前缀，权限中间件据此拦截
    lockable: true             # 是否可被管理员按用户禁用
    default_locked: false      # 新用户注册时默认是否锁定该模块
    ai: true                   # AI 类模块标记，权限对话框中置顶并显示「AI」标签
  - key: ai-workbench
    name: AI 工作台
    route_prefix: /ai-workbench
    api_prefix: /api/ai-workbench
    lockable: true
    default_locked: false
    ai: true
  # ……其余侧边栏模块（首页/仪表板/分析中心/数据管理/数据库/数据下载/任务中心/
  # 流程监控/结果报告中心/生信工具箱/用量统计/系统设置/关于OmicHub）按实际路由补齐
  # 系统管理类模块（用户管理/首页入口管理/饼干中心）也要列出，但 lockable: false，
  # 表示管理员专属、不参与按用户配置
```

2. 后端启动时加载该 YAML：解析失败或 key 重复时启动报错并打印具体行号，

   GET /api/modules/registry）把注册表下发给前端。
3. 用户表新增模块授权字段：存该用户被禁用的模块 key 列表（disabled_modules，
   字符串数组，默认空数组 = 全部可用）。

4. 新用户注册时：按注册表中 default_locked: true 的模块初始化其 disabled_modules。

## 一、数据模型与后端（阶段 1）

1. 用户信息接口（/me 或登录返回）中下发 disabled_modules，供前端渲染。
2. 后端权限中间件/装饰器：按注册表中各模块的 api_prefix 匹配请求路径，
   校验当前用户的 disabled_modules 不含该模块 key，否则返回 HTTP 403 +
   统一错误码 MODULE_LOCKED，错误消息为「该模块未开通，请联系管理员解锁」。
   新增模块接入拦截只需在 YAML 里配好 api_prefix，无需改中间件代码。
3. 系统管理（用户管理/首页入口管理/饼干中心）属于管理员专属模块，仅管理员角色
   可见可用，不纳入 disabled_modules 配置项；管理员账号的模块权限默认全开
   且接口层强制不可被取消（防自锁）。

## 二、管理员配置入口（阶段 2）

1. 用户管理表格「操作」列的「更多」下拉中新增「模块权限」菜单项
   （普通用户行可用；管理员行该项禁用并 tooltip 提示「管理员默认拥有全部模块权限」）。
2. 点击弹出对话框（复用现有 Dialog 组件）：标题为「模块权限 - {用户邮箱}」，
   内容为模块勾选矩阵：列表数据从后端下发的模块注册表渲染
   （只列出 lockable: true 的模块，禁止前端写死模块名），每个模块一行，
   含模块名、勾选框。勾选 = 开通，取消勾选 = 禁用。
   注册表中 ai: true 的模块排在最前并加「AI」小标签，方便管理员快速定位。
   YAML 里新增模块后，对话框自动出现对应行，无需改前端代码。
3. 对话框底部显示「已开通 X / 共 Y 个模块」，「保存」调用后端接口更新该用户
   disabled_modules，成功后 toast 提示「模块权限已更新」，并刷新用户列表数据。
4. 边界态：保存失败显示错误消息且不关闭对话框；网络加载中按钮 loading 防重复提交。

## 三、用户侧拦截交互（阶段 3）

1. 侧边栏：无权限的模块菜单项右侧显示小锁图标（el-icon Lock 或现有图标体系），
   菜单项保持可点击（不隐藏、不禁用），视觉上略微降透明度（opacity 0.6）。
2. 路由守卫：按注册表中各模块的 route_prefix 匹配目标路由，对应模块 key 在
   当前用户 disabled_modules 中时，正常进入路由，
   页面渲染统一的「模块未开通」占位页组件（新建 NotAuthorized.vue）：
   居中大锁图标 + 标题「该模块未开通」+ 说明文案「您暂无此模块的使用权限，
   如需开通请联系管理员解锁。」+ 主按钮「联系管理员」（mailto:管理员邮箱或
   复制管理员联系方式，按现有平台联系方式实现）。
3. 首次进入弹窗：每个会话（session）内，用户第一次进入未授权模块时，在占位页
   之上额外弹出一个提示弹窗（复用现有 Dialog/MessageBox），标题「模块未开通」，
   文案「您暂无「{模块名}」模块的使用权限，请联系管理员解锁后使用。」，
   单按钮「我知道了」。用 sessionStorage 记录「模块key:已提示」，
   同一会话内重复进入只显示占位页、不再弹窗；新会话重置。
4. 前端 API 拦截：收到 MODULE_LOCKED 错误码的响应时，统一按上述占位页/弹窗
   逻辑处理，不当作普通错误 toast。
5. 权限变更实时性：管理员修改权限后，用户侧下次刷新或重新拉取用户信息即生效，
   不要求 WebSocket 实时推送。

## 四、与既有「禁用」状态的区分（阶段 4）

1. 账号「禁用」（现有功能）= 账号不可登录/使用全平台；「模块未授权」= 可登录、
   可使用已开通模块，仅被管控模块显示锁定。两者文案与状态互不影响。
2. 自检：管理员不能通过任何入口取消自己的模块权限；角色切换为用户后再切回
   管理员，权限数据不丢失。

## 风险与回退

- **只做前端拦截**：后端不校验等于没做安全，验收必测「绕过前端直调 API」。
  应对：阶段 1 先行，后端中间件是硬门槛。
- **模块标识前后端不一致**：菜单 key 与后端模块标识写两遍容易漂移。
  应对：集中定义一份模块清单常量，后端下发或前后端共用。
- **管理员自锁**：把自己模块权限取消后无法恢复。
  应对：接口层强制拒绝取消管理员的模块权限，前端入口同步禁用。
- **弹窗骚扰**：每次进入都弹会打断用户。
  应对：sessionStorage 每会话每模块只弹一次，占位页常驻承担引导职责。
- **与「账号禁用」混淆**：两种状态文案/逻辑耦合会导致误判。
  应对：禁用走登录层拦截，模块未授权走模块层拦截，互不引用。

## 追加章节（第 2 轮需求）：模块注册表配置文件 data/MODULE_LOCKED.yaml

### 需求来源

用户提出：模块权限管控需要配套一个配置文件 `data/MODULE_LOCKED.yaml`，
支撑后续模块扩展——平台新增模块后，只在 YAML 里加一条配置即可纳入权限管控，
不需要改权限相关代码。

### 设计要点

1. **职责边界（关键）**：
   - YAML = **模块注册表**，声明平台有哪些模块、哪些可锁、路由/API 前缀、
     新用户默认锁定状态。全平台唯一数据源。
   - 数据库 `disabled_modules` = **每个用户实际被禁的模块 key 列表**。
   - 两者不得合并：per-user 权限写进 YAML 会导致多管理员并发修改互相覆盖。
2. **YAML schema**（见上方提示词块「〇、模块注册表配置文件」）：
   `key / name / route_prefix / api_prefix / lockable / default_locked / ai`。
   管理员专属模块（系统管理）也列入但 `lockable: false`，前端权限对话框只渲染
   `lockable: true` 的条目。
3. **加载与校验**：后端启动时加载，语法错误或 key 重复则拒绝启动并报具体原因；
   经接口下发前端，权限对话框、路由守卫、API 中间件全部从注册表取清单，
   前端任何位置禁止写死模块名。
4. **新模块接入工作流**（扩展时只需 3 步）：
   1. 在 `data/MODULE_LOCKED.yaml` 追加模块条目（填好 key、route_prefix、api_prefix）；
   2. 实现该模块的前端页面/菜单与后端 API（沿用注册表中的 key 与前缀）；
   3. 重启后端（如实现热加载则免重启）。
   权限对话框自动出现新模块行，路由守卫与 API 中间件自动对其生效。
5. **default_locked 的用途**：新模块上线想「默认关闭、按需开通」时设
   `default_locked: true`，新注册用户自动锁定，老用户不受影响
   （如需对老用户生效，另做一次数据迁移，属一次性运维操作，不进代码）。
