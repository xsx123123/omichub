# 任务：实现「聊天统一入口 · 双通道协作分流」——重通道连接层 + 状态回流

> 本文件是给 AI 编码助手（ChatGPT 等）的实施提示词，配套设计文档为
> `docs/26.8.1/聊天统一入口_双通道协作分流实现方案.md`（先完整阅读，特别是 §3、§4、§6、§7、§10、§12）。

## 背景

你在 OmicHub 仓库中工作（FastAPI + Celery + Vue3 + Naive UI）。平台要落地「聊天统一入口」：

```text
聊天输入 → router 判断意图
  ├─ 轻量协作 → parallel_subagents（已实现，不在本次范围）
  └─ 重型交付 → 创建 AgentTeams Case → 聊天挂 Case 卡片 → 关键状态回流聊天
```

已落地、可直接复用的部分（不要重写）：

- AgentTeams Bridge 与受控代理：`integrations/agentteams/bridge/`、`src/omichub/api/v1/agentteams.py`、
  `src/omichub/application/services/agentteams_service.py`（Case 创建/预检/审批/提交链路完整）；
- 前端协作中心与状态映射：`frontend/src/views/AgentTeams*.vue`、`frontend/src/api/agentTeams.ts`、
  `frontend/src/stores/agentTeams.ts`、`frontend/src/utils/agentTeamsState.ts`；
- 聊天 SSE chunk 机制：参考 `chat_service.py` 中 `consultation` / `subagents` / `handoff` chunk 的接法；
- 工具注册惯例：`tool_configs/tools_schema.yaml` + `data/ai/tools/*.yaml` + 薄壳 service
  （对照 `agent_handoff_tool_service.py`、`parallel_subagent_tool_service.py`）；
- 免迁移会话元数据：`chat_sessions.sandbox_meta`（JSON 字段）；
- 管理端运行时开关模式：参考 `subagent_fanout_enabled`（`site_settings` + `PATCH /admin/platform-config`）。

## 你要实现的（对应设计文档 Phase 1 + Phase 2）

### 1. `create_agentteams_case` 工具（后端）

- 按设计文档 §6.2 的契约在 `tool_configs/tools_schema.yaml` 注册
  （`requires_confirm: true`、`control_tool: agentteams_case`、幂等注解）；
- 新建 `src/omichub/application/services/agentteams_case_tool_service.py`：
  校验开关/流程白名单/项目归属 → 幂等检查（同会话同 objective 哈希 5 分钟窗口）→
  调 `AgentTeamsService` 创建 Case → 写 `sandbox_meta` 会话绑定 → 返回自包含 `llm_payload`；
- `chat_service.py` 增加 `control_tool: agentteams_case` 特判分支（对齐 `subagent_fanout` 先例，
  绕开 ToolBridge 3KB 上限），透出 §6.5 的 `agentteams_case` SSE chunk；
- 确保该工具在 fan-out 子 Agent 环境中不可见（沿用 control_tool 剥离规则）。

### 2. 意图分流（router 侧）

- `data/ai/prompts/router.md` 增加 `delivery_case` 意图判定标准与置信度输出（设计文档 §4.2）；
- `data/ai/prompts/general.md` 追加双通道决策表（设计文档 §10）与
  「模糊时默认轻通道 + 末尾提示可创建协作 Case」的行为纪律；
- `create_agentteams_case` 挂载进 `general`（及 router 可达的主 Agent）的工具包。

### 3. 前端（聊天内 Case 卡片 + 入口）

- 新建 `frontend/src/components/ai-chat/AgentTeamsCaseCard.vue`：阶段 Tag（复用
  `agentTeamsStatus.ts`）、下一步角色、「查看协作」跳转、`approval_pending` 高亮条、
  20s 可见轮询（复用 `agentTeams` store）；注册进 `KimiMessageItem` chunk 渲染分支；
- 聊天输入框加「转为协作 Case」按钮（引导文案模板，不直接调 API），受 `agent_teams`
  模块权限控制（复用 `moduleGuard.ts`）；
- 系统通知消息渲染为居中提示条（对齐「上下文已压缩」样式）。

### 4. CaseWatchService（状态回流，Phase 2）

- 新建 `src/omichub/application/services/agentteams_case_watch_service.py`：
  60s beat 扫描绑定会话的非终态 Case → 代理读状态比对 →
  关注集合 `{approval_pending, quality_blocked, delivery_ready, execution_failed, cancelled}`
  迁移时写系统通知消息 + 在线会话 SSE 推送；同状态只通知一次；终态停监控；
- 在 `src/omichub/infrastructure/celery_app/celery.py` 注册 beat（对齐现有 mas beat 模式）；
- 扫描/通知任何异常只记日志，绝不影响聊天主链路。

### 5. 配置与测试

- `core/config.py` + 管理端平台设置新增 `agentteams_chat_entry_enabled`（默认 false，免 TOTP 灰度）、
  `agentteams_chat_flow_whitelist`、`agentteams_case_watch_interval_seconds`；
- 聚焦单测：工具契约与幂等、白名单/权限拦截、开关关闭时工具不可见、子 Agent 工具表剥离、
  通知去重、beat 失败隔离；前端 `agentTeamsCaseCard` 状态渲染单测（Vitest）。

## 硬约束（违反即为不合格）

- 不修改 Bridge 状态机、MAS DAG、ChatService 主循环结构；连接层只读复用受控代理。
- Case 创建必须经 `requires_confirm` 确认卡；任何路径不得跳过用户确认直接建 Case。
- 意图分流「宁轻勿重」：拿不准一律走轻通道，不得把问答/咨询判成 `delivery_case`。
- Case 状态读取只走 `/api/v1/agent-teams/*` 受控代理（`requester_ref` 用户过滤），
  不新增直连 Bridge 的通道；会话绑定信息不含令牌/快照/样本原文。
- 通知去重必须实现；同一 Case 同一状态重复通知视为 bug。
- LLM Manager 未部署，文档、UI 文案、注释中不得出现「智能 Manager 已上线」类不实描述；
  Case 编排能力描述统一用「流程自动化编排」。
- 凭证不出现在代码、日志、SSE 事件或返回体中。

## 验收标准（对应设计文档 §12）

1. 聊天输入「帮我跑完项目 X 的 RNA-seq 并出报告」→ 确认卡 → 确认后创建真实 Case，
   聊天气泡出现 Case 卡片，阶段与协作中心一致；
2. 「TP53 是什么」「RNA-seq 参数怎么填」不触发 Case 创建；
3. Case 进入 `approval_pending` 后一个扫描周期内聊天收到系统通知，重复状态不重复通知；
4. 开关关闭时工具对模型不可见、前端入口隐藏；
5. 同会话重复确认相同目标返回既有 Case；
6. 全部新增测试通过；`ruff check`、`ruff format --check`、`vue-tsc --noEmit`、
   `npm run build` 通过；
7. `docker restart omichub-web omichub-beat` 后做一次双 Agent 运行时冒烟（不只 py_compile）。
