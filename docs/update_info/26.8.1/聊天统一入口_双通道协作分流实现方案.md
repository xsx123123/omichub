# 聊天统一入口：双通道协作分流实现方案

> **文档状态**：设计稿（待实施）
> **创建日期**：2026-08-01
> **适用目标**：聊天界面作为多 Agent 协作的统一入口；按意图分流为「对话内轻量协作」与「AgentTeams 重型交付」两条通道，用户无感切换。
> **前置文档**：
> - `ARCHITECTURE_DESIN/multi-agent.md`（fan-out 已落地能力与设计约束）
> - `docs/26.8.1/AgentTeams_非侵入式多Agent协作编排实施方案.md`（Case/Bridge/审批链现状）
> - `docs/26.8.1/AgentGateway_实施提示词.md`（受控 Agent Gateway，重型通道的科学解读依赖）

---

## 1. 目标链路

```text
聊天输入
  → router 判断意图
  ├─ 轻量协作（查几个基因、并行起草、讨论个问题）
  │    → parallel_subagents / 多轮讨论（对话内秒级返回）
  └─ 重型交付（"给我跑完这个 RNA-seq 并出报告"）
       → 创建 AgentTeams Case（LLM Manager 解析分配）
       → 聊天气泡里挂 Case 卡片，实时状态可跳协作中心
       → 关键节点（科学解读完成/待审批/交付）回流聊天通知
```

## 2. 设计原则

1. **一个入口，两条通道**：用户只在聊天界面表达意图；分流由系统完成，不要求用户理解 Case、fan-out 等概念。
2. **轻重不混**：秒级问答/并行子任务绝不创建 Case；分钟/小时级交付任务绝不在对话内硬跑。
3. **重通道复用现有 AgentTeams 链路**：Case 创建、预检、审批、提交、质量门禁全部走已落地的 Bridge/代理/协作中心，本方案只做「聊天 ↔ Case」的连接层。
4. **诚实状态**：LLM Manager（真 AgentTeams 控制面）未部署前，Case 编排由 Bridge 状态机驱动，文档与 UI 均不得宣称"智能 Manager 已上线"。
5. **最小侵入**：不改 ChatService 主循环结构、不改 Bridge 状态机语义、不改 MAS/Celery；新增能力以工具 + SSE chunk + 独立服务层落地。

## 4. 意图分流设计

### 4.1 三级分流（成本从低到高）

```text
用户消息
  │
  ├─ L1 确定性规则（~0 成本，<10ms）
  │    命中「交付类强信号」→ 重通道候选
  │    命中「显式指令」→ 直接执行（/case、「转为协作 Case」按钮）
  │
  ├─ L2 Router LLM 分类（复用 agent-router）
  │    输出 intent ∈ {chat, light_collab, delivery_case}
  │
  └─ L3 模糊兜底
       默认轻通道；主 Agent 在回答末尾提示
       「如需完整流程交付，我可以为你创建协作 Case」
```

**L1 交付类强信号**（正则/关键词 + 上下文，任一条命中即候选）：

- 动词 + 流程名组合：「跑/运行/提交 + rna-seq/atac-seq/流程名」；
- 交付词：「出报告 / 交付 / 全流程分析 / 帮我分析完」且会话含项目或文件上下文；
- 显式指令：`/case` 前缀、输入框「转为协作 Case」按钮（前端新增，见 §7.3）。

L1 只负责"快速放行明显的交付请求"，拿不准的一律交 L2，**宁轻勿重**（错判为轻的代价是用户多一次确认；错判为重的代价是污染 Case 列表）。

### 4.2 L2 Router 扩展

`agent-router` 的分类输出增加 `delivery_case` 意图，提示词补判定标准：

- 用户目标包含**真实计算 + 交付物**（报告、结果文件、可审计产物）→ `delivery_case`；
- 只是询问流程怎么做、参数怎么填、要个解释 → 仍归 `chat`/`light_collab`；
- router 输出附带 `confidence`，< 阈值时按 L3 兜底。

### 4.3 重通道确认卡（必经）

即使命中 `delivery_case`，也**不直接创建 Case**。主 Agent 调用 `create_agentteams_case` 工具（`requires_confirm: true`），前端弹确认卡：

- 将创建的 Case 目标（流程、项目、样本上下文摘要）；
- 明示「创建后先只读预检，不会立即提交计算任务」；
- 用户确认后才真正调用 `/api/v1/agent-teams/cases`。

理由：Case 是持久化协作实体且有通知副作用，创建动作必须留人审痕迹；这与 Bridge「提交计算需审批令牌」的纪律一致。

## 5. 轻量通道（对话内协作）

### 5.1 v1：直接用已有 fan-out（零新代码）

- 管理端打开「对话内并行子 Agent」开关（`site_settings.subagent_fanout_enabled`）；
- 灰度面按 Agent YAML 双标记控制（`tool_packs: [subagents]` 能派生、`features.subagents_spawnable` 能被派生）；
- 当前已挂：`general`、`code` 可派生；`rnaseq`、`scrna` 可被派生。v1 追加 `viz`、`shania` 可被派生。

### 5.2 v2：多轮讨论（host-mediated，独立迭代）

在 `ParallelSubAgentService` 上增加轮次循环：

```text
第 1 轮：各助手独立作答（现有 fan-out）→ {结论, 证据, 异议}
第 2..N 轮（N≤3）：主 Agent 互投他人摘要 → 助手补充/反驳
收敛：主 Agent 综合裁决
```

约束沿用 multi-agent.md §4.4 的 C1–C7（独占 session、剥离控制工具、超时、轮数上限、失败隔离），新增：

- 轮间互投内容只传**摘要**（每条 ≤800 字），不传原始全文；
- 总 token 预算 = 单次 fan-out × 轮数，硬上限可配；
- 助手之间不直连，主 Agent 是唯一 hub（主持式，非自由对话）。

v2 是独立工作包，不阻塞 v1 与重通道。

## 6. 重型通道（聊天 ↔ AgentTeams Case 连接层）★ 本方案核心

### 6.1 链路详图

```text
用户：「帮我把这个项目跑完 RNA-seq 并出报告」
  │
  ▼
[1] router 判定 delivery_case
  │
  ▼
[2] 主 Agent 调 create_agentteams_case（requires_confirm）
  │    参数：{project_id, flow_id, objective, sample_context_refs}
  ▼
[3] 前端确认卡 → 用户确认
  │
  ▼
[4] 后端经受控代理 POST /api/v1/agent-teams/cases
  │    （requester_ref = 当前用户；Bridge 自动分派 Data Steward 只读预检）
  ▼
[5] 会话 ↔ Case 绑定：chat_sessions.sandbox_meta.agentteams_case_ids += [case_id]
  │
  ▼
[6] 聊天内挂 Case 卡片（SSE chunk: type="agentteams_case"）
  │    显示：Case 名称 / 当前阶段 / 下一步角色 / 跳转协作中心
  │    卡片自轮询状态（复用 agentTeams store，20s，页面可见时）
  ▼
[7] Case 按 Bridge 状态机推进：预检 → 审批 → 执行 → 质量 → 交付
  │    （科学解读节点待 Agent Gateway 落地后插入，见 §9）
  ▼
[8] 关键状态回流聊天（CaseWatchService，见 §6.3）：
  │    approval_pending / quality_blocked / delivery_ready / execution_failed
  │    → 以系统消息写入会话，SSE 推给在线会话
  ▼
[9] 用户在聊天里点卡片跳 /agent-teams/cases/:id 完成审批/查看证据
```

### 6.2 `create_agentteams_case` 工具契约

`tool_configs/tools_schema.yaml` 新增：

```yaml
  - key: agentteams-create-case
    name: create_agentteams_case
    description: >
      为需要真实计算交付的用户目标创建 AgentTeams 协作 Case。创建后仅执行只读预检，
      不提交任何计算任务；任务提交须经用户在协作中心人工审批。
      仅当用户目标包含真实流程执行与交付物时使用；普通问答、参数咨询、
      轻量并行子任务禁止使用本工具。
    category: agent-orchestration
    invocation_mode: backend_sync
    service: omichub.application.services.agentteams_case_tool_service.AgentTeamsCaseToolService
    method: run
    requires_confirm: true
    annotations: {readOnlyHint: false, destructiveHint: false, openWorld: false, idempotent: true}
    extra: {user_scoped: true, control_tool: agentteams_case}
    input_schema:
      type: object
      properties:
        objective: {type: string, description: 自包含的交付目标描述，≤500 字}
        project_id: {type: string, description: 目标项目 UUID}
        flow_id: {type: string, description: 目标流程 ID，如 rna_seq / atac_seq}
        sample_context_refs:
          type: array
          items: {type: object, properties: {kind: {type: string}, id: {type: string}}}
          description: 样本表/文件引用（可选）
      required: [objective, project_id, flow_id]
    llm_result_fields: [case_id, title, status, summary]
    ui_result_fields: [case_card]
```

服务层 `AgentTeamsCaseToolService`（薄壳，对齐 `agent_handoff_tool_service.py` 分层）：

1. 校验：`flow_id` 在流程白名单内、`project_id` 归属当前用户、开关 `agentteams_chat_entry_enabled` 开；
2. 幂等：同一会话 + 相同 `objective` 哈希 5 分钟内重复调用 → 返回已创建的 Case，不新建；
3. 调用 `AgentTeamsService`（现有 `/api/v1/agent-teams` 代理服务层）创建 Case；
4. 写会话绑定（§6.4）；发 SSE chunk（§6.5）；
5. 返回自包含 `llm_payload`（case_id、当前阶段、预检结论摘要、下一步指引）。

### 6.3 CaseWatchService（状态回流）

新建 `application/services/agentteams_case_watch_service.py`：

- Celery beat 每 60s 扫描「绑定到会话且非终态」的 Case（从 `chat_sessions.sandbox_meta` 反查）；
- 对每个 Case 经代理读当前状态，与上次记录比对；
- 状态迁移到关注集合 `{approval_pending, quality_blocked, delivery_ready, execution_failed, cancelled}` 时：
  - 以 `role="system"` 通知消息写入会话（内容：阶段变化 + 下一步动作 + Case 链接）；
  - 在线会话经 SSE 推送 `agentteams_case` chunk（`phase:"status_changed"`）；
- 同一 Case 同一状态只通知一次（`sandbox_meta.agentteams_case_notified` 记录已通知状态）；
- 终态后停止监控；全部扫描失败仅记日志，不影响主链路。

**为什么用 beat 而不是长连接**：Bridge 事件当前就是 20s 轮询模型，聊天侧 60s 节拍足够；不引入新的推送基础设施。

### 6.4 会话 ↔ Case 绑定

- 复用 `chat_sessions.sandbox_meta`（已有 JSON 字段，免迁移）：
  ```json
  {
    "agentteams_case_ids": ["bioops_..."],
    "agentteams_case_status": {"bioops_...": "executing"},
    "agentteams_case_notified": {"bioops_...": ["approval_pending"]}
  }
  ```
- 一个会话可绑多个 Case；Case 详情反向关联会话用于通知（v1 只正向查询，不建反查索引）。

### 6.5 SSE chunk 契约

新增 chunk 类型 `agentteams_case`（对齐 `consultation`/`subagents` 的接法）：

```json
{
  "type": "agentteams_case",
  "metadata": {
    "phase": "created | status_changed",
    "case_id": "bioops_...",
    "title": "rna-seq 全流程分析",
    "status": "preflight_running",
    "next_actor": "data-steward",
    "case_url": "/agent-teams/cases/bioops_...",
    "session_id": "...", "message_id": "..."
  }
}
```

### 6.6 权限与安全

- Case 创建、状态读取全部经受控代理 `/api/v1/agent-teams/*`（`requester_ref` 按当前登录用户过滤），聊天连接层不新增任何直连 Bridge 的通道；
- `create_agentteams_case` 为 `requires_confirm: true`，子 Agent（fan-out）环境按 C3/C4 规则**不可见**该工具；
- CaseWatchService 只读代理接口，不持有 Bridge 写凭证；
- 会话绑定信息不含令牌、快照、样本原文。

## 7. 前端方案

### 7.1 Case 卡片气泡（`AgentTeamsCaseCard.vue`）

- 位置：`frontend/src/components/ai-chat/`，注册进 `KimiMessageItem` 的 chunk 渲染分支；
- 内容：Case 标题、阶段 Tag（复用 `agentTeamsStatus.ts` 映射）、下一步角色、最近更新、
  「查看协作」按钮（跳详情页）、「待审批」高亮条（状态为 `approval_pending` 时）；
- 状态刷新：卡片挂载后经 `agentTeams` store 轮询（20s，页面可见时），复用现有 `api/agentTeams.ts`；
- 视觉复用 `ApprovalCard`/`TaskProgressCard` 信息结构，遵守 `ARCHITECTURE_DESIN/fontend.md` 令牌规范。

### 7.2 系统通知消息

- CaseWatchService 写入的系统消息渲染为居中提示条（样式对齐现有「上下文已压缩」提示），
  附 Case 链接；不产生 AI 回答轮次。

### 7.3 显式入口

- 聊天输入框工具区加「转为协作 Case」按钮（带 `NTooltip` + `aria-label`）：点击后在输入框插入
  引导文案模板，由用户补全后发送（不直接调 API，保持「模型理解 → 确认卡」链路统一）；
- 入口显隐由模块权限 `agent_teams` 键控制（复用 `moduleGuard.ts`）。

## 10. 与其他机制的决策表（写入 router/主 Agent 提示词）

| 场景 | 通道 |
|---|---|
| 秒~分钟级、独立子任务、无需用户中途确认 | parallel_subagents（轻通道 v1） |
| 多助手就同一问题讨论收敛 | 多轮讨论（轻通道 v2） |
| 整段会话换专家接手 | Handoff |
| 真实计算 + 交付物 + 需要审批/证据 | **AgentTeams Case（重通道，本方案）** |
| 已批准的管道 DAG、断点重试 | MAS |
| 普通问答、解释、咨询 | 直接回答 / 会诊 |

## 11. 实施步骤

**Phase 1 —— 重通道连接层（核心，4–6 人日）**

1. `agentteams_case_tool_service.py` + schema 注册 + 开关配置；
2. 会话绑定读写 + 幂等；
3. SSE chunk `agentteams_case` 后端透出；
4. 前端 Case 卡片气泡 + 确认卡 + 显式入口按钮；
5. router 提示词增加 `delivery_case` 意图与决策表；
6. 聚焦单测（契约/幂等/权限/开关）+ 运行时冒烟。

**Phase 2 —— 状态回流（2–3 人日）**

7. CaseWatchService + beat 注册 + 通知去重；
8. 系统通知消息渲染。

**Phase 3 —— 轻通道增强（独立，3–5 人日）**

9. 多轮讨论（§5.2）+ 前端泳道卡片迭代。

## 12. 验收标准

1. 聊天中说「帮我跑完项目 X 的 RNA-seq 并出报告」→ 弹确认卡 → 确认后创建真实 Case，
   聊天气泡出现 Case 卡片，阶段与协作中心一致；
2. 卡片状态与 `/agent-teams/cases/:id` 详情页状态一致（容差一个轮询周期）；
3. Case 进入 `approval_pending` 后 ≤90s 聊天内收到系统通知；重复状态不重复通知；
4. 普通问答（「TP53 是什么」）不触发 Case 创建；参数咨询不触发；
5. 开关关闭时 `create_agentteams_case` 对模型不可见；
6. 同会话重复确认相同目标 → 返回既有 Case，Case 列表不重复；
7. 子 Agent（fan-out）工具表中无 `create_agentteams_case`；
8. 全部新增单测通过，`ruff check` / `vue-tsc --noEmit` / 生产构建通过；
9. 文档与 UI 文案不出现「智能 Manager 已上线」类不实描述。

## 13. 风险与开放问题

| 风险 | 说明 | 缓解 |
|---|---|---|
| 意图错判 | 轻判重污染 Case 列表；重判轻用户得不到交付 | L3 宁轻勿重 + 确认卡必经 + 显式入口兜底 |
| 通知噪音 | 多 Case 多状态频繁打断聊天 | 只关注 4 类关键迁移；同状态去重；终态停监控 |
| beat 延迟感知 | 60s 节拍对「等审批」场景偏慢 | v1 可接受；v2 评估事件驱动 |
| 双通道认知混淆 | 用户/模型分不清轻重边界 | 决策表进提示词；确认卡文案明示「不立即提交计算」 |
| 会话绑定膨胀 | sandbox_meta 随 Case 数增长 | 终态 Case 清理状态缓存，仅留 ID 列表 |

**开放问题（实施前定）**：

1. Case 卡片是否需要「在聊天内直接审批」（v1 不做，跳协作中心审批——保持审批 UI 单点维护）；
2. 多轮讨论 v2 是否与会诊服务合并（倾向不合并：会诊只读无工具，多轮带工具）；
3. 游客/无 `agent_teams` 模块权限用户的降级形态（隐藏入口 + 工具不可见，还是仅只读）。
