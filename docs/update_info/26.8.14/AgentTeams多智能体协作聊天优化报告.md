# AgentTeams 多智能体协作聊天优化报告

> 适用对象：基于 AgentTeams 实现的「团队协作聊天框」（Manager 管家 + 代码助手 + 可视化专家等多智能体编排）。
> 本文档结构：现象复盘 → 问题清单与诊断 → 根因假设 → 分阶段优化方案 → 可粘贴给编码 Agent 的提示词 → 验收 Checklist。
> 核心原则：**在现有系统基础上修改，不是重新设计**；所有视觉诉求落成具体数值，所有流程诉求落成状态机/事件级改动。

---

## 一、背景与触发场景

用户在团队聊天框中发送：`@workspace/chat-uploads/29418210ba504a31aa61544788605d87.treefile 帮我对这个文件进行可视化并解释需要`（IQ-TREE 输出的 TnpD 转座酶系统发育树，约 22 KB）。

**预期行为**：用户已授予全部权限，系统应自主完成「规划 → （自动）审批 → 执行 → 质控 → 交付」，最终回传系统发育树图 + 生物学解释文本。

**实际行为**：Case 停在规划阶段，计划校验失败（`general plan work item lacks objective or skill_name`），状态条停在「等待修正」，但界面看不到修正了什么、谁在修、修到什么程度；全程未产出任何文件。

## 三、问题清单与诊断

### A. 核心流程问题（致命，优先级 P0）

**A1. 计划校验失败后系统躺平，无自愈机制**
`general plan work item lacks objective or skill_name` 说明 Planner 生成的计划 work item 缺少必填字段，被 schema 校验拦截。这是**编排层内部错误**，正确行为是：编排层把校验错误反馈给 Planner 自动重试重生成（self-healing loop，带次数上限），而不是把英文校验原文抛给用户并停住。当前实现等于「内部 bug 让用户扛」。

**A2. 「已授予全部权限」没有穿透到审批节点**
用户明确已给所有权限，但流程仍被「审批」环节阻断（Manager 原话：「计划冻结后会在本房间请求确认，确认通过后才会…执行」）。说明权限配置只覆盖了工具调用层，**没有覆盖 Case 状态机的审批门禁**；或者状态机根本没有读取 auto-approve 配置。这是用户「没有自主调用工具产出最终结果」的直接原因。

**A3. 「等待修正」状态黑盒**
状态条显示「等待修正」，但：修正对象是什么（哪个 work item、缺哪个字段）、由谁修正（Manager 自动修？等用户修？）、修正进度、失败后的出口——全部不可见。用户只能干等，且不知道自己在等什么。

**A4. 无超时与升级路径**
从截图时间线看，校验失败后 Case 悬挂，没有「自动重试第 n 次」「重试超限，需要你介入」等任何后续事件。

### B. 回复内容问题（P1）

**B1. 助手回复被截断**：代码助手的文件解读以「…以…」结尾，句子不完整。需排查两层：后端生成侧（max_tokens / 输出截断）与前端流式渲染侧（SSE 断流后未续传、done 事件提前触发）。

**B2. 内部实现细节泄露**：`planning_running`、`planning_advice`、`agent-viz`、`ggtree`、`沙盒`、`workspace_file_preview` 等工程术语直接出现在用户可见文案里。用户要的是「树画得怎么样了」，不是你们的编排架构。

**B3. Manager 回复冗长且负面**：「当前不会产出任何文件，请勿将规划阶段误认为已完成执行」这类话术是在教育用户，而不是帮用户。规划阶段的进度反馈应压缩为一条简短状态（如「规划已完成，正在自动执行分析」），而非整段流程说明书。

### C. 排版与交互问题（P1~P2）

**C1. 长标识符无断行**：用户气泡内哈希文件名挤压正文。需 `word-break: break-all` + 路径类内容等宽字体处理。

**C2. 状态枚举原文直出**：`planning_running` 等需经 i18n 字典映射为中文友好文案。

**C3. 工具调用卡片信息失真**：
- 同一工具连续调用 4 次平铺展示，未折叠；
- 30.8s 的调用只显示「工具调用」，无工具名（兜底文案缺失）；
- 进度条恒满（蓝条全满但状态「进行中」），无真实进度语义。

**C4. 错误横幅无引导**：英文原文 + 无解释 + 无操作按钮（重试/终止/修改需求），用户看到后没有任何可做的事。

**C5. 状态条与实际状态脱节**：「等待修正」不在「计划→审批→执行→质控→交付」五个节点里，是异常态，但 UI 上没有异常态的专门呈现（谁修、修什么、还要多久）。

**C6.（待验证）消息重复推送**：同一 Manager 消息疑似渲染两次，需验证是 SSE 重复投递还是前端去重逻辑缺失。

## 四、根因假设与排查方向（供编码 Agent 验证，勿直接当结论）

> 以下假设基于截图现象推断，编码 Agent 需逐条在代码中证实/证伪后再动手。

### 针对 A1/A4（计划校验失败、无自愈）

- **假设 1**：Planner 的 prompt/输出解析层在生成 general plan work item 时丢失 `objective` 或 `skill_name` 字段（可能因长文件路径挤压 prompt、或结构化输出解析丢字段）。验证：抓取本次 Case 的 Planner 原始输出 JSON，检查字段缺失发生在生成侧还是解析侧。
- **假设 2**：编排层有 schema 校验，但校验失败后**没有重试回路**（没有将校验错误作为反馈重新调用 Planner）。验证：读 Case 状态机代码，查 `plan_validation_failed` 状态的后继转移是「重试」还是「停机」。
- **假设 3**：重试回路存在但对前端不可见（静默重试中），即「等待修正」其实是「自动修正中」——若证实，问题降级为 C5 的展示问题。

### 针对 A2（权限未穿透审批）

- **假设 4**：「全部权限」配置只作用于工具调用白名单，Case 状态机的 `approval` 节点硬编码了「必须人工确认」。验证：grep 审批节点代码，确认是否读取用户权限/auto-approve 配置。
- **假设 5**：auto-approve 配置存在但作用域不对（如对 Manager 生效、对新分派的 agent-viz 不生效）。

### 针对 A3（等待修正黑盒）

- **假设 6**：修正流程（correction）没有定义领域事件（如 `correction_started / correction_applied / correction_failed`），或后端发了事件但前端未订阅。验证：查 SSE 事件流日志，看「等待修正」期间有无事件推送。

### 针对 B1（回复截断）

- **假设 7**：后端 LLM 输出触及 max_tokens 被截断（`finish_reason=length`），后端未做续写或截断标记。验证：查本次响应的 finish_reason。
- **假设 8**：前端 SSE 流提前断开或 done 事件提前触发，正文渲染停止。验证：对比后端完整响应与前端渲染文本的末尾。

### 针对 C6（消息重复）

- **假设 9**：断线重连后历史消息与实时消息未按 message_id 去重。验证：检查前端消息列表的 key 与去重逻辑。

## 五、分阶段优化方案

### 阶段 1：让任务跑通（流程自主性，P0）

1. **计划校验失败自动重试**：schema 校验失败时，编排层将错误详情（缺哪个字段、哪个 work item）作为反馈追加给 Planner 重新生成，上限 3 次；超限后升级为「需要人工介入」事件，前端给出可操作按钮（重试 / 修改需求 / 终止 Case）。
2. **审批节点尊重权限配置**：用户权限为「全部允许 / 全自动」时，Case 状态机跳过人工审批节点（auto-approve），状态条直接 计划 → 执行，并在时间线留一条「已根据你的授权自动批准」记录；权限为「需确认」时才出现人工审批 UI。
3. **超时兜底**：任一节点超过阈值（如规划 120s、执行 600s）无事件输出，自动上报并给出重试入口，禁止 Case 无声悬挂。

### 阶段 2：状态透明化（「等待修正」可见，P0~P1）

1. **定义修正领域事件**：`correction_started`（谁在修、修什么：work item 名 + 缺失字段）、`correction_applied`（修正 diff 摘要）、`correction_failed`（失败原因 + 下一步）。后端推送，前端订阅。
2. **异常态专门 UI**：状态条出现「等待修正」时，下方展开修正详情卡：修正对象、进度（第 n 次/上限 m 次）、预计动作；不再只显示一个干巴巴的标签。
3. **状态文案中文化**：建立状态枚举 → 中文文案映射字典（如 `planning_running` →「规划中」、`waiting_correction` →「自动修正中（第 n 次）」），用户可见层禁止出现 snake_case 原文。

### 阶段 3：回复内容与排版治理（P1~P2）

1. **截断治理**：后端检测 `finish_reason=length` 时自动续写或在末尾追加「内容可能被截断」标记；前端对非句末标点结尾的回复显示「继续生成」按钮。同时按第四节假设 7/8 排查流式链路。
2. **文案分层**：用户可见消息只讲「进度 + 结果 + 需要你做什么」；`agent-viz / ggtree / 沙盒 / workspace_file_preview` 等实现术语收进「技术详情」折叠区。Manager 规划阶段反馈压缩为一句话（例：「规划完成，正在执行系统发育树可视化与解读」）。
3. **工具调用卡片**：同一工具连续调用折叠为「工具名 ×n」，点击展开明细；工具名缺失时禁止显示「工具调用」兜底（从调用上下文取 display name）；耗时 ≥5s 显示已运行秒数；进行中状态用不确定进度动画（indeterminate），不用恒满进度条。
4. **长标识符断行**：聊天气泡内路径/哈希/URL 类内容 `word-break: break-all`，等宽字体（如 `ui-monospace, SFMono-Regular`），气泡 max-width 保持约 75%。
5. **错误横幅改造**：用户可见层只显示中文摘要 + 当前自动处理状态（「计划生成不完整，正在自动重试（第 1/3 次）」）；英文原始错误折叠进「技术详情」；重试超限后给出按钮组（重试 / 修改需求 / 终止）。
6. **消息去重**：前端消息列表按 message_id 去重，断线重连合流时丢弃已存在 id（验证假设 9 后实施）。
