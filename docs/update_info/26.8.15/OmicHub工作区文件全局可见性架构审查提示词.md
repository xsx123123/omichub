# OmicHub 工作区文件全局可见性：方案评估 + 架构审查提示词

## Part 1：方案评估结论（2026-08-15）

### Verdict：方向正确，是多组学平台的骨架级设计，但有 3 个实现要点必须守住

**设计内容**：用户个人空间（工作区）下的所有文件，对四个模块统一可见——
1. AI 助手（星尘 AI 对话，含 Workspace MCP 文件工具 list_files / read_file / get_file_info）
2. AI 工作台（沙盒执行环境，Agent 读写/产出分析文件）
3. 团队协作（协作室/共享空间）
4. 生物信息工具箱（BLAST 等，消费工作区文件、结果回写）

并需同时支持**云端 SaaS 部署**与**本地私有化部署**两条路径。

### 业界依据

- **Terra（Broad Institute）以 workspace 为基本单元**：文件存于 workspace 专属存储桶，
  分析产出回写同一桶，访问权限按 workspace 共享设置统一控制（READER/WRITER/OWNER 三级）。
  OmicHub 的"四模块统一可见"本质就是 workspace 模型的 AI 化变体。
- 多组学平台的核心痛点是"数据搬运"（下载→上传→导出），统一文件空间正是消灭该环节的标准解法。
- AI 原生生物平台（2026 趋势）把"单工作区内完成解读 + 代码执行 + 多组学分析"作为核心卖点。

### 三个必须守住的实现要点

| # | 要点 | 业界教训 / 依据 |
|---|------|----------------|
| 1 | **沙盒产出必须回写工作区**：沙盒直接挂载工作区，或产出自动回写并生成 file_id | Terra 反面教材：交互式分析的持久盘 per-user 独享、协作者互不可见，workflow 结果需手动 transfer 才能给 notebook 用，是用户抱怨最多的断点 |
| 2 | **统一文件抽象层**：四个模块不得各自直连存储；云端对象存储（S3/OSS）与本地文件系统对上层透明，本地可用 MinIO（S3 兼容）兜底，一套代码两个部署形态 | 业界统一命名空间实践（本地与云存储对上层透明，消除数据孤岛） |
| 3 | **可见 ≠ 全量读取**：AI 助手对大文件（FASTQ/BAM/单细胞矩阵）只取元数据+预览（沿用 read_file 100KB 截断、二进制只读元数据的设计）；团队协作区分只读/读写角色（对标 Terra 三级权限） | 多组学数据体量决定的硬性约束；权限粒度不足会把"成员可见"变成安全隐患 |

## Part 2：给 Kimi Code 的架构审查提示词（只查不改）

```text
你是一名资深全栈架构师，任务是对 OmicHub 生信分析平台做一次架构审查。
本次只做代码级调研与评估，禁止修改任何代码；先读代码再下结论，
所有结论必须标注对应文件路径与关键代码位置。

## 审查背景

平台有一个核心设计：**用户个人空间（工作区）下的所有文件，对四个模块统一可见**：
1. AI 助手（星尘 AI 对话，含 Workspace MCP 文件工具 list_files / read_file / get_file_info）
2. AI 工作台（沙盒执行环境，Agent 在其中读写/产出分析文件）
3. 团队协作（协作室/共享空间，成员可见彼此或团队文件）
4. 生物信息工具箱（BLAST 等分析工具，直接消费工作区文件、结果回写工作区）

同时平台规划两条部署路径：**云端 SaaS 部署**与**本地私有化部署**，
同一套代码需要通过配置切换，两条路径下文件可见性设计都必须成立。

## 审查任务

### A. 统一文件可见性审查（核心）

1. 定位平台当前的文件存储与寻址实现：
   - 工作区文件的存储后端是什么（本地磁盘？对象存储？数据库记录 + 文件实体？）
   - 文件的唯一标识与寻址方式（file_id / upload://xxx / 相对路径 / 绝对路径）
   - 是否存在文件访问的统一抽象层（如 FileService / Storage 接口），
     还是各模块各自直连存储
2. 逐一核查四个模块访问工作区文件的实际路径：
   - 每个模块**通过什么方式**拿到文件（统一抽象层？直接读磁盘？HTTP 接口？MCP？）
   - 各模块看到的文件集合是否一致（同一 user 的同一目录树），
     是否存在某个模块只能看到子集、或看到的路径表示不一致的情况
   - 模块间文件流转是否闭环：AI 工作台沙盒产出的文件能否被 AI 助手 @ 引用、
     被生信工具箱作为输入、被团队成员看到
3. 权限与边界：
   - 当前各模块访问文件时有无用户级权限校验，是否存在越权读取他人空间的可能
   - 团队协作场景下"个人空间 vs 团队共享空间"的边界在代码里如何体现
   - 路径逃逸（../、绝对路径穿越）防护是否在每个模块都生效，还是只在一处做了
4. 输出一张「模块 × 能力」矩阵：每个模块 ×（列目录 / 读文件 / 写文件 /
   删除 / 权限校验点 / 寻址方式），标注已实现、部分实现、缺失。

### B. 双部署路径（云端 / 本地）就绪度审查

1. 存储层可替换性：当前文件存储是否硬编码了某一种后端
   （如写死本地路径、写死某个 OSS/S3 SDK 调用）？切换到另一种部署形态需要改多少处？
2. 云端路径缺口：多租户隔离、对象存储适配、文件元数据与实体的分离、
   沙盒容器内的文件挂载方式，目前缺哪些？
3. 本地路径缺口：纯本地文件系统运行时，哪些云端假设会失效
   （如无对象存储、无公网回调、单机部署）？
4. 配置化程度：部署形态（cloud/local）目前有没有统一的配置开关，
   还是散落在代码各处的 if-else？

## 交付格式

1. 「模块 × 能力」矩阵表（标注每格对应的代码位置）
2. 模块间文件流转链路图（文字版即可：谁产出 → 存到哪 → 谁能读到）
3. 风险与缺口清单：按严重度分级（阻断云端迁移 / 阻断本地部署 / 权限安全隐患 /
   体验不一致），每条给出代码证据
4. 建议的演进方案：先抽象统一 Storage/FileAccess 层，还是分模块补齐，
   给出你的判断和理由
5. 不做任何代码修改，只输出上述报告
```

## Part 3：Kimi Code 报告回来后的审核 checklist（供下一轮逐条核对）

重点核三块（对应 Part 1 的三个实现要点）：

- [ ] **沙盒回写闭环**：报告中的流转链路图里，"AI 工作台沙盒产出 → 工作区"这一段
      是自动回写还是断裂？产出文件有没有 file_id、能否被助手 @、被工具箱消费、被团队看到？
- [ ] **统一抽象层**：四个模块是走同一 FileService/Storage 接口，还是各自直连？
      直连的模块有几个、分别在哪？（直接决定云端/本地双路径要改多少处）
- [ ] **权限粒度**：每个模块的权限校验点是否都存在？个人空间 vs 团队空间边界是否清晰？
      AI 助手读大文件是否只到元数据/预览级？
- [ ] **双路径配置化**：cloud/local 是否有统一开关？报告是否给出 MinIO 或等效的
      本地兜底建议？
- [ ] **演进方案合理性**：Kimi Code 建议"先抽象统一层"还是"分模块补齐"，
      理由是否站得住（对照报告里直连存储的模块数量判断）
