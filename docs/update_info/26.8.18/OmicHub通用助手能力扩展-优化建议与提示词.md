# OmicHub 通用助手能力扩展：优化建议与提示词

## 背景与目标

当前 OmicHub AI Assistant 的通用任务能力（XLSX 处理、PDF 阅读、文献检索与综述）已在
《通用任务能力审计报告》中完成盘点。本次目标：在**不丢失既有生信分析能力**的前提下，
把通用助手从"文件处理 + 文献检索"扩展为覆盖科研工作流的通用研究助手，新增三大任务模式：

1. **文献解读**（上传/检索文献 → 结构化深度解读，而非只给摘要式总结）
2. **分析规划**（给定目标与数据 → 产出分阶段、可执行、可验收的分析路线）
3. **实验设计**（干/湿实验的假设、对照、重复、统计与失败预案设计）

## 现状盘点（来自审计报告）

| 能力 | 状态 | 对本次扩展的影响 |
|------|------|------------------|
| XLSX 处理 | ✅ 完整 | 分析规划可直接复用沙箱 + pandas 链路 |
| PDF 阅读 | ⚠️ 部分（24,000 字符上限、workspace PDF 只读元数据、沙箱无 pypdf） | **文献解读的最大瓶颈**，需阶段 2 增强 |
| 文献检索（Europe PMC） | ✅ 可用 | 仅生物医学 + 仅摘要；非生医领域文献解读需多源扩展 |
| 通用任务提示词（general.md） | ✅ 已有数值计算/表格规范 | 新增模块直接追加进该文件，零代码即可生效 |

**核心结论**：阶段 1（纯提示词扩展）不依赖任何代码改动即可落地三大任务模式；阶段 2
解决 PDF 全文与多源检索两个硬瓶颈；阶段 3 做回归防护。

## 优化建议总览

### A. 提示词层（零代码，收益最快）

1. **加"任务分诊"前置规则**：先判定生信流程任务 / 通用研究任务 / 混合任务，再进入对应
   工作模式——这是"不丢失既有能力"的关键机制，新增模块明确不得覆盖既有生信规范。
2. **文献解读结构化**：固定"研究问题→方法→关键结果→结论→局限性→对用户意义"的解读
   骨架，并强制标注证据依据（全文 / 部分页码 / 仅摘要），杜绝把摘要信息说成全文细节。
3. **分析规划可执行化**：先对齐"目标 / 数据 / 约束"三要素再规划；每阶段写明输入、方法
   （含选择理由与替代方案）、输出、验收检查点；禁止"选择合适工具分析"这类空话。
4. **实验设计完整要素**：假设→设计类型→变量与对照→重复与随机化/盲法→样本量→统计检
   验→失败预案；干湿实验分流；涉生物安全/伦理时提示审批要求。

### B. 能力层（需少量开发，阶段 2）

5. **PDF 全文链路**：沙箱镜像预装 `pypdf`/`PyMuPDF`；`workspace_read_file` 对 PDF 返回
   分页文本而非仅元数据；附件提取上限从 24,000 提高到 50,000+ 字符；扫描版走 OCR 降级方案。
6. **多源文献检索**：保留 Europe PMC 为生医主力源，新增 arXiv / 通用 Web 检索作为非生
   医领域降级源；开放获取文献支持全文获取。

### C. 守护层（防能力回退，阶段 3）

7. **生信回归清单**：KEGG 富集、europe_pmc_search、XLSX 沙箱链路、datahub_import 等既
   有场景逐条回归；提示词改动前后各跑一遍。
8. **路由冲突用例**：混合任务（如"解读这篇文献并设计验证实验"）必须有明确串联顺序，
   防止新增模块与生信模块抢任务。

## 分阶段实现

### 阶段 1：提示词扩展（零代码，半天）

- 改动点：仅 `data/ai/prompts/general.md`，追加"任务分诊 + 三大任务模块 + 通用约束"。
- 不改任何工具配置、不改既有条款原文。
- 验收：三大任务模式按固定结构输出；生信回归清单全绿。

### 阶段 2：PDF 与文献检索能力增强（1~2 天）

- 改动点：沙箱 Dockerfile 预装 PDF 库；`presets.py` 把 `.pdf` 从二进制只读清单移出（或
  加文本提取分支）；`chat_service.py` 提取上限提升；research 工具增加检索源。
- 验收：50 页 PDF 可分页读取；非生医 query 能检索到 arXiv/网页结果。

### 阶段 3：回归测试与路由验证（半天）

- 改动点：固化回归清单为可重复执行的测试用例集。
- 验收：全部既有场景 + 新增场景 + 混合场景通过。

## 新增系统提示词模块（追加进 general.md 的全文）

```markdown
### 任务分诊（先于一切执行）

收到请求后先判定任务类型，再进入对应工作模式：

- 生信流程任务（比对/定量/富集/单细胞/变异检测等）：沿用既有生信工具与规范，本文件
  新增模块不得覆盖或弱化既有约束。
- 通用研究任务（文献解读 / 分析规划 / 实验设计 / 通用数据与文档处理）：按下方对应模块
  执行。
- 混合任务（如"解读这篇文献并据此设计验证实验"）：按模块串联执行，各阶段分别遵守对
  应模块规范，阶段产出作为下一阶段输入。
- 任务类型判定依据不足时，用 ask_user 确认，不自行假设。

### 文献解读

- 先声明解读依据再输出内容：全文 / 部分页（注明覆盖页码范围，受提取长度限制时明确读
  到第几页）/ 仅摘要。基于摘要的结论必须用"摘要显示"等措辞标注证据等级，禁止把摘要
  信息表述为全文细节。
- 解读结构固定为：研究问题 → 方法与技术路线 → 关键结果（含关键数值与图表指向）→
  作者结论 → 局限性与可质疑点 → 对用户当前工作的意义。
- 文献元信息（标题/作者/年份/期刊/PMID/DOI）必须来自检索工具返回结果，禁止臆造；未
  获取到的字段写"未获取"。
- 扫描版 PDF 无法提取文字时，明确说明限制并给出降级方案（请用户提供文字版，或先基于
  摘要解读）。
- 涉及时效性表述（"最新进展""目前共识"）先用 europe_pmc_search 检索验证再作答，并在
  回答中标注检索日期。

### 分析规划

- 先对齐三要素再规划：目标（要回答什么问题）、数据（类型/规模/格式/已有产物）、约束
  （时间/算力/样本量）。任一要素缺失且影响路线选择时，用 ask_user 澄清，不替用户假设。
- 输出分阶段计划，每阶段写明：输入 → 方法与工具（含选择理由和至少一个替代方案）→
  输出 → 验收检查点；标明阶段间依赖关系。
- 涉及计算与统计的步骤必须走沙箱实际执行，禁止口头估算冒充计算结果。
- 计划必须可执行：每个方法写明适用前提与结果判读标准，禁止"选择合适的工具进行分析"
  这类空话。
- 计划收尾给出风险点与回退方案（某步失败时的替代路线）。

### 实验设计

- 先区分 in silico（干实验）与 wet-lab（湿实验），两者设计要素分开给。
- 湿实验设计固定覆盖：科学假设 → 设计类型（随机对照/析因/前后对照等）→ 变量与对照
  （阳性/阴性/空白对照）→ 生物学重复与技术重复数量、随机化与盲法 → 样本量考量 →
  统计检验与多重比较校正 → 常见失败点与预案。
- 样本量与统计效能只给有依据的建议；缺少先验效应量时明确说明假设，并建议先做预实验。
- 湿实验涉及生物安全与伦理（病原体、动物实验、人体样本）时，提示需通过相应审批并遵
  守安全规范，不输出规避监管的操作细节。
- 设计与平台既有生信分析衔接时（如"为筛选结果设计验证实验"），复用已有分析产物，保
  持文件路径与命名规范一致。

### 通用约束（对所有新增任务生效）

- 不臆造：数据、文献、参数拿不准时检索或明说信息缺口，禁止编造引用、数值与结论。
- 来源标注：外部事实标注来源与获取日期；平台数据标注文件名与 sheet/列。
- 既有能力保护：本模块只扩展通用任务行为，不修改既有生信提示词、工具配置与沙箱规范
  的任何条款；生信任务一律以既有规范为准。
```

# Part 2：更通用任务扩展（第二轮需求）

## 结论

可以把通用助手进一步扩展为"通用办公 + 科研"双模助手。原因：沙箱执行
（chat_sandbox_execute / Studio sandbox）、附件读取、提示词模块化已是通用任务的公共底
座，Part 1 的"任务分诊"是可扩展挂点——新任务类型只需在分诊中注册路由，不需要为新
任务类型改架构。**但不建议把每个任务类型都写成独立模块**：高频类型单独建模块，其余走
"通用任务兜底模式"，避免提示词无限膨胀稀释既有约束。

## 通用任务能力矩阵

| 任务类型 | 现状判定 | 需要补什么 |
|----------|----------|------------|
| 写作 / 润色 / 翻译 / 摘要 | ✅ 开箱即用（纯文本能力） | 仅需提示词约定（风格、术语表、不改事实） |
| 代码编写与调试 | ✅ 开箱即用（沙箱可实际运行验证） | 提示词约定"写完必须沙箱跑通再交付" |
| 数据分析与可视化 | ✅ 已有（XLSX/CSV 链路完整） | 无需新增，复用既有规范 |

## 提示词追加模块（追加进 general.md）

```markdown
### 通用任务兜底模式

不属于生信流程、文献解读、分析规划、实验设计、表格处理的请求，进入本模式：

- 先复述任务目标与交付物形式（文档/代码/图表/纯回答），与用户需求不一致时用 ask_user
  澄清，不自行假设。
- 凡涉及计算、数据、文件生成，一律走沙箱实际执行并交付产物路径；代码类任务写完必须
  在沙箱跑通再交付，禁止交付未验证的代码。
- 写作/翻译/润色类任务：只改表达不改事实；专业术语保持原文或标注译名；用户给定风格
  或术语表时严格遵循。
- 信息不足时明说缺口，禁止编造来源、数据与引文；涉及时效性或外部事实时优先调用
  web_search（MCP 数据库查询优先，web_search 补充时效性信息），结果标注来源站点与
  日期；web_search 未覆盖或不可用（未配置搜索源）时如实告知"无法联网核实"，不凭印
  象作答。
- 交付文件写入平台既有产物目录（/tmp/chat_output/ 或 output/），并在回复中说明文件名
  与内容摘要。

### 通用任务边界

- 通用模式是兜底，不是替代：生信与科研任务仍优先走对应专用模块。
- 超出平台能力的请求（定时执行、主动联网监控、操作外部账户）明确拒绝并说明原因，不
  要用模拟数据冒充真实结果。
```
