## 1. 总体架构概览

协作室的系统分为三层：

```
┌─────────────────────────────────────────────┐
│           第1层: OmicHub Platform             │
│  FastAPI (Python) + Vue 前端                  │
│  - 消息接收 / 意图路由 / Agent协调            │
│  - 知识库检索 / Domain Rules 匹配             │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│        第2层: AgentTeams Bridge               │
│  Matrix 房间管理 + Case 生命周期              │
│  - 创建工作项 (Work Items)                    │
│  - Worker 招募与调度                          │
│  - 质量门控与审批                              │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│       第3层: Agent Teams Gateway/Workers      │
│  实际 Agent 执行层                            │
│  - agent-rnaseq, agent-viz, agent-code ...   │
│  - RNAFlow Pipeline / Snakemake              │
│  - ggtree / IQ-TREE 工具调用                 │
└─────────────────────────────────────────────┘
```

### 两条编排路径

用户在协作室发起任务后，根据请求类型进入**不同路径**：

| 路径 | 触发条件 | Planner | 特点 |
|------|---------|---------|------|
| **Overdrive / LLM 规划路径** | 未命中预定义 Flow 的通用或跨域请求 | Manager 选择 Lead Planner；领域命中时选专长 Agent，否则 `agent-general` 兜底 | LLM 可生成非锚点工作项；Domain Rules 对必需任务、依赖和交付物施加约束 |
| **Bridge Workflow 路径** | 命中预定义的 `data/ai/flows/*.yaml` | Flow YAML 决定阶段和 actor；Bridge 负责把配置实例化为 Work Item | 质量/交付/解读等标准工作项 target 从 flow YAML 或 `_shared/policies.yaml` 读取，不再要求改代码 |

## 3. 两种分析路径对比

### Overdrive 路径（LLM 辅助规划）

```
用户请求
  │
  ├─→ Domain Registry 匹配（读取 domains/*.yaml 的 domain_markers 与 intake slots）
  │     data/ai/domains/omics.yaml → rnaseq-domain 规则
  │     data/ai/domains/phylo.yaml → task_type slot
  │
  ├─→ Lead Planner Selector（Domain Registry 派生的 planner hints 评分；未命中时 agent-general 兜底）
  │
  ├─→ Research Phase (知识库 + 网页搜索)
  │
  ├─→ LLM 生成 assignments (受 domain rules 约束)
  │
  └─→ Plan Builder（保留 required anchor 与依赖；通用路径可进入计划确认后再执行）
```

### Bridge Workflow 路径（配置驱动 Work Items）

```
用户请求命中 preflow
  │
  ├─→ flow YAML 中的 stages/edges 被读取
  │
  ├─→ Bridge service 按 Flow YAML / _shared/policies.yaml 创建标准 work items:
  │     quality-01 → standard_work_items.quality 或 shared default
  │     delivery-01 → standard_work_items.delivery 或 shared default
  │     interpret-01 → standard_work_items.interpret 或 flow.actor
  │
  └─→ DAG topological sort 决定执行顺序
```

## 4. 场景一：输入"帮我进行rna-seq分析"

### 4.1 关键前置判断——是否有附件？

**文件**: `execution_intent.py:63-80`

系统首先运行 `classify_execution_intent()`。执行动词存在但尚无明确对象时，不再静默降级为闲聊，而是进入 `clarify` 并发送选项式澄清卡：

| 条件 | "帮我进行rna-seq分析"(无附件) | "帮我进行rna-seq分析"+FASTQ |
|------|------|------|
| 未命中否决词 | ✅ | ✅ |
| 含执行动词("分析") | ✅ | ✅ |
| 有明确作用对象(context_refs或文件名) | ❌ | ✅ |
| **结果** | **`clarify`：追问文件/工作区路径/公共库 accession** | **`execute`：进入执行流程** |

> ⚠️ **纯文本无附件时不会启动 Case planning**。系统保留原始请求并最多追问两轮；用户补充文件名、路径、上传附件或 accession 后会带着原始目标重新判定。超出轮次则明确降级为讨论，不会静默卡住。

下面假设你附带了 FASTQ 文件或已上传的数据，进入执行流程。

### 4.2 完整执行步骤

#### Step 1: 消息接入与异步分发

**文件**: `agentteams.py:546-571`

```python
POST /cases/{case_id}/messages
  → 保存为 room.user_message 事件
  → Celery 异步任务: respond_to_room_message.delay(case_id, user_id, content)
```

#### Step 2: Manager 初始回复

**文件**: `room_response_service.py`

1. 获取 Redis 锁（防并发）
2. 获取 case 状态 + 最近 30 条消息
3. 构建 prompt（用户消息 + context_refs + 用户偏好）
4. 选择 Manager agent（优先 `agent-general`）
5. 调用 `AgentConsultationService.run_consultation(capability="interpretation")`

此步只是快速确认收到请求，如果意图检测通过，将触发 `_maybe_start_chat_execution()`。

#### Step 3: 意图路由 → 匹配 RNAFlow

**文件**: `agentteams_intent_router.py`

从 `data/ai/flows/rnaseq.yaml` 读取主路由提示：
```yaml
trigger_hints: [RNA-seq, bulk RNA, 差异分析, RNAFlow]
actor: agent-rnaseq
bridge_workflow: rna_seq
```

`data/ai/domains/*.yaml` 中声明的 `routing.flow_aliases` 会由 `DomainRegistry` 派生为补充别名；新领域优先只改 YAML。旧 `_LEGACY_EXTRA_HINT_ALIASES` 仅保留兼容兜底并会输出弃用日志。

判定结果: `IntentRoute(flow_id="rnaseq", lead_planner="agent-rnaseq")`，随后 `room.route_decision` 会把该结果外显到消息流。

#### Step 4: Domain Registry 匹配

**文件**: `domains/omics.yaml:60-65`

```yaml
assignments:
  rules:
    - id: rnaseq-domain
      when_message_markers: [bulk, rna-seq, 转录组, 表达矩阵]
      agent_match: [agent-rnaseq, rna-seq 分析师]
      task_id: domain-analysis
```

同一份 Domain YAML 的 `routing.planner_agent` + `match.domain_markers` 会派生为 Planner 评分关键词；`overdrive_planning_service.get_domain_hints()` 只在未迁移的旧 Agent 上使用硬编码兼容表。

#### Step 5: 研究阶段 (Research Phase)

LLM 收集：
- 平台 RNA-seq 知识库中的最佳实践
- 网络上的最新方法/数据库版本
- 模型通用知识

#### Step 6: Plan 构建与 Case 创建

**文件**: `chat_service.py:3903` / `agentteams_service.py`

Plan Builder 组装 enriched_tasks 并创建 Case Payload：
```python
{
    "case_id": "bioops_<uuid>",
    "intent": "帮我进行rna-seq分析",
    "execution_mode": "cluster_case",
    "flow_id": "rnaseq",
}
```

创建 Matrix 房间并配置参与者。

#### Step 7: Agent 编排执行

##### A. RNAFlow Pipeline 的实际两步 (YAML 定义)

**文件**: `data/ai/flows/rnaseq.yaml:17-41`

```yaml
stages:
  - key: quantify                # Stage 1: 定量与质控
    executors:
      - key: rnaflow
        queue: rnaseq_analysis
        resource_profile: standard_8c32g
        inputs: [fastq_manifest]
        outputs: [quant_counts]

  - key: differential            # Stage 2: 差异表达与审查
    executors:
      - key: deseq2
        queue: rnaseq_analysis
        inputs: [quant_counts]
        outputs: [de_results]
    review:
      skill: de-review
      output: de_review
    gate: {template: annotation_revision, required: true}

edges: [[quantify, differential]]

thresholds:
  mapping_rate: 0.70    # 比对率 ≥ 70%
  q30: 0.80             # Q30 ≥ 80%
  duplicate_rate: 0.50  # 重复率 ≤ 50%
```

##### B. 底层 Snakemake 流水线的真实子步骤

**文件**: `pipelines/RNAFlow/src/src/` 下的脚本

```
MD5 校验 → FastQ Screen(污染筛查) → 文库方向检测
    ↓
RSEM 基因级定量 (STAR+RSEM 或 Salmon准比对)
    ↓
DEG 差异分析 (DESeq2) + 热图/PCA 可视化
    ↓
富集分析 (GO/KEGG/GSEA)
    ↓
可选: rMATS 可变剪接分析
    ↓
HTML 报告生成 + 产物打包交付
```

##### C. Agent Teams 层面的 Agent 参与

由于走的是 workflow-execution 路径，Bridge service 硬编码添加了以下工作项：

| Work Item | Target | 谁执行 | 来源 |
|-----------|--------|--------|------|
| plan-01 | agent-rnaseq | agent-rnaseq | dynamic (Lead Planner) |
| preflight-01 | data-steward | agent-data | hardcoded |
| quality-01 | quality-auditor | agent-qc | hardcoded |
| interpretation-01 | interpretation_target | agent-rnaseq | lookup |
| delivery-01 | delivery-reporter | agent-delivery | hardcoded |

Agent Teams Worker 注册表中可用的人员：

| Agent | 角色 | Skills |
|-------|------|--------|
| **agent-rnaseq** | 主规划者 + RNAFlow 执行专家 | rnaflow, deg, enrichments, wgcna, rmats |
| **agent-data** | 数据预检 | project-preflight, evidence-retrieval |
| **agent-qc** | 质量门控 | quality-gate, artifact-inspect |
| **agent-viz** | 可视化 | visualization-review, figure-specification |
| **agent-code** | 代码生成/调试 | code-review, reproducibility-advice |
| **agent-delivery** | 产物交付 | delivery-pack, runbook-capture |

## 5. 场景二：输入"帮我进行系统发育树和解读"

### 5.1 与 RNA-seq 的核心区别

| 维度 | RNA-seq | 系统发育树 |
|------|---------|-----------|
| 预定义 Flow | `data/ai/flows/rnaseq.yaml` ✅ 存在 | `data/ai/flows/treeplot.yaml` ✅ 存在（但更简单） |
| Domain Rules | `data/ai/domains/omics.yaml` 复杂规则 | `data/ai/domains/phylo.yaml` 带 intake 问答 |
| Slot 分类 | 仅一个 `domain-analysis` 任务 | **两类互斥分支**: `tree_visualization` vs `phylogeny_construction` |
| 强制锚点 | 无 | homolog-search → phylogeny-build 两锚点依赖链 |
| LLM 自由度 | 较低（受 2 stage 限制） | 中等（可拆分/重组 sub-tasks，但锚点不可变） |

### 5.2 意图检测

与 RNA-seq 相同的路径：`detect_execution_intent()` 检查执行动词 + 作用对象。

关键词匹配来自 `data/ai/domains/phylo.yaml` 的 domain_markers：
```yaml
domain_markers:
  - 系统发育
  - 进化树
  - phylogenetic
  - 建树
  - 进化分析
  - 序列比对
  - 同源序列
  - treefile
  - treeplot
  - ggtree
  ...
```

"系统发育"和"建树"都在列表中，Domain Registry 命中 `phylo` 域。

### 5.3 Slot 分类——两种互斥路径

这是系统发育任务的关键分支点：

```
检测到 domain_marker ∈ phylo_markers
         │
    ┌────▼──────────────────────────────────┐
    │ Slot 匹配 task_type                    │
    │                                        │
    │ 命中 markers: [已有树, 美化, treeplot] │ → task_type = tree_visualization
    │ 命中 markers: [建树, 进化分析, 建树]   │ → task_type = phylogeny_construction
    └────┬──────────────────────────────────┘
```

#### 分支 A: tree_visualization（处理已有树）

```yaml
# phylo.yaml:99-104
rules:
  - id: tree-viz-only
    when_slot_is: {task_type: tree_visualization}
    minimize_to_single: true      # 只分配一个 Agent
    agent_match: [agent-viz]
    task_id: tree-visualization
    task: "处理已有系统发育树文件...不要重新建树"
```

**Agent**: 仅 `agent-viz`（最小化到单个 Agent）

#### 分支 B: phylogeny_construction（从头建树）— 你问的场景

这里有 **两个权威锚点（authoritative anchors）**：

```yaml
# phylo.yaml:105-129
rules:
  - id: homolog-search
    when_slot_is: {task_type: phylogeny_construction}
    authoritative: true
    required: true
    allow_split: true             # 可按基因组分片
    allow_reorder: false          # 不可重排
    agent_match: [agent-code]
    task_id: tnpd-homolog-search
    task: "验证 TnpD 查询序列与 20 个基因组输入，逐基因组检索并提取同源候选"

  - id: phylogeny-build
    when_slot_is: {task_type: phylogeny_construction}
    authoritative: true
    required: true
    allow_split: false            # 不可拆分
    allow_reorder: false          # 不可重排
    depends_on: [tnpd-homolog-search]  # ← 硬依赖！
    agent_match: [agent-viz]
    task_id: tnpd-phylogeny
    task: "对筛选后的序列做多序列比对，选择替换模型构建带支持度评估的系统发育树"
```

```
    │    任务: MSA比对 → 模型选择 → IQ-TREE建树          │
    │    输入: 候选同源序列 FASTA                         │
    │    输出: Newick/treefile + 节点支持度 + 进化树      │
    │                                                   │
    │  【Bridge 配置化附加】                              │
    │  quality-01 → flow/shared policy 声明的质量身份     │
    │  delivery-01 → flow/shared policy 声明的交付身份    │
    │  interpretation-01 → flow 声明值，缺省时使用 actor  │
    │                                                   │
    │  底层工具链:                                       │
    │  Diamond/HMMER → MAFFT 比对 → IQ-TREE 模型测试    │
    │  → IQ-TREE ML建树 (1000 ultrafast bootstraps)     │
    │  → ggtree 可视化渲染                               │
    └──────────────────────────────────────────────────┘
```

### 5.5 Branch A vs Branch B 对比

## 6. 固定 vs 动态：流程有多大自由度？

### 固定部分 🔒

| 层级 | 具体内容 | 文件位置 |
|------|---------|---------|
| Flow YAML 的阶段数 | RNA-seq 固定 2 stage，TreePlot 固定 1 stage | `data/ai/flows/*.yaml` |

| Capability Registry | 主 Agent 不可用时，按配置 `fallback_agents` 顺序解析；链路耗尽显式等待资源 | `agentteams_capability_registry.py`、`data/ai/*.yaml` |
| Domain Assignment Anchors | phylo 的两个 anchor 是 `required: true` + `allow_reorder: false` | `phylo.yaml:107-108, 119-121` |

### 动态部分 🟢

| 层级 | 具体自由 | 文件位置 |
|------|---------|---------|
| Lead Planner 选择 | 按 Domain Registry 派生的关键词评分；无专长命中时 `agent-general` 兜底 | `overdrive_planning_service.py` |

### 中间地带 🟡

| 层级 | 限制 | 自由度 |
|------|------|--------|
| DAG 拓扑排序 | 依赖方向不可逆 (`allow_reorder: false`) | 时间上允许并行 |

## 7. 关键判断逻辑——意图检测

**文件**: `src/omichub/application/services/agentteams_execution_intent.py`

```python
def classify_execution_intent(content: str, context_refs: list[dict]) -> ExecutionIntent:
    """将消息分类为 execute / tool_execute / clarify / chat。"""
    if hit_veto_pattern(content) or not has_execution_verb(content):
        return ExecutionIntent.CHAT
    if not has_explicit_object(content, context_refs):
        return ExecutionIntent.CLARIFY
    if is_readonly_tool_request(content):
        return ExecutionIntent.TOOL_EXECUTE
    return ExecutionIntent.EXECUTE
```

| 结果 | 行为 |
|------|------|
| `execute` | 有执行动词和明确作用对象，启动 planning / Case 执行链路 |
| `tool_execute` | 只读检索、查看或复核，进入受控工具会诊，不启动 Case planning |
| `clarify` | 有执行意图但缺对象，发送可选答案的澄清卡，并在补全后重新判定 |
| `chat` | 咨询、寒暄、否决词命中或没有执行动词，保留普通对话 |

`detect_execution_intent()` 仍保留为兼容布尔适配层，只有 `execute` 时返回 `True`；新调用方应使用上述四态接口。

## 8. 路由可见性与故障恢复

### 8.1 路由决策卡

意图判定完成后，`AgentTeamsRoomResponseService` 会写入 `room.route_decision` 事件，并同步记录结构化日志。前端将高置信结果渲染为可展开卡片，显示：路径、Flow、命中提示、Lead Planner、评分、预计阶段与参与 Agent。

当多个 Flow 的评分并列时，事件标记为 `confidence=ambiguous`；前端升级为选项式确认而不是阻塞弹窗。若某个 Agent 的 fallback 链已耗尽，决策会带上 `resource_status=waiting`，避免给用户“已派发”的错误印象。

### 8.2 Work Item 状态与恢复

Bridge 将 Work Item 生命周期持久化为 `pending`、`claimed`、`running`、`completed`、`failed`、`skipped`、`timeout` 等状态。运行中的任务通过租约和心跳巡检：Worker 失联时，未耗尽预算的任务按 backoff 回收重派；预算耗尽后标记 `timeout`，其下游依赖被级联标记为 `skipped`，并向房间写入可见事件。

服务重启后从持久化 Case 恢复，只重新派发未完成的 Work Item；已完成前置节点及其产物不会重复执行。Manager 可以将失败、超时或跳过的节点手动重置到 `pending` 进行一次新的重试周期。
