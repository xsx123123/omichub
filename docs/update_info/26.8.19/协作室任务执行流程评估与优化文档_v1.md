## 1. 背景与评估范围

用户针对流程文档提出四点判断：

1. 两条编排路径（Overdrive / Bridge Workflow）对用户不可见，建议加"模式切换提示"（弹窗）；
2. 已定义的 domain 规则（omics / phylo）之外的**通用分析需求**（如"处理 xlsx → 基因文献检索 → 输出文档 + 网页报告"），当前框架能否处理；
3. 获得需求后，是否由特定领域专业助手创建 plan 并派发给不同 Agent 执行；
4. 通审全文，找出框架可优化点。

评估依据：流程文档描述的组件与行为 + 业界主流 Agent 产品的交互约定（Cursor Plan Mode、Gemini Deep Research、ChatGPT Agent、Devin/Genspark 等）。

> ⚠️ 注意：本评估基于流程文档而非源码逐行核对。文档中的文件路径与行号（如 `service.py:434-505`）可能与当前代码漂移，实施提示词中已要求编码 Agent **先读代码验证再动手**。

## 2. 四点判断的评审结论

### 2.1 点一：路径可见性 —— ✅ 成立，但不用阻塞式弹窗

**用户判断**：发起任务后进入不同路径，应加模式切换提示（弹窗）告知用户。

**Verdict**：缺口判断正确，交互形式需要修正。

**依据**：

- 缺口真实存在：两条路径的 Planner（LLM vs 硬编码）、自由度、参与 Agent、质量门控差异显著，用户完全无法感知自己的请求走了哪条路、由谁规划、会经过哪些阶段。
- 但业界约定不是弹窗：主流 Agent 产品采用"思考外显（Think-Aloud）+ 非阻塞状态/计划卡片"——Cursor Plan Mode 用 `Shift+Tab` 切换模式并在执行前展示可编辑的计划文件；Gemini Deep Research 先给任务拆解方案并提供"修改方案"按钮；ChatGPT Agent 把操作步骤实时显示在屏幕上；Devin/Genspark 用进度条/步骤锚点展示分解步骤。[^2^][^5^][^6^] 共同特征：**可见、可干预、不打断**。阻塞式弹窗违反"注意力引导"原则，高频任务下每次弹窗会成为噪音。[^2^]

**修正后的方案**（详见 §3 优化项 O1）：

- 默认形态：**路由决策卡**（内嵌消息流的卡片，非弹窗），展示：命中路径、命中的规则/关键词、Lead Planner、预计阶段列表、涉及 Agent；可点击展开详情，可折叠。
- 弹窗仅在两种情形升级使用：① 路由模糊（多个 flow 评分接近，需要用户裁决）；② 即将进入高成本/长耗时执行（用户确认后才启动）。

### 2.2 点二：通用分析需求 —— ✅ 判断基本正确："能走通，但走不稳"

**用户判断**：除已定义的领域（omics/phylo）外，现阶段的通用分析需求（处理 xlsx + 文献检索 + 输出文档/网页报告），框架是否能够处理？

**Verdict**：框架骨架理论上能承载（通用 Overdrive 路径 + agent-general），但存在三个断点，实际可靠性低，需要补"通用分析域"。

**按文档逐环节推演**（以"帮我处理这个 xlsx，对其中描述的基因做文献搜索，整理成文档并输出网页报告"为例）：

| 环节 | 推演结果 | 断点 |
|------|---------|------|
| 意图检测 `detect_execution_intent()` | 有附件 → context_refs ✅；但执行动词表为"分析\|运行\|执行\|跑\|可视化\|绘图\|画"，"处理/搜索/整理"**未必命中** | ⚠️ 断点 1：可能连执行模式都进不去，被降级为咨询模式 |
| Domain Registry 匹配 | xlsx 处理、文献检索不命中 omics/phylo 的任何 message_markers | 落入无 domain rules 约束的通用路径 |
| Lead Planner 选择 | DOMAIN_HINTS 无通用任务关键词，评分最高者大概率是 agent-general（通才） | 无领域专家护航 |
| LLM assignments | 无 domain rules 约束 = 无锚点、无 required 任务、无顺序保证 | ⚠️ 断点 2：计划质量完全靠 LLM 自由发挥，同类请求两次执行可能产出完全不同的计划，不可复现 |
| Work Item 创建 | 不命中任何 preflow → 无 Bridge 硬编码工作项 → 无质量门控、无交付节点 | ⚠️ 断点 3：文献检索可勉强挂 agent-data（evidence-retrieval），但"文档生成""网页报告"没有对应 deliverable 定义与负责 Agent |
| 质量与交付 | 无阈值门控、无 delivery-reporter 兜底 | 产物可能散落在对话里，无打包交付 |

**结论**：不是"能不能"的问题，是"裸奔还是有护栏"的问题。需要补一个**通用分析域（general domain）**：通用锚点（file-processing → literature-search → report-generation）、交付物类型定义（docx / html report）、以及对应的轻量质量门控。详见 §3 优化项 O2。

### 2.3 点三：领域专家规划 + 派发 —— ✅ 大体正确，两个修正

**用户判断**：获得需求后，使用特定领域的专业助手进行 plan 创建，并基于 plan 将任务发送给不同 Agent 干活。

**Verdict**：主链条正确（Lead Planner Selector 按 DOMAIN_HINTS 选领域专家 → LLM 在 domain rules 约束下生成 assignments → Bridge 派发 work items 给各 Agent），但有两个必要修正：

- **修正一：只在 Overdrive/LLM 路径完整成立。** Bridge Workflow 路径中，quality-01 / delivery-01 / interpretation-01 的 target 是 Bridge service 硬编码的（`service.py:434-505`），plan 更像"模板组装"而非"专业助手规划"；真正由 Lead Planner 决策的只有 plan-01 等动态工作项。
- **修正二：通用请求没有领域专家可匹配时，落到 agent-general（通才）规划**，而不是"特定领域专业助手"。这与点二断点 2 是同一缺口的两个侧面——补通用分析域后，通用请求也能获得"半个专家"级的锚点约束。

### 2.4 点四：框架级优化点汇总

除用户提出的三点外，通审文档还可读出以下优化点（详见 §3）：

| # | 优化点 | 现状问题 | 严重度 |
|---|--------|---------|--------|
| O4 | 关键词规则三处分散维护 | `domains/*.yaml` 的 message_markers、`overdrive_planning_service.py` 的 DOMAIN_HINTS、`intent_router` 的 _EXTRA_HINT_ALIASES 是三份真相源，新增领域需三处手工同步（平台已有"白名单漏配 scrna"的同类事故先例） | 高 |
| O5 | Bridge work item target 硬编码 | quality/delivery/interpret 的 target 写死在 `service.py:434-505`，新增流程必须改代码，与 YAML 配置化方向（2026-08-02 方案）冲突 | 高 |
| O6 | 意图检测三条件过刚 | 无附件纯文本一律降级咨询模式；"有执行意图但缺作用对象"没有中间态（phylo 的 intake questions 机制没有推广到全局） | 中 |

## 3. 优化项详单

### O1 路由决策卡（对应用户点一）

**现状**：两条路径的决策过程（意图路由结果、domain 命中、Lead Planner 评分）只存在于服务端日志，前端无感知。

**目标**：让路径决策"可见、可干预、不打断"。

**Spec**：

1. **后端**：在 `room_response_service` 的回复回路中，意图路由完成后把路由决策结构化为一个 `room.route_decision` 事件，字段：
   ```json
   {
     "path": "overdrive | bridge_workflow",
     "flow_id": "rnaseq | treeplot | null",
     "matched_hints": ["RNA-seq", "差异分析"],
     "lead_planner": "agent-rnaseq",
     "planner_scores": {"agent-rnaseq": 4, "agent-general": 1},
     "estimated_stages": ["quantify", "differential"],
     "confidence": "high | ambiguous"
   }
   ```
2. **前端**：消息流内嵌"路由决策卡"（非弹窗）：
   - 折叠态一行：路径图标 + `已选择「RNA-seq 标准流程」· 规划者 agent-rnaseq · 预计 2 个阶段`；
   - 展开态：命中关键词、Planner 评分明细、预计阶段与参与 Agent 列表；
   - 视觉风格与平台现有卡片体系一致，复用现有消息卡片组件，不新增独立样式体系。
3. **升级弹窗仅两情形**：`confidence=ambiguous`（多个 flow 评分接近，给出选项让用户裁决，用选择代替输入）；或预计执行为高成本长耗时任务（确认后才创建 Case）。
4. 决策数据同时写入日志（供 O9 可观测性使用）。

**验收**：发送"帮我进行rna-seq分析"+附件，消息流出现路由决策卡且信息与后端日志一致；发送模糊请求（如"帮我分析这个数据"）时出现选项式确认。

### O2 通用分析域（对应用户点二）

**现状**：domain 覆盖只有 omics / phylo 等垂直领域，通用任务无锚点、无交付物定义、无质量门控。

**目标**：让"处理文件 + 文献检索 + 产出报告"类通用需求获得与领域任务同级的护栏，但不引入垂直领域的重流程。

**Spec**：

1. 新增 `data/ai/domains/general.yaml`：
   ```yaml
   domain: general
   domain_markers: [文献, 检索, 整理, 汇总, 报告, 表格, xlsx, excel, csv, 文献综述, 网页报告, literature]
   assignments:
     rules:
       - id: file-processing
         when_slot_is: {has_structured_file: true}
         authoritative: true
         required: true
         allow_split: false
         allow_reorder: false
         agent_match: [agent-data, agent-code]
         task_id: general-file-processing
         task: "解析用户提供的结构化文件，提取核心实体（如基因列表）并输出结构化清单"
       - id: literature-search
         when_message_markers: [文献, 检索, literature, 综述]
         authoritative: true
         required: false          # 仅在用户要求文献时激活
         depends_on: [general-file-processing]
         agent_match: [agent-data]
         task_id: general-literature-search
         task: "对提取的实体做文献检索，输出带来源引用的证据表"
       - id: report-generation
         when_message_markers: [报告, 文档, 整理, 网页, report]
         authoritative: true
         required: false
         allow_reorder: false
         agent_match: [agent-delivery, agent-viz]
         task_id: general-report-generation
         task: "将分析结果整理为交付文档与（可选）网页报告"
   ```
2. 交付物类型注册：docx 文档、html 报告纳入 deliverable 类型库（复用 `_shared/artifact_types.yaml` 思路，见《Multi-Agent流程YAML配置化设计方案》）。
3. 执行动词表扩充：`处理|整理|汇总|检索|搜索|生成|制作|导出` 加入 `_EXECUTION_VERB_PATTERN`（修断点 1）。
4. `DOMAIN_HINTS` 增加 agent-general 的通用任务关键词（与 general.yaml 同源生成，见 O4）。
5. 轻量质量门控：报告类交付前由 agent-qc 做"引用完整性 + 文件可打开"检查（不重写垂直领域的阈值门控）。

**验收**：上传含基因列表的 xlsx 并说"对里面的基因做文献检索，整理成文档和网页报告"，系统进入执行模式、plan 含 file-processing → literature-search → report-generation 三段锚点且顺序正确、最终产出打包交付。

### O3 规划者角色的事实澄清（对应用户点三，文档向修正）

不改代码，改《协作室任务执行流程详解》文档表述：

- 明确区分两条路径中"plan"的不同含义：Overdrive = Lead Planner 决策 + LLM assignments；Bridge = 模板组装 + 硬编码工作项；
- 明确通用请求的规划者是 agent-general（通才），避免"所有请求都有领域专家"的误解；
- 在"两条编排路径"表格中增加一行"规划主体"。

### O4 关键词规则单一真相源

**现状**：领域关键词散在 `domains/*.yaml`（message_markers）、`overdrive_planning_service.py:817`（DOMAIN_HINTS）、`agentteams_intent_router.py`（_EXTRA_HINT_ALIASES）三处。

**Spec**：domains/*.yaml 为唯一声明处；启动时由 Registry 解析后**派生注册**到 DOMAIN_HINTS 与 intent 路由别名表（沿用《Multi-Agent流程YAML配置化设计方案》第 1 节"YAML 是唯一的注册入口"的派生注册机制，不另造轮子）。代码中的硬编码关键词表删除，改为从 Registry 读取。

**验收**：新增一个 domain yaml（不改任何 .py）后，意图路由与 Planner 评分同时生效。

### O5 Bridge 工作项 target 配置化

**现状**：quality-01 / delivery-01 / interpret-01 的 target 写死在 `service.py:434-505`。

**Spec**：把这三类标准工作项的 target 声明迁移到 flow YAML（如 `standard_work_items:` 段），Bridge service 改为读配置创建；默认 target（quality-auditor / delivery-reporter）收敛到 `_shared/policies.yaml`。与 O4 同属"配置化收敛"，复用既有 schema 设计。

**验收**：新流程 YAML 声明标准工作项后无需改 service.py 即可调度。

### O6 意图检测增加"澄清中间态"

**现状**：三条件门控是二元的——要么执行、要么咨询式回复；"有执行动词但无作用对象"被一刀切降级。

**Spec**：意图检测结果从 bool 改为三态：`execute / clarify / chat`。`clarify` 态复用 phylo 域已有的 intake questions 机制（推广为全局能力）：含执行动词但缺作用对象时，Manager 用选项式追问（"请问数据来源是？① 上传文件 ② 选择工作区已有数据 ③ 公共数据库"），用户补全后自动转 execute。否决词逻辑不变。

**验收**：发送"帮我做差异分析"（无附件）→ 收到选项式澄清而非纯文本闲聊；补全后进入执行。

### O7 Capability Registry fallback 链

**现状**：`capability_registry.py:272` role→agent 一对一静态映射。

**Spec**：映射值从单 agent 改为有序列表 `role: [primary, fallback1, fallback2]`；分配时按可用性/负载取第一个健康实例；全部不可用时在路由决策卡上显式提示"等待资源"而非静默失败。

### O8 通用路径执行前计划确认

**现状**：Overdrive 路径 LLM 生成 assignments 后直接创建 Case 执行。

**Spec**：对齐业界 Plan Mode 约定——LLM 生成 plan 后先输出"计划预览卡"（阶段列表、每阶段负责 Agent、预计产物），用户可确认/修改（增删非 required 任务）/取消；确认后才创建 Matrix Case。Bridge 路径流程固定，可仅在卡片中展示不强制确认（或提供 N 秒倒计时自动确认）。

### O9 路由与规划可观测性

**现状**：路由决策、domain 命中、planner 评分无结构化记录。

**Spec**：O1 的 `route_decision` 事件 + planner 评分明细落日志，可在会话日志排查页查看（衔接《会话日志排查-可观测性评估与优化计划》）。

## 4. 分阶段实施方案

| 阶段 | 内容 | 优化项 | 依赖 | 预期收益 |
|------|------|--------|------|---------|
| 阶段 R | 故障恢复与断点续跑（状态机 + 心跳 + 重试/级联跳过） | O10 | 衔接 8-06 调度优化方案 | 补齐最大鲁棒性短板（v1.1 前置） |
| 阶段 0 | 路由决策卡（后端事件 + 前端卡片） | O1 | 无 | 用户感知路径，立竿见影；同时是 O8 的载体 |
| 阶段 1 | 通用分析域 + 执行动词扩充 | O2 | 无 | 通用需求从"裸奔"变"有护栏" |
| 阶段 2 | 意图检测三态化 + 澄清中间态 | O6 | 无（复用 phylo intake 机制） | 减少"该执行却在闲聊"的误判 |
| 阶段 3 | 配置化收敛（关键词单源 + Bridge target 配置化 + fallback 链） | O4/O5/O7 | 衔接 8-02 YAML 配置化方案 | 消灭三处手工同步，新增领域零改码 |
| 阶段 4 | 计划预览确认 + 可观测性 | O8/O9 | 阶段 0（卡片载体） | 执行前可干预，对齐 Plan Mode 业界约定 |

**v1.1 优先级修订**：鲁棒性相关项前置——阶段 R（故障恢复）与阶段 0/1/2 并行启动且优先级最高；阶段 2（三态意图）与阶段 3（配置化收敛 + fallback 链）同属鲁棒性补课，不应排在纯体验优化之后。即推荐执行序：**R ∥ 0 ∥ 1 → 2 → 3 → 4**。理由见 §7：当前框架"设计内的鲁棒"已不错，短板全部集中在"设计外的鲁棒"（故障、降级、漂移、通用、错误输入），越早补收益越大。

**v1.3 优先级修订**：阶段 H 与阶段 R 同级最优先（**R ∥ H ∥ 0 ∥ 1**）——"Manager 说了交接但实际没派发"是信任级缺陷，比体验问题更伤用户；且阶段 H 不动调度骨架、只加事件与检查门禁，改动面小。阶段 5 是本轮用户核心目标（多 Agent 协调）的主链路，排在 H 之后；阶段 6 依赖阶段 5 产生的真实 work item 事件流。

## 6. 鲁棒性专项评估（v1.1 新增）

### 6.1 总判断：设计内的鲁棒不错，设计外的鲁棒还没建

当前框架的鲁棒性要分两层看，不能笼统说"鲁棒性不错"：

**设计内的鲁棒（已比较扎实）**——请求落在已定义领域、所有 Agent 健康、配置无漏配时：

- **流程结构鲁棒**：锚点机制（`required: true` + `allow_reorder: false`）保证关键步骤不可被 LLM 跳过或乱序，phylo 的同源检索→建树依赖链是硬约束；
- **质量鲁棒**：阈值门控（mapping≥70%、Q30≥80%、Dup≤50%）+ 人工审核 gate，不合格结果不会静默通过；
- **意图误判有兜底**：三条件门控 + 否决词，宁可降级为咨询也不乱启动 Agent。

**设计外的鲁棒（明显不足）**——故障、降级、漂移、通用任务、错误输入五个方向：

### 6.2 五大短板详单

| # | 短板 | 具体表现 | 对应优化项 | 严重度 |
|---|------|---------|-----------|--------|
| R1 | 故障恢复能力缺失 | 流程文档完全未定义：任务失败/超时怎么办、能否断点续跑、Agent 崩溃后 work item 如何重派。8-06 调度优化方案要补的"状态机 + 心跳 + 重试/级联跳过"恰好印证这块当时就是缺失的 | **O10（新增）** | 🔴 最高 |
| R2 | 无降级路径 | Capability Registry 一对一静态映射，某 Agent 不可用/满载时任务只会卡住或失败，没有 fallback 链 | O7 | 🟠 高 |
| R3 | 配置漂移风险 | 关键词三处手工同步，漏配一处路由静默失效（已有 scrna 白名单漏配事故先例）；Bridge target 硬编码意味着改配置要动代码，动代码就引入回归风险 | O4 / O5 | 🟠 高 |
| R4 | 通用路径无护栏 | "裸奔"本质是鲁棒性问题：同类请求两次执行计划可能完全不同，出错时没有任何锚点能兜住 | O2 | 🟡 中 |
| R5 | 错误输入吸收能力弱 | 意图检测二元门控，用户表达不完整时只能整体降级为闲聊，没有"澄清后继续"的弹性恢复 | O6 | 🟡 中 |

### 6.3 O10 故障恢复与断点续跑（新增优化项）

**现状**：执行链路无状态机、无心跳、无失败策略定义——一个 stage 挂掉，整条链的命运未定义。

**Spec**：

1. **任务状态机**：work item 全生命周期状态（pending / assigned / running / succeeded / failed / skipped / timeout），迁移全部落库，崩溃后可从最后一致状态恢复；
2. **心跳监控**：running 任务定期心跳，超时失联按策略处置：重试（`max_attempts` + backoff，沿用 8-06 方案 DAG schema 的 retry/timeout 字段）→ 超限后**级联标记下游 skipped 并显式告知用户**，禁止静默卡死；
3. **断点续跑**：恢复时复用已落盘产物（产物即文件原则），已成功的前置 stage 不重复执行；
4. **崩溃重派**：Worker 失联 → 任务回收回 pending → 结合 O7 fallback 链重派；
5. **全程可见可干预**：失败/重试/跳过/恢复均产生房间状态消息，用户可终止或手动重试。

**与既有文档的关系**：本项是 8-06《OmicHub多Agent调度优化方案》"状态机 + 心跳 + 失败恢复"在协作室链路的落地执行项，schema 与策略默认值复用该方案，本文不重复定义。

### 6.4 优先级结论

鲁棒性补课（R1→O10、R2→O7、R3→O4/O5、R4→O2、R5→O6）整体优先于纯体验优化（O1/O8/O9 可并行但不抢占资源）。推荐执行序已按此修订进 §4：**R ∥ 0 ∥ 1 → 2 → 3 → 4**。

## 7. Agent 引擎分级评估（v1.2 新增）

> 评审对象：《agent引擎选型与优化建议.md》（2026-08-18，16 个 Agent 引擎现状盘点 + LangGraph vs Direct 选型矩阵）。
> 评审问题："是不是应该将所有 Agent 升级为 LangGraph？"

### 8.1 评审结论（Verdict）

**不应该全部升级。** 被审文档自身结论（§5.1"不建议一刀切"，按任务复杂度分级 Level 0~3）方向正确，予以确认；真正的收敛目标是"**统一接口、分级引擎**"，而不是"**统一引擎**"。

**三重依据**：

1. **业界约定明确反对一刀切**。Anthropic 工程指南原则："找尽可能简单的方案，只在必要时增加复杂性"，框架会增加抽象层、掩盖底层 prompt 与响应 [^1^]；LangChain/LangGraph v1.0 官方选型指南：标准 Agent 循环用 `create_agent`，只有"确定性与智能体步骤混合、长时运行、敏感流程需人工监督、高度自定义、延迟/成本需精细控制"才下沉到 LangGraph [^2^]；LangGraph 官方定位是"低层级编排运行时，不抽象 prompt 与架构" [^3^]。
2. **逐个评估，真正必须升级的只有 1 个**（详见 8.2）。
3. **全升级背离目标状态**。被审文档 Phase 4 的目标是 OverdriveRunService 统一编排入口 + 标准化 Engine Interface（引擎可插拔）——这与 Anthropic Managed Agents 的设计哲学一致："虚拟化 Agent 组件，接口比实现长寿" [^4^]。全部锁死 LangGraph 等于放弃 Level 0 任务的低延迟/低成本优势和未来换引擎的自由。

### 8.2 现状盘点与逐 Agent 结论

**现状**：16 个 Agent 中 11 个已是 LangGraph（~73%），核心分析域（rnaseq / scrna×4 / atacseq / qc / data / delivery / general）全部在 LangGraph 组——**该上的都已经上了**。

> ⚠️ 被审文档小瑕疵：§1.3 标题与占比写"非 LangGraph 4 个"，表格实际列了 5 行（viz / code / skill-builder / orchestrator / shania），建议原文顺手修正。

| Agent | 结论 | 理由要点 |
|-------|------|---------|
| **orchestrator** | 🔴 **P0 必须升级** | 控制面核心，职责即拆 DAG + plan confirmation，天然是图问题；却是全局唯一既无 engine 又无 managed_prompt 的 Agent，是最大的不一致点 |

## 9. 单细胞 Case 交接真实性与多 Agent 协调专项（v1.3 新增）

> 输入材料：《AgentTeams 单细胞 Case 交接与完成通知问题调查》（源码级核查，含文件路径与行号证据）。
> 场景：用户在协助室发起小鼠单细胞分析（C57BL/6、mm39、已有 Cell Ranger/STARsolo 产物），Manager 输出完整分析方案并列出 4 个专项 Agent（agent-scrna-upstream / agent-scrna / agent-scrna-integration / agent-scrna-advanced），但 Case 停在 `received`，用户从回复语气中感觉"已要转接给其他 Agent"。
> 用户核心目标：**Manager 能协调多个专项 Agent 一起干活，并且过程真实可见。**

### 9.1 两个用户判断的 Verdict

**判断一："Manager 回复让我感觉要转接，但实际没派发"——✅ 成立，且比预想更严重。**

不只是"还没派发"，而是当前链路**结构性不可能派发**：

- 聊天规划入口 `start_chat_planning` 只创建一个只读工作项 `{work_item_id: "plan-01", target: "agent-code", skill_name: "planning_advice", read_only: true}`（`agentteams_service.py:630-640`）——规划目标是 agent-code，不是任何单细胞 Agent；
- Bridge reconcile 逻辑对无 `flow_id` 的聊天 Case 跳过自动 planning，没有 plan-01 时甚至会从 `planning_running` 退回 `received`（`chat_case_skips_auto_planning`，bridge `service.py:334-352`）；
- 全程没有 `work_item.assigned / claimed / running` 事件，没有任何专项 Agent 的中间产物。

即："Manager 在房间里说了一份规划文本"与"Bridge 创建了一个可执行 Flow Case"是两条互不相通的链路。

**判断二："单细胞流程应该由单细胞 Agent 来生成，而不是 Manager"——✅ 方向正确，需一个修正。**

缺的不是"让 scrna agent 写方案"——`data/ai/flows/scrna.yaml` 已完整声明 upstream → integrate → advanced 三阶段分工与责任 Agent。缺的是**聊天入口没有把请求路由到这份 Flow 定义**。修正后的分工应该是：

| 角色 | 职责 | 不该做的 |
|------|------|---------|
| Manager | 意图识别、路由到领域 Flow、确认点交互、结果汇总 | 亲自代写领域方案、口头"宣布"交接 |
| 领域 Flow（scrna.yaml） | 阶段 DAG、责任 Agent、输入输出、质量门 | —— |
| 专项 Agent | 各自阶段的规划与执行 | —— |

Manager 亲自输出领域方案属于**角色越界**：方案看起来像"来自单细胞专家"，实际来自通用规划，专业可信度与可追责性都落空。

### 9.3 新增优化项 O12~O17

#### O12 交接真实性门禁（对应用户判断一，止血项）

**原则：Manager 的语言不能先于系统的运行时事实。**

Spec：

1. 新增统一交接事件序列并全部接入房间投影器：
   `case.handoff_proposed` → `case.handoff_started` / `case.handoff_failed` → `work_item.assigned` → `work_item.claimed` → `work_item.running` → `work_item.finished` → `case.delivery_ready` → `case.closed`。
2. `case.handoff_started` 至少携带：`case_id`、`flow_id`、`agent_ids[]`、`work_item_ids[]`、`status`。
3. **文案门禁**：Manager 回复生成时校验——只有当 `handoff_started` 事件已成功写入，文案才允许使用"已交接/已派发/已开始分析"；未写入时强制使用"待确认交接"并附结构化确认入口。仅规划回复（planning_only）禁止出现任何执行时态措辞。

**验收**：造一个 Worker 不在线的场景，Manager 回复中不出现"已交接"字样，且房间内有 `handoff_failed` 错误卡。

#### O13 聊天 Case 领域 Flow 路由（对应用户判断二 + 核心目标）

**原则：聊天入口识别到正式领域分析请求时，必须落到既有 Flow 定义，而不是自由文本规划。**

Spec：

1. 意图识别命中领域分析（如单细胞全流程）且有作用对象时，为聊天 Case 绑定 `flow_id: scrna`；

3. reconcile 逻辑对带 `flow_id` 的聊天 Case 不再跳过自动 planning（消除 `chat_case_skips_auto_planning` 回退路径）；
4. 与 O5 的关系：O5 解决 Bridge 侧标准工作项 target 硬编码，本项解决聊天入口不绑定 flow——两者合流后，"聊天发起"与"Flow 发起"收敛为同一条执行链路；
5. 路由判断来源复用 O4 的关键词单源机制，禁止在聊天入口再维护一份领域关键词表。

**验收**：发送与本次相同的小鼠单细胞请求，Case 绑定 `flow_id: scrna` 且可查询到三个领域工作项（或明确的不可用原因），Manager 回复引用的是 Flow 阶段结构而非自由文本。

## 11. 重复提醒死循环与回复变慢的根因排查（v1.5 新增）

> 触发：v1.4 修复提示词下发后实测，"需要你先确认数据来源，再启动执行"仍重复推送且升级到 4 次（00:20/00:21/00:22/00:23，精确每分钟一条），用户已回复仍被反复追问；同时 AI 回复速度明显变慢。
> 结论先行：v1.4 的修复没有触及根因（或未实施），本轮要求编码 Agent **先交根因证据再改**，禁止再次盲改。

### 11.1 关键物证：60 秒节律

4 条重复消息精确每分钟一条——这不是 LLM 的随机行为，是**定时循环在 ticking**。结合调查报告 §3.3 已证实的 reconcile 逻辑（无 `flow_id` 的聊天 Case 每轮 reconcile 以 `chat_case_skips_auto_planning` 退回 `received`），最大嫌疑链条：

```text
用户文字回复
  → ask_user 答案未回写消费（选项未渲染成卡片，文字回复不被识别为答案）
  → "数据来源未确认"门禁条件永远不满足
  → reconcile/提醒循环每 60s tick，条件不满足就再发一遍
  → watcher/系统消息无去重 → 每分钟刷屏一条
```

### 11.2 为什么"和预期完全不同"

阶段 H 只给 Manager 的语言加了门禁（"说什么"），没有动 Case 流转（"怎么流转"，属阶段 5）。Case 结构性停在 received，系统唯一能做的就是反复提醒；澄清链路是半截功能——ask_user 会生成，但答案回收与状态迁移缺失。

### 11.3 回复变慢的嫌疑排序

1. 每次 tick 可能触发 Manager 全量重生成，正常回复排队；
2. 文案门禁若实现为"生成后额外一次 LLM 校验"，回复路径串行多一次模型往返；
3. 能力检查若为同步阻塞式健康检查，缺 token/心跳的 Agent 逐个等超时；
4. ask_user 大 JSON 单次生成 token 量大，若有二次修复校验更慢。
