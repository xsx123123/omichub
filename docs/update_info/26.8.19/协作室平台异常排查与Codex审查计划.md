# 协作室多智能体平台异常排查与 Codex 审查计划

> 版本：v1.1（审查计划校正：异常分析 + 只查不改审查提示词）
> 工作流：本对话负责分析日志、出提示词与核对报告；Codex 负责代码级审查执行。

## 一、背景

在协作室（Manager + 多 Worker 的多智能体编排平台）测试一个真实任务：

> 用户输入：我有 6 个样本的小鼠单细胞数据，分为两个 group 3v3，想要找到不同 group 间的细胞类型差异和差异基因。

运行结果异常：任务未产出任何单细胞分析结果，Case 在路由、计划生成、文件解析、Worker 存活、状态上报多个环节出现问题，最终以工作项超时终止、下游跳过的方式烂尾，但界面一度显示"已完成"。

## 二、对分析内容本身的评审（科学层面无问题）

Manager 思考过程中给出的单细胞分析建议是严谨、符合领域规范的，无需修改：

- 差异表达采用 pseudobulk 策略，以 6 只独立小鼠为生物学重复——正确，避免了把细胞当独立重复导致假阳性膨胀这一最常见硬伤；
- 细胞类型比例比较推荐 scCODA / propeller（考虑组成性数据特性）——正确；
- 批次校正推荐 Harmony/scVI——正确；
- 明确提示了三大风险（假重复、批次混淆、注释准确性）——到位。

**工作假设：目前证据更支持平台编排链路存在故障；但在没有完整输入文件、Bridge/Worker 原始事件流和最终 Case 快照前，不能写成“100%”。科学方案本身暂未发现明显问题，但仍应把“方案正确性”和“平台执行正确性”分开验证。**

平台是 Manager（管家）+ 多 Worker（代码助手/通用助手/单细胞分析师等）的多智能体

## 审查任务

### A. 路由与澄清链路
1. Manager 路由决策实现：路径候选如何生成与打分，dispatch 如何选择 planner——定位
   "识别为 agent-scrna 却分派给 agent-code"的决策代码，确认是选择逻辑错误、默认值
   兜底，还是 UI 点选事件未接入
2. 澄清机制：问题如何生成、答案如何回写；是否存在"推荐答案自动填充/超时自动采纳"
   逻辑；用户未回答时系统是否会带着推荐值继续执行
3. Case 状态机在路由阶段的流转条件（received → 规划中 → 进行中）

### B. Worker ReAct 循环与计划生成
1. no_progress 保护的判定逻辑（连续相同工具？相同结果？）与触发后的处理
2. 计划 schema 校验与自动修正：proposed_submission 字段的定义来源、修正重试时是否
   把具体校验错误反馈给模型、为何多次不收敛、预算耗尽后的兜底行为
3. 工具调用去重/循环检测在哪一层（workspace_file_preview 连续相同返回的检测）

### C. 文件上下文解析链路（重点）
1. file:// 逻辑上下文引用的生命周期：在哪生成、在哪注册/落库、Worker 侧如何解析
2. workspace_file_preview 实现：支持哪些寻址方式，"任务文件不存在或不是普通文件"
   在什么条件下返回
3. Manager 侧可见的上下文与 Worker 侧可读文件集合是否一致——这条链路是否设计上
   就断的
4. 上下文解析失败时的行为：有无中止/回问保护，还是放任 Worker 自由发挥导致目标
   漂移

### D. Worker 租约与心跳
1. 心跳上报机制与租约时长：如何上报、多久过期、超时如何判定
2. agent-general"开始处理：生成执行计划"后 5 分钟无心跳的可能原因：同步长调用阻塞
   无心跳、worker 崩溃、还是心跳线程本身缺陷
3. 重试预算耗尽后的收尾：工作项终止、下游跳过、Case 最终状态如何落库与展示

### E. 状态与日志一致性
1. "已完成"由谁置位：规划完成与任务完成是否共用状态，是否存在假完成
2. 日志时间戳来源与排序：09:58 的人工审批为何渲染在 11:17 条目之后

### F. 证据边界与运行时复现
1. 先建立本次 Case 的证据包：Case ID、创建/更新时间、完整事件流（含 event_id、事件时间、入库时间）、
   work item 快照、审批记录、Worker stdout/stderr、Bridge 请求/响应摘要和前端收到的事件顺序。
2. 对每个异常输出四种结论之一：**代码已证实**、**代码机制存在但本次未证实**、**与当前代码矛盾**、
   **仓库内缺少实现/证据**。禁止用“疑似”直接升级为根因。
3. 代码位置统一使用审查时的 commit SHA + `文件:行号`；若工作区有未提交改动，必须同时标注“工作区版本”，
   并说明该改动是否可能改变结论。
4. 对外部 Bridge/Worker 服务不在本仓库的部分，明确列为“仓库审查边界外”，给出需要补充的接口契约或日志，
   不得仅凭 OmicHub 调用方代码推断远端行为。

## 七、首轮审查校正结论（基于当前工作区代码，2026-08-19）

本节不是最终故障报告，而是对本计划中“预判”部分的审核，避免把待验证假设写进 Codex 的提示词。

### 7.1 已有代码证据支持的方向

- **路由存在明确的 `agent-code` 默认值**：`src/omichub/application/services/agentteams_service.py:52` 定义 `DEFAULT_LEAD_PLANNER = "agent-code"`；`start_chat_planning` 在 `:792-813` 先尝试 `infer_intent_route`，失败或无命中时回退到该默认值。因此异常 1 应重点核对“意图命中结果为何为空/被覆盖”，而不是预设为候选打分错误。
- **路由决策卡不是审批门**：`src/omichub/application/services/agentteams_room_response_service.py:576-606` 先发 `room.route_decision`，随后直接调用 `start_chat_planning`；当前片段没有等待用户选择的同步门。这支持“展示决策与真正 dispatch 可能脱钩”的审查方向，但仍需核对 Bridge 是否在后端另有门控。
- **`no_progress` 的实现语义需要纠正**：`src/omichub/application/services/parallel_subagent_service.py:895-928` 按连续相同工具结果触发保护，并返回 `status: "ok"` 的阶段性结果，不是简单的“触发后原样失败重试”。报告必须核对阈值、上层如何消费该 `ok`，以及是否因此出现“看似完成但无产物”。
- **文件预览工具按工作区路径解析**：`src/omichub/application/services/agentteams_data_tool_service.py:57-68` 把参数传给 `PipelineResultService.preview_workspace_file`；`src/omichub/application/services/pipeline_result_service.py:86-98` 预览的是用户 workspace 内的路径，`file://` 是否可用必须由解析函数和调用方共同证明，不能从日志自述推出“注册链路从未存在”。

### 7.2 当前代码已否定或尚未支持的预判

- **“推荐答案自动填充确实存在”目前不能成立**：澄清卡只是把“上传文件后执行（推荐）”作为选项文案，见 `src/omichub/application/services/agentteams_room_response_service.py:715-756`；答案回收还要经过下一条 `room.user_message`。另有旧自动确认入口，但 `src/omichub/application/services/agentteams_service.py:611-626` 明确返回 `skipped_manual_approval_required`。必须取得本次 Case 的用户消息/审批事件后再定性。
- **“规划完成与任务完成共用状态位”尚未被当前代码证明**：`start_chat_planning` 写入的是 `planning_running`（`src/omichub/application/services/agentteams_service.py:815-818`），而工作项和 Case 的终态由 Bridge/事件消费者回写。需要补看 Bridge 状态模型、状态转换接口和前端投影，不能只凭“已完成”文案断言。
- **心跳/租约故障的核心实现可能在 Bridge 外部**：仓库内能看到 `work_item.lease_expired` 的投影文案，但这不等于能证明租约续期线程、超时阈值或远端 Worker 的同步阻塞原因。该项必须列为“需要 Bridge/Worker 原始证据”。

### 7.3 修订后的行动顺序

1. **先固定证据**：导出本次 Case 的事件流和状态快照，建立事件时间与入库时间双时间轴；同时记录审查 commit SHA。
2. **先止血验证，不先改代码**：确认 dispatch 是否真正等待选择、上下文引用是否在目标 Worker 工具契约内可读、失败是否有回问/阻断。
3. **再做根因归因**：把路由、澄清、文件、循环、租约、状态日志分别映射到代码证据和运行证据；对无法闭环的项保留意见。
4. **最后才排实施优先级**：仅对已确认且有最小复现的缺口安排修复；“一次登记/一行默认值”只能作为候选止血点，不能预先承诺。
