### 1.3 不能直接成立的原始预判

1. **“推荐答案被系统自动填充”未被当前代码证明。** “（推荐）”是澄清选项文本的一部分；答案需要前端形成下一条 `room.user_message` 才会回到服务端。旧的自动确认入口当前固定返回 `skipped_manual_approval_required`，不再自动放行真实计算。
2. **“规划完成和任务完成共用一个状态位”未被当前代码证明。** 通用聊天 Case 启动规划时写入的是 `planning_running`，而 work item 终态、Case 终态与 Bridge 事件投影属于后续链路；需要 Case 状态快照及事件流确认。
3. **“心跳机制缺失”未被当前代码证明。** Bridge 内有心跳 API、后台续租协程与 watchdog；本次三次超时更可能是续租协程未被启动、被取消、与实际执行路径不一致，或请求无法落到 Bridge。需要 trace ID 和运行日志才能区分。
4. **“`file://` 从未注册到 Worker 可读存储”未被当前代码证明。** 目前能证明的是 `workspace_file_preview` 不把 `file://` 当作可直接使用的相对路径。引用从何处生成、是否应先映射/挂载、以及 Worker 实际拿到的上下文，需要沿 Case payload 和工具调用继续取证。

## 4. 异常逐项审查

### 4.1 异常 1：识别为 `agent-scrna`，实际却派给 `agent-code`

**日志现象**：候选中出现单细胞分析师，界面提示点选裁决，但最终消息显示派发给代码助手。

**相关实现**：

- `infer_intent_route` 会从流程提示词、领域别名及迁移期别名生成候选，并按命中数量、命中字符数和 flow ID 的稳定规则选出 winner，见 `src/omichub/application/services/agentteams_intent_router.py:126-207`。
- 消息处理层先调用 `infer_intent_route`，再将 `route.lead_planner` 作为 `target_agent_id` 传给 `start_chat_planning`，见 `src/omichub/application/services/agentteams_room_response_service.py:576-597`。
- `start_chat_planning` 在 `target_agent_id` 缺失、路由失败或无命中时，以 `DEFAULT_LEAD_PLANNER = "agent-code"` 兜底，见 `src/omichub/application/services/agentteams_service.py:51-52`, `:792-813`。

**当前判断**：

- `agent-code` 兜底机制是真实存在的，属于本次最优先核对点。
- 候选卡使用的 `build_route_decision` 是“只读观察”层，而 `start_chat_planning` 重新调用 `infer_intent_route` 执行实际目标选择；两次调用理论上应一致，但若两次的输入文本、可用能力注册或异常处理不同，就可能出现“卡片显示 A、实际 target 为 B”。
- 当前 OmicHub 代码在发出路由卡后不会等待用户选择；“请点选裁决”可能只是 UI 表达或 route decision payload 的模糊度提示，而不是控制流门。是否存在 Bridge 侧或前端侧真正的选择回写，仍需用 HTTP 请求和事件记录确认。

**最小验证步骤**：

1. 从 `plan-01` 创建请求提取 `target` 与 `objective`；检查是否已经是 `agent-code`。
2. 比对同一轮 `room.route_decision.payload.lead_planner`、`matched_hints` 与 `plan-01.target`。
3. 记录 `infer_intent_route` 的输入文本、Flow registry 和 capability registry 快照；如果 `scrna` 胜出却仍创建 `agent-code`，再定位目标被覆盖的后续调用。

### 4.2 异常 2：未见用户回答，却出现包含“（推荐）”的澄清答案

**相关实现**：

- 当执行请求没有明确作用对象，系统会生成澄清卡；首轮选项固定包含“上传文件后执行（推荐）”，见 `src/omichub/application/services/agentteams_room_response_service.py:715-756`。
- 注释明确说明前端把答案格式化为带 `【澄清回复】` 的下一条 `room.user_message`，然后再返回响应链路，见同文件 `:720-722`。
- 历史 auto-confirm 入口虽然仍保留，但当前实现直接返回 `skipped_manual_approval_required`，并声明真实计算必须由当前 Case 的用户显式批准，见 `src/omichub/application/services/agentteams_service.py:611-626`。

**当前判断**：

- 仅凭“包含（推荐）”不能证明服务端自动填入答案，因为这是选项文本的正常组成部分。
- 若分派消息确实携带四个选项的原文，它也可能是把卡片 payload 或 UI 展示文本误拼入了 Manager 消息；这是“渲染/投影混淆”和“自动回答”两种不同问题。
- 若日志中存在 `【澄清回复】` 但没有用户交互，需检查前端是否在渲染卡片时自动生成回传消息、是否有旧缓存/重放，或事件流是否漏掉了用户消息。

**最小验证步骤**：按 `event_id` 和 `recorded_at` 查找该澄清卡之后的全部 `room.user_message`；对每条消息检查 actor、content、client_message_id 及是否带 `【澄清回复】`。没有该消息时，再查前端网络请求和 Bridge audit。

### 4.3 异常 3：重复读文件、`no_progress`、`proposed_submission` 校验失败后不收敛

**相关实现**：

- `no_progress` 在连续 `_MAX_REPEATED_TOOL_RESULTS` 次工具响应 JSON 完全一致时触发，见 `src/omichub/application/services/parallel_subagent_service.py:895-903`。
- 该分支会发出 `agent_loop_guard_triggered` 审计事件，却返回 `status: "ok"` 与阶段性答案，见同文件 `:904-928`。注释的设计意图是让 Manager 汇总已有证据，而不是把 Worker 直接当成失败。
- 通用聊天计划的契约要求输出 `proposed_submission`，并且工作项必须明确 `target`、输入引用与期望产物，见 `src/omichub/application/services/agentteams_execution_intent.py:24-35`。

**当前判断**：

- “no_progress 触发”本身不是 Worker 失败的直接证据；更准确的风险是**在没有足够执行证据或可提交计划时，保护分支的 `ok` 可能被上层误投影为阶段完成**。
- “自动修正两次仍不收敛”的直接修复路径尚未在本次静态取证中定位；需继续审查 `AgentConsultationService` 对模型 JSON、schema error 和 repair prompt 的处理，并用实际 repair 输入/输出确认模型是否得到具体错误。
- 该问题的验收标准不应是“循环不再出现”，而应是“无 `proposed_submission` 或无满足质量门的产物时，不能进入可展示为完成的状态”。

### 4.4 异常 4/5：`file://` 无法预览后目标漂移

**相关实现**：

- `workspace_file_preview` 以用户 workspace 根目录为边界，将 `path` 传给 `preview_workspace_file`，见 `src/omichub/application/services/agentteams_data_tool_service.py:57-69`。
- 路径解析将 `Path(requested)` 视为相对文件路径；拒绝绝对路径和 `..`，并在 backend 中不存在或为目录时返回“请求的任务文件不存在或不是普通文件”，见 `src/omichub/application/services/pipeline_result_service.py:345-363`。

**当前判断**：

- `file://cb79...` 作为 `path` 传入时，不是该工具的显式 URI 协议；很可能被当作一个不在 workspace 内的普通相对路径，从而得到“文件不存在”错误。这个判断有代码支撑。
- 但这尚不能证明“逻辑引用从未注册”。可能的真实问题包括：引用没有映射到 workspace、Worker 选择了错误工具、上下文 payload 只传了 URI 未传实际路径、或该 URI 本来应由另一个工具解析。
- 上下文解析失败后是否存在强制中止/回问，需检查 Worker 的 planner prompt、工具失败处理与计划修复代码。当前可见的通用执行意图链路在起始阶段有对象澄清，但无法保证已经启动的 Worker 在工具失败后会再次回问。

**建议的止血验收**：只要 `context_refs` 中含 URI，系统必须在 dispatch 前将每一个引用标注为“可由目标 Worker 读取的 workspace 路径”“可由专用 URI 工具读取”或“不可读”；存在不可读输入时，不得创建可执行的 `plan-01`，而是发 `room.ask_user` 或 `work_item.blocked`。

### 4.5 异常 6a：连续心跳超时、重试耗尽、下游跳过

**相关实现**：

- Work item 领取时携带 `lease_seconds`，Bridge 的 `heartbeat_work_item` 会更新租约并记录 `worker.heartbeat`，见 `integrations/agentteams/bridge/omichub_agentteams_bridge/service.py:860-892`。
- 对阻塞式 Gateway 会诊，`_renew_work_item_lease` 每个租约时长的三分之一执行一次 store-level heartbeat，见同文件 `:1159-1182`。
- 应用启动时会按配置启动 watchdog；watchdog 调用 `sweep_work_items` 回收过期 work item，见 `integrations/agentteams/bridge/omichub_agentteams_bridge/app.py:73-93`, `:157-163`，以及 `service.py:1748-1756`。
- 超时投影有明确的 `work_item.lease_expired`、`work_item.timeout` 与 `work_item.skipped` 标签，见 `src/omichub/application/services/case_room_projector.py:293-308`。

**当前判断**：

- 代码并非没有心跳/租约机制；“约 5 分钟一次”很可能对应 deadline 或 watchdog 节奏，但必须读 runtime settings 和 work item 实例才能确认。
- 若每轮都刚好在租约到期时被回收，优先排查：该执行路径未启动 `_renew_work_item_lease`、异步任务被取消、续租访问 CaseStore 失败、Worker 从未认领、或 Clock/时区不一致。
- 下游跳过是可能的故障收尾策略，不等同于根因；需要从 sweep 与依赖处理事件确认它是否按设计发生。

### 4.6 异常 6b：已显示“完成”，之后仍重派；人工审批条目位置异常

**相关实现**：

- 前端 `projectCaseEvents` 会先按 `recorded_at` 升序排序，同时间戳才保持原数组顺序，见 `frontend/src/utils/agentTeamsRoom.ts:1175-1191`。
- Bridge 审计统计也按 `recorded_at` 排序，见 `integrations/agentteams/bridge/omichub_agentteams_bridge/audit.py:258-264`。
- UI 文案把 `work_item.finished` 渲染为“已完成工作项”，把 `work_item.lease_expired` 渲染为“心跳超时，工作项已回收重派”，见 `src/omichub/application/services/case_room_projector.py:293-308`。

**当前判断**：

- 前端存在排序逻辑，故“人工审批在 11:17 后面”可能由 `recorded_at` 本身错误、服务器写入延迟、时钟问题、同毫秒 tie、不同事件源混用业务时间与记录时间，或 UI 从其他接口插入了未投影消息造成；不能简单归因为“前端没有排序”。
- 必须区分 `work_item.finished`、规划完成、审批完成、Case closed 四种不同层次。若 UI 只显示“已完成”而不说明对象，属于体验与状态语义问题；若 Case 状态已变为终态却仍重派，才是状态机一致性问题。

## 5. 风险分级与建议行动顺序

| 优先级 | 风险 | 建议动作 | 验收标准 |
|---|---|---|---|
| P0 | 不可读的输入引用仍进入执行，导致 Worker 目标漂移 | 在 dispatch 前做 `context_refs` 可读性预检；失败转澄清/阻断 | 每个输入都有可读取路径或专用解析器；不可读时没有执行 work item |
| P0 | 路由卡片与实际 planner target 可能不一致 | 将决策 payload、`plan-01.target`、route 输入/版本写入同一审计事件 | 任意 Case 可直接比对“展示路由”和“实际 dispatch” |
| P1 | `no_progress` 返回 `ok` 可能造成伪完成 | 在计划/交付聚合层引入最小完成证据门：计划结构、输入证据、产物/阻断原因 | 只有满足质量门的 `ok` 才能显示完成；否则显示阻断/待处理 |
| P1 | 心跳超时缺少可定位诊断 | 每次 claim、续租、续租失败、sweep 均带 trace ID、deadline、attempt、worker ID | 可在一条 trace 中还原从认领到过期的原因 |
| P1 | “完成”文案语义不清 | 区分“规划完成”“工作项完成”“Case 交付完成”“失败/跳过” | 时间线与卡片显示对象和终态一致 |
| P2 | 澄清选项与用户回答混淆 | 审计事件显式标记 `ask_user`、`user_reply`、`answer_source` | 报告能证明答案来源，不靠文案猜测 |

## 6. 推荐的下一轮复核脚本/问题清单

下一轮不要先改业务逻辑。应先针对本次 Case 产出一张“单 Case 证据表”，每一行对应一个事件，并至少包含：

```text
event_id | recorded_at | business_at | event_type | actor | case_status |
work_item_id | target | attempt | lease_expires_at | trace_id |
context_refs | payload 摘要 | 前端消息 ID
```

然后按以下顺序复核：

1. **路由一致性**：`room.route_decision.lead_planner`、`plan-01.target`、Bridge 收到的 work item target 是否一致。
2. **澄清来源**：每个 `【澄清回复】` 是否能找到此前 `room.ask_user` 和之后的真实用户消息。
3. **文件契约**：每个 `context_ref` 能否映射到 workspace 相对路径或专用工具；`file://` 是否有映射记录。
4. **循环与计划**：列出每次工具调用的名称、arguments hash、result hash、`no_progress` 触发位置、计划修复 prompt 与 schema error。
5. **租约诊断**：比对 claim、首次 heartbeat、后台续租、最后一次 heartbeat、lease expiry、sweep、retry 与 timeout 的时间差。
6. **状态投影**：对照 Bridge Case status、work item status、CaseRoomProjector 标签、前端显示文本与 `recorded_at` 排序结果。

## 7. 审查结论的使用方式

本文可作为后续 Codex 代码审查和线上故障复盘的输入，但不应直接转换为修复任务清单。推荐把每一项结论标为以下四类之一后再排期：

- **代码已证实**：静态实现明确存在，且无需运行事实即可成立。
- **机制存在，需运行证实**：代码可能解释故障，但尚未证明本次 Case 实际走过该分支。
- **与原预判不一致**：例如自动审批与心跳缺失，目前有代码证据反驳。
- **证据不足**：需要 Case audit、Bridge 请求日志、Worker trace 或前端原始事件。

最终修复应优先处理那些同时满足“阻断主任务”“有稳定复现”“输入/输出契约可明确验收”的问题，尤其是 `context_refs` 可读性预检与路由展示/派发一致性审计。
