# 多 Agent 协作流程优化建议与实现计划

> 适用平台：OmicHub 多智能体系统（general / router / rnaseq / code / viz / scrna）
> 文档性质：问题诊断 + 优化方案 + 分阶段实现计划（每阶段附可直接粘贴给编码 Agent 的提示词）
> 版本：v1.0（2026-08-02）

---

## 一、背景与目标

平台现有 4 条多 Agent 协作路径：

1. **Agent Handoff**：串行转交专家（白名单见 `data/ai/general.yaml:22`、`data/ai/scrna.yaml:22` 等）
2. **并行 Sub-Agent Fan-out**：2–5 个并行子任务（开关 `SUBAGENT_FANOUT_ENABLED`，默认关，`src/omichub/core/config.py:97`）
3. **多专家会诊**：并行咨询最多 3 位专家，只读不执行（开关 `MULTI_EXPERT_CONSULTATION_ENABLED`，默认关，`src/omichub/core/config.py:95`）
4. **AgentTeams Case**：可审批、可追踪的协作闭环（需 `AGENTTEAMS_BRIDGE_ENABLED` + `AGENTTEAMS_CHAT_ENTRY_ENABLED` + Bridge URL + 4 个身份 token，模板见 `.env.example:5`、`deploy/agentteams/README.md:90`）

**核心痛点：机制设计本身合理，但"选择路径"的认知成本被甩给了用户。** 用户需要记住 4 条路径分别叫什么、什么任务该用哪条、触发咒语怎么说、开关开没开——任何一步出错，体验就是"说了没反应"或"不知道为啥没走想要的路"。

**优化总目标：用户只说人话，路径由系统选；机制不变，入口统一。**

- 用户侧：零咒语、零路径记忆，说需求即可；系统决策过程可见、可纠正。
- 管理侧：开关从"散装的布尔值"变成"三档预设 + 自检"，开没开、缺什么一目了然。
- 机制侧：4 条路径**全部保留、互不合并**——会诊（讨论）与 Case（立项）的关系是前后串联，不是平级互斥。

## 二、现状问题清单

| # | 问题 | 严重度 | 具体表现 |
|---|---|---|---|
| P1 | 路径选择依赖用户"念咒" | 🔴 高 | 用户必须说"请转给单细胞专家""请并行检查…""请创建协作 Case"等精确话术；不知道话术的用户永远用不上 ②③④ |
| P2 | 开关关闭时静默降级，无反馈 | 🔴 高 | Fan-out / 会诊默认关，用户说了"并行检查"也会被静默串行处理，用户以为系统听不懂 |
| P3 | 会诊与 Case 割裂 | 🟡 中 | 会诊出方案后，想升级成正式 Case 要重新描述一遍需求，会诊结论不会带入 Case 预检 |
| P4 | 系统决策不透明 | 🟡 中 | 走了哪条路径、为什么走这条，用户无从知晓；走错了也无法一句话纠正 |
| P5 | 管理端配置门槛高、无自检 | 🟡 中 | Case 需要桥接开关 + URL + 4 个 token + 外部 Worker 部署（`deploy/agentteams/README.md:90`），仅改平台配置 Worker 不会启动，管理员容易"以为开了其实没通" |
| P6 | 能力边界有隐藏断点 | 🟢 低 | Bridge 白名单仅 `rna_seq`（`deploy/agentteams/bridge.env:7`），scrna 能参与会诊/Work Item 但流程本身提不进去；MAS DAG 与多 Agent 对话协作概念易混 |

## 三、优化方案总览

### 方案 A：统一意图路由层（解决 P1、P4）—— 核心

在现有 Router 之前增加一层**意图分类**，用户输入不再要求任何咒语，由系统判定该走哪条路径：

```
用户自然语言输入
      │
      ▼
┌─────────────────┐
│  意图分类器      │  输出：transfer / fanout / consult / case / dag / 普通问答
│ (主 Agent 前置)  │  + 置信度 + 理由（一句话）
└─────────────────┘
      │
      ├── transfer → ① Handoff（现有白名单逻辑不变）
      ├── fanout   → ② 并行子任务（需开关，未开走方案 B 降级）
      ├── consult  → ③ 多专家会诊（需开关，未开走方案 B 降级）
      ├── case     → ④ 弹 Case 确认卡（现有确认卡逻辑不变）
      └── 普通问答 → 当前 Agent 直接答
```

判定规则（写进系统提示词，锚定 `src/omichub/application/services/chat_service.py:129` 附近改造）：

| 信号 | 判定 |
|---|---|
| 明确点名其他专家 / 当前问题超出本 Agent 领域 | transfer |
| 一句话里出现 2–5 个**互相独立**的子任务（"同时/分别/并行/一起"） | fanout |
| 问"合理吗/怎么解读/这样设计行不行"，需要多角度判断 | consult |
| 出现"长流程/要审批/要交付/给客户/正式跑"等治理信号 | case（必须先弹确认卡） |
| 提到跑分析管道/工作流（分钟-小时级） | dag（MAS，非对话协作，引导至对应入口） |
| 置信度 < 阈值 | **反问一句**，不瞎猜 |

**决策透明化**：每次路由后，在消息流顶部渲染一行轻量路径提示（可折叠），如：
`🔀 已转交 单细胞专家 · 原因：涉及 scRNA 注释判断`／`⚡ 已并行处理 3 个子任务`／`💬 已咨询 2 位专家`。
路径提示附带"走错了？"链接，点击后用户一句话可改派其他路径。

### 方案 B：能力降级显式化（解决 P2）

开关未开启时，**禁止静默退回串行**，改为明确告知 + 给替代方案：

> 「并行处理需要管理员开启 `SUBAGENT_FANOUT_ENABLED`，当前未开启。我可以改为**逐个串行**为你处理这 3 个任务，预计多 1–2 分钟；或你可以联系管理员开启后重试。」

会诊、Case 同理。告知文案中给出当前**实际可用**的替代路径，不让用户死等。

### 方案 C：会诊 → Case 一键串联（解决 P3）

- 会诊结果卡片底部新增按钮：**「基于本次会诊结论创建协作 Case」**。
- 点击后把会诊纪要（专家意见、分歧点、建议方案）作为结构化上下文**预填进 Case 描述**，并作为 Data Steward 预检的输入材料。
- 定位："会诊是 Case 的免费前置咨询"，用户动线变成一条线：先问意见 → 觉得靠谱 → 一键立项。

### 方案 D：管理端三档预设 + 部署自检（解决 P5、P6）

**三档预设**（管理后台一键应用，替代逐个翻 `.env`）：

| 档位 | 开启项 | 适用团队 |
|---|---|---|
| 轻量协作 | Handoff + 多专家会诊 | 只要"问对人、问多方意见"，不跑正式流程 |
| 并行增强 | 轻量协作 + Fan-out | 需要真实并行短任务 |
| 全流程闭环 | 并行增强 + AgentTeams Bridge 全套 | 需要审批、执行、质控、交付归档 |

**部署自检脚本**（`deploy/agentteams/` 下新增 `check_setup.sh` 或平台内置健康检查页）：

- 检查 Bridge URL 连通性、4 个身份 token 有效性；
- 检查 agent-code / agent-viz / agent-scrna 外部 Worker 心跳（是否真在轮询 `/v1/work-items/assigned`）——只改平台配置没部署 Worker 的情况直接报红；
- 报告 Bridge 白名单当前值（`deploy/agentteams/bridge.env:7`），提示 scrna 流程尚未纳入，避免管理员误以为已支持。

## 四、分阶段实现计划

每阶段独立可交付、可验收，顺序即依赖关系。

### Phase 1：意图路由层 + 决策透明化（方案 A）

**改动点**：

1. `chat_service.py:129` 附近的系统提示词扩展：加入意图分类规则与 few-shot 示例（下附），要求主 Agent 在路由前先输出结构化意图（JSON：`intent / target / confidence / reason`）。
2. Router 消费该结构化意图，映射到现有 4 条路径的既有实现，**不改各路径内部逻辑**。
3. 置信度 < 0.6 时不路由，生成一句反问（"你是想让我并行处理这三件事，还是逐个来？"）。
4. 前端消息流增加路径提示条（可折叠）+ "走错了？"改派入口。
5. 新增总开关 `UNIFIED_INTENT_ROUTER_ENABLED`（默认关，灰度用），关闭时行为与现状完全一致。

**few-shot 示例语料**（加入提示词）：

```
"这个结果应该怎么解读，注释策略合理吗"      → consult
"帮我把代码、QC 和图表方案都看一下"          → fanout
"这个 RNA-seq 流程要跑给客户，结果要归档"     → case（弹确认卡）
"这个我答不了，需要单细胞的专家"             → transfer → agent-scrna
"帮我跑一下上游比对定量流程"                → dag（引导至 MAS 管道入口）
```

**验收 checklist**：

- [ ] 20 条覆盖 6 类意图的测试语料，路由准确率 ≥ 90%，低置信度全部反问而非误路由
- [ ] 每条被路由的消息都有路径提示条，且含一句人话理由
- [ ] "走错了？"改派后按新路径正确执行
- [ ] 总开关关闭时，行为与上线前完全一致（回归测试）

### Phase 2：能力降级显式化（方案 B）

**改动点**：

1. Router 在意图命中 fanout / consult / case 但对应开关未开时，走降级话术模板（第三章方案 B），而非静默串行。
2. 降级话术中动态渲染当前可用替代路径（如 Handoff 可用则建议转专家串行处理）。
3. 管理后台对应开关旁显示"近 7 天被用户触发但因未开启而降级的次数"，给管理员开启决策提供数据。

**验收 checklist**：

- [ ] 开关关闭时触发对应意图，100% 收到降级说明而非静默失败
- [ ] 降级话术给出的替代路径实际可用
- [ ] 管理后台能看到降级计数

### Phase 3：会诊 → Case 串联（方案 C）

**改动点**：

1. 会诊结果卡数据结构增加 `consultation_summary` 字段（专家意见、共识、分歧、建议）。
2. 前端会诊结果卡新增「基于此创建协作 Case」按钮（Case 能力未开启时隐藏或显示降级提示）。
3. Case 确认卡支持从 `consultation_summary` 预填描述；Data Steward 预检 prompt 中注入会诊纪要。
4. 后端在 Case 记录中保留 `origin_consultation_id`，实现从 Case 回溯到会诊。

**验收 checklist**：

- [ ] 会诊 → Case 一键创建，描述自动预填且可编辑
- [ ] Data Steward 预检输出中能看到对会诊结论的引用
- [ ] Case 详情页可回溯查看来源会诊

### Phase 4：管理端预设 + 自检（方案 D）

**改动点**：

1. 管理后台新增"协作能力档位"设置，三档预设一键写入对应开关组合。
2. 新增自检能力：Bridge 连通性、token 有效性、3 个外部 Worker 心跳、白名单内容，结果展示在管理后台健康检查页，并提供 `deploy/agentteams/check_setup.sh` 命令行版本。
3. 文档整合：把分散在 `.env.example:5`、`deploy/agentteams/README.md:90`、各 `data/ai/*.yaml` 注释中的配置说明收敛成一篇《多 Agent 协作配置指南》，并在每处保留指向该篇的链接。

**验收 checklist**：

- [ ] 三档预设切换后，各开关值与预设定义完全一致
- [ ] 未部署外部 Worker 但开了 Case 开关时，健康检查页报红并说明原因
- [ ] 白名单仅 `rna_seq` 时，页面明确提示 scrna 流程暂不可提交

## 六、风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 意图误路由（如把普通问答误判为 case） | 用户被弹确认卡骚扰 | 置信度阈值 + 反问；case 永远必须经确认卡，不会直接创建；保留"走错了？"改派 |
| 提示词改造影响现有对话质量 | 主 Agent 回答退化 | 总开关默认关，灰度放量；上线前用既有对话集回归 |
| 降级话术打扰高级用户 | 啰嗦 | 降级说明每会话只完整展示一次，后续折叠为一行提示 |
| 会诊纪要预填进 Case 后泄漏讨论上下文 | 信息边界问题 | consultation_summary 只含结论性内容，原始专家对话不进 Case；确认卡上明示将携带哪些内容 |

**回退策略**：所有阶段均由独立开关控制（`UNIFIED_INTENT_ROUTER_ENABLED` 等），任一阶段出问题关闭对应开关即回到现状，4 条路径的既有实现全程未被改动。

## 七、优先级建议

如果只做一件事，做 **Phase 1（统一意图路由层）**——它解决的是最大的痛点（用户要记咒语），且是 Phase 2/3 的地基。Phase 4 可与 Phase 1 并行由运维侧推进，互无依赖。

预期收益（可用遥测验证）：

- ②③④ 路径的使用率提升（当前因不知道咒语而趋近于零的自然触发 → 意图自动命中）；
- 降级事件数 → 管理员开开关的决策依据；
- 会诊 → Case 转化率 → 衡量方案 C 是否成立。
