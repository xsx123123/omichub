# 01 跨模式共性问题

三种模式共享的系统性根因,修复时应统一设计而不是各修各的。

## C1. 流式请求全程单事务,断流即整轮回滚(高)

- 位置:`src/omichub/api/v1/chat.py:119-163`,配合 `src/omichub/api/deps.py:22-31`
- 问题:`generate_sse` 复用请求级 `DbSession`,只在 `"done"` 后 `await db.commit()`;生成器被关闭/取消时走 rollback。前端有中断机制(`frontend/src/composables/useAgentChatStream.ts:375,384` AbortController),用户中途停止后:已 flush 的用户消息、AI 占位消息、handoff 审计事件(`chat_service.py:5644-5648`)、会话 meta 全部回滚,但前端已渲染——历史与 UI 永久不一致。一轮对话最长可跑 100~1000 轮工具循环(`chat_service.py:4765`),长事务还长时间独占连接池连接并持有会话行锁(代码注释自述因此引发过 plan 被擦除的 bug)。
- Studio 侧叠加问题:`register_artifact_report`(`studio_context_service.py:391`)在工具执行时已把产物复制到报告中心,DB 回滚后留下孤儿文件。
- 修复:关键节点(用户消息落库、handoff 事件、artifact 报告行)用独立会话即时 commit;或把文件复制延迟到 commit 后;前端"停止"后提示"本次回复未保存"。

## C2. 同一会话无服务端并发锁(高)

- 位置:`chat.py:102-173`;并发控制只靠前端 `isStreaming`(`useAgentChatStream.ts:381`)
- 问题:两个浏览器标签对同一 session 同时发消息,两轮 agent 循环并发改 `sandbox_meta`(共享 JSONB,已出过多丢更新 bug)、并发在同一沙盒写文件/执行,消息 timeline 交错。
- `sandbox_meta` 的"读快照→改→整体赋回"在三条并发路径间互相覆盖(lost update):SSE 持有 meta 快照(`chat.py:252-261`)× 超频轮写回(`chat_service.py:2748-2757, 2978-2998, 3004-3017`)× watch 写回(`agentteams_case_watch_service.py:109-114`)。
- 修复:Redis 每会话流式锁,冲突返回 409;高频键移出 `sandbox_meta`(独立列/Redis);或用 `SELECT ... FOR UPDATE`/乐观锁。

## C3. SSE 无心跳、前端重连策略差(高)

- 审批等待(`studio_approval_service.py:109-132`,BLPOP 300s)期间 SSE 零字节,nginx/网关常见 60s 空闲超时即切断;连接一死,消费决议的 BLPOP 随之消失。
- `AgentTeamsCaseView.vue:294`:断开后固定 300ms 无限重连,无指数退避/次数上限/抖动;端点持续 4xx/5xx 时形成 ~3 次/秒重连风暴。同时 20s 轮询与 SSE 并行,每条 `case.state_changed` 又触发全量 refresh,同一数据三条通道重复拉取。
- 修复:SSE 层加周期性心跳(如 15s 注释行);前端指数退避(1s→30s 封顶)+ 失败上限后退回纯轮询;SSE 健康时暂停轮询。

## C4. 流式 token 用量统计系统性丢失(高,一行修复)

- 位置:`src/omichub/infrastructure/ai_provider/litellm_provider.py:220-228` 与 `:128`
- 问题:`stream_chat` 只从 chunk 读 `chunk.usage`,但 `_build_kwargs` 的 override 白名单不含 `stream_options`,从未传 `stream_options={"include_usage": True}`。OpenAI 及多数兼容端点流式默认不返回 usage,于是 `record_ai_call_metrics(..., usage=None)`(:247)记录 token 全 0。流式是主链路,`ai_metrics_service.py` 的日趋势、模型分摊、成本告警全部被大幅低估。
- 修复:kwargs 注入 `stream_options={"include_usage": True}`(litellm 对不支持端点自动降级)。

## C5. LLM 公共层无重试(高)

- 位置:`litellm_provider.py:90-137`
- 问题:kwargs 无 `num_retries`(litellm 默认 0),429/限流/瞬时网络错误直接抛给 ReAct 循环,整条流失败。超时配置是有的(`config.timeout`,:101)。
- 修复:`num_retries=2~3`,仅对 `RateLimitError`/`APIConnectionError`/`Timeout` 重试。

## C6. 全局 SSE 长连接泄漏(高)

- 位置:`frontend/src/stores/agentHub.ts:973-974`
- 问题:`selectSession()` 对任意会话都启动 `startAgentTeamsCaseEvents(id)` + `startRoomEvents(id)` 两条 fetch 长连接;agentHub 是全局单例 store 无 `onScopeDispose`,用户导航到 `/tasks`、`/settings` 后连接一直挂到服务端主动关闭。对普通单 Agent 会话这两条流完全是无谓开销。
- 修复:仅在 `session.multi_agent` 或存在 AgentTeams case 时启动;路由离开 AI 区时统一 stop。

## C7. 指标缓冲写库失败静默丢弃(中)

- 位置:`src/omichub/core/ai_metrics.py:92-94` — flush 失败整批丢弃仅 warning;进程退出丢一个刷写间隔。这是用量统计/成本告警的唯一来源。
- 修复:加失败计数指标,避免 DB 故障期间成本告警静默失效。
