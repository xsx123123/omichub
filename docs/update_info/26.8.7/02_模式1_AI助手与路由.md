# 02 模式 1:简单 AI 助手 + Router 路由

链路:`/chat/stream` → `ChatService.stream_agent_chat` → `_route_to_agent` → 目标 Agent/handoff;另有 WS Copilot 旧链路 `ai.py` → `AIService.stream_chat`。

## 高严重度

### H1. 路由决策完全丢失多轮上下文,且每条消息都重新路由

- 位置:`src/omichub/application/services/chat_service.py:2317-2327`;`:4127-4129` 注释明确"同一会话的每条消息都重新路由"
- 问题:路由 LLM 调用的 `messages=[{"role": "user", "content": user_text}]` 只传当前一条消息,不带会话历史。用户说"继续""按刚才的参数跑样本 B"这类指代性跟进时,路由器零上下文决策,几乎必然误路由到 general fallback。同时每条消息多付一次 LLM 调用的延迟和成本。
- 修复:路由请求带最近 N 条对话摘要;或同一会话已路由的专家做"粘性"(follow-up 默认留在当前专家,仅新意图明显时重路由)。

### H2. 路由失败被静默吞掉,fallback 时用 router 人格直接回答用户

- 位置:`chat_service.py:2430-2432`(`except Exception` 仅 `logger.warning` 并 `return None, None`);router system prompt 见 `agent_service.py:77-85`
- 问题:路由异常后调用方继续用 router 自己的 ctx 跑完整对话,而 router 的 prompt 要求"只输出路由 JSON、禁止解释性话术"——模型在此约束下直接面对用户问题,容易输出裸 JSON 或异常话术。`_extract_route_json` 解析失败(`:2328`)同样静默落到 general(`:2375-2379`),用户只看到"已匹配通用助手",无降级提示。
- 修复:路由失败给用户可见的降级事件;fallback 应答换用通用对话 prompt。

### H3. Provider 重试时无条件丢弃 tools

- 位置:`src/omichub/infrastructure/ai_provider/openai_compatible.py:223-237`
- 问题:`attempt_tools = tools if attempt == 0 else None`——无论重试原因是"带 tools 空响应"还是"瞬时网络错误"(`:265-266` retryable 分支),第二次尝试一律去掉 tools 并追加 `_NO_TOOL_FALLBACK_NOTE`。一次网络抖动就让该轮模型无法调用任何工具(包括 ask_user、分析提交),用户无感知。
- 修复:仅当首试"空响应且疑似 tools 不兼容"时才去 tools 重试;网络错误重试保留原参数。

### H4. 流式单事务回滚

见 `01_跨模式共性问题.md` C1(对模式 1 同样适用)。

## 中严重度

### M1. 路由输出 max_tokens=200,fanout/consult 类 JSON 必然频繁截断

- 位置:`chat_service.py:2322`;路由 prompt(`:186`)要求输出含 `fanout_tasks`、`consult_agent_ids` 的 JSON,200 token 很容易截断 → `_extract_route_json` 失败 → 静默 fallback general。
- 修复:提高到 800~1000,或对截断显式检测告警。

### M2. YAML 关键词路由可劫持 LLM 意图判断,平局裁决随意

- 位置:`src/omichub/application/services/flow_registry.py:381-392`;直通逻辑 `chat_service.py:2293-2299`
- 问题:任一 `trigger_hints` 子串命中即以 confidence 0.98 直通对应 stage agent,完全绕过 LLM 路由;`score` 并列时 `max(matches)` 按 `(score, agent_id)` 元组字典序决胜,结果取决于 agent_id 字符串排序而非语义。用户随口提"质控"也会被直通流程 agent。
- 修复:命中关键词只作为 hint 注入路由 LLM;或要求最低命中数 + 平局确定性规则。

### M3. 路由纠错规则硬编码 agent_id

- 位置:`chat_service.py:2347-2374`(`target_id.startswith("agent-scrna")`、`"agent-rnaseq" in valid_ids` 写死)
- 修复:改为按 category/features 标记判断。

### M4. GET 读路径每次做磁盘解析 + 数据库写入

- 位置:`agent_service.py:277-279`;入口是公开 GET `/agents`(`api/v1/agents.py:23-28`)
- 问题:`list_agents` 每次调用 `ensure_builtin_agents`(重新解析全部 YAML + flush 内置同步)和 `_reconcile_model_bindings`,每次列表请求触发全量文件 IO 和潜在多行 UPDATE,并发请求互相覆盖。
- 修复:内置同步移到启动钩子或加 TTL 缓存。

### M5. `_reconcile_model_bindings` 在读路径静默改绑管理员的模型配置

- 位置:`agent_service.py:401-442`
- 问题:provider 被停用后,所有绑定它的 agent 被自动改绑到 fallback provider 并 flush,与 `_resolve_model` 注释声称的"严格按 Agent 绑定的 model_id 解析"(`:747-748`)直接矛盾。管理员停用模型做维护时,全体 agent 配置被悄悄改写。
- 修复:失效绑定只标记/告警,不自动改写。

### M6. 显式清空 mcp_ids 的 Agent 反而获得全部内置工具

- 位置:`agent_service.py:611-627`(`omichub_selected or not mcp_uuids`)
- 问题:管理员把 `mcp_ids` 置空(意图收缩工具面)时,因 `not mcp_uuids` 为真,整套 omichub-tools builtin 工具被注入,工具权限边界与配置意图相反。
- 修复:区分"从未配置"(NULL)与"显式为空"([])。

### M7. handoff 白名单对显式列表不检查目标是否为 router

- 位置:`agent_handoff_service.py:79-85` — 禁止转交路由 agent 的检查只在 `allow_all_active_targets` 分支;显式 `allowed_targets` 写入 router id 可形成 router→router 转交(仅受 max_hops≤5 限制)。
- 修复:router 检查移到两个分支之外。

### M8. 执行确认门靠关键词子串判定,误判即自动进入 Studio 执行

- 位置:`chat_service.py:221-228`(`_is_route_execution_confirmation`)+ `:4143-4183`
- 问题:用户消息含"现在开始""确认执行"等子串且 gate target 匹配,就 `auto_start=True` 并把会话切成 studio 模式。闲聊中出现这些词(如"我们现在开始讨论")即被误判为执行授权。
- 修复:确认应由前端确认卡/结构化事件触发,而非文本子串。

### M9. WS Copilot 链路安全缺口(整条旧链路)

- `ai_service.py:269-277` + `ai_tools.py:44-60`:工具命中后直接 `task_service.submit`,不走 `ai.py:173` 的 tool-confirmations 确认流;
- `ai_service.py:321-346`:`_extract_tool_calls` 从模型正文解析 ````tool` 代码块执行工具——非 FC 模型可被提示注入诱导输出该块而直接提交计算任务;
- 整条 WS 链路没有 `_ensure_cookie_balance` 之类的余额/限流检查(对比 `chat_service.py:3866`)。
- 修复:submit_task 统一走确认服务;补计费闸;逐步下线文本块工具协议。

### M10. `list_samples` 目录为空时伪造 demo 数据

- 位置:`ai_tools.py:97-101` — 返回 `demo_pbmc.h5ad`、`demo_tumor.h5ad` 假样本,模型会把不存在的文件当作真实用户数据陈述,与平台"只陈述真实结果"的规范(`agent_service.py:64-75`)冲突,主动制造幻觉。
- 修复:返回空列表 + 明确提示。

### M11. Copilot 链路上下文只按消息条数截断,不估 token

- 位置:`ai_service.py:175-176` — 单条粘贴大文件的消息即可打爆上下文窗口;主链路有 token 估算(`chat_service.py:1970-2033`),WS 链路没有。
- 修复:复用同一套 token 估算压缩逻辑。

### M12. WS 端点:原始异常外泄 + token 走 query 参数

- 位置:`api/v1/ai.py:159-163`(`f"内部错误:{e}"` 把 DB 错误、内部路径直接发给客户端);`ai.py:104` JWT 在 query string,会进入反向代理/访问日志。
- 修复:对外只发通用错误码;token 改子协议或首条消息认证。

## 低严重度

- **L1** handoff 后交接信息全部依赖 LLM 写的 ≤2400 字节摘要(`agent_handoff_service.py:213-219` + `chat_service.py:5693`),历史是否保留取决于源模型摘要质量。建议 packet 之外附最近 K 条原始消息。
- **L2** `route_execution_gate` 可能长期残留(`chat_service.py:4159-4165`):只在"确认"或再次路由到同一 agent 时清理。建议 gate 加 TTL 或按消息轮次失效。
- **L3** 后端无会话级并发锁(见共性问题 C2)。
- **L4** 杂项:`ai_service.py:308-311` tool arguments JSON 解析失败静默变 `{}`;`agent_service.py:142-143` fallback 查询无 `order_by`,fallback 模型选择不稳定;`ai_service.py:128` 新会话默认模型写死 `settings.kimi_model`;`agentHub.ts:1946` handoff 后前端立即改 `session.agent_id`,若后端回滚则前后端 agent 绑定分裂,下一条消息触发 `chat_service.py:3935` 的"会话绑定的 Agent 与当前请求不一致",会话卡死。

## 架构建议

`ai.py` WS Copilot 与 `/chat/stream` 主链路功能重叠且防护水平不一致(`agentHub.ts:10` 也有"旧 chatStore 待废弃"的架构级 TODO),建议明确模式 1 的唯一正统入口并收敛旧链路。
